# NJ03 project decisions for lexical slots and focused axes

Status: independently reviewed requirement decision at `8c82b7a`; **not an implemented or executed check**. This fixes the meanings of N02 and N03 in [NJ03KotlinCurriculumPlan.md](NJ03KotlinCurriculumPlan.md) before candidate source mutations or compiler diagnostics are observed. The 32 old skill rows in [NJ03CurriculumIndependent.cases](NJ03CurriculumIndependent.cases) remain unchanged. These are new project rules, not claims of old-validator parity.

## N02: the filterable lexical slot is declared by the project

The current Polish and English curriculum permits a lexical filter only on the `noun` seed slot. Its allowed `where` keys are `nounId` (a noun identity) and `gender` (a noun feature); each value must resolve in that language's typed noun catalog. The project validator must resolve `slot` against this explicit filterable-slot declaration before looking up any `where` value. A generic Core data reader must not hardcode `noun`, and the Kotlin exercise engine must not infer a new filterable slot from a map key or silently use a default. Later adjective or owner filters require a separately reviewed project declaration and positive/negative examples.

Positive requirements: English `en:role.recipient` with `slot=noun` and `nounId=wife`, and Polish `case.acc.f` with `slot=noun` and `gender=f`, remain valid. Negative requirement: keep the English row and its valid noun IDs intact but change only `slot` to `owner`; reject at the `slot` source value as an undeclared filterable slot, before attempting noun lookup or exercise generation. `owner` can exist as a runtime lexical value, but it is not a seed slot authorized for curriculum filtering. A separate `slot=adjective` mutation must also reject until an adjective filter declaration and matching key/value contract exist. The old schema checks nonempty slot text and does not prove either rejection.

## N03: a focused axis cannot also be fixed

`focus` asks the exercise to vary one feature from one catalogued value to another; `fixed` holds **other** features constant. If `focus` is present, its feature key must not appear in `fixed`, regardless of whether the fixed value equals the `from` value, the `to` value or another catalogued value. This is a project curriculum relation checked before generation, without mutating the skill or exercise state. It is separate from the existing no-op `from == to` check and from individual feature/value resolution.

Positive requirements: `en:role.object` focuses `Case:Subj>Obj` while fixing `Tense=Pres`, `Person=1`, `Number=Sing`; `en:possessive.my` has no focus and may fix `Case=Obj`. Negative requirements: starting with `en:role.object`, add `Case=Subj` to `fixed`; in a second independent mutation add `Case=Obj` instead. Both values are valid catalogued values, but both candidates must reject at the added `fixed.Case` source key as a focus/fixed conflict. An unrelated fixed feature remains valid. The old validators do not establish this new relation.

The independent tester must pin the exact Biome source bytes and UTF-16 locations for these accepted and rejected cases after syntax is selected and **before** candidate diagnostics run. The project developer then proves the relation through the same typed validator used by the Kotlin build and an executed Kotlin consumer; copied expected values from generator output do not count. If a shared `.given` contract with `FACT`/`QUERY` and `LET` yields one useful decision plus a real Kotlin EditMode test at acceptable P8 cost, it may own the relation. Otherwise one small pure Kotlin/project helper owns it. Kotlin PlayTest remains unsupported until a real runner exists.
