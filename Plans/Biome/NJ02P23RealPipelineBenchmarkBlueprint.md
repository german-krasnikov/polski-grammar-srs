## Reproducible workload

Before implementation, seal full compiler/product revisions and SHA-256 of the 14 registry source rows, frozen 32 `pl`+`en` DSL skill rows after NJ03, definitions, types, project catalog, printer code, generated Kotlin, and exact test launcher. Store the seed and transformations as readable line records in **NEW** `Plans/Biome/NJ02P23BenchmarkInputs.cases`. Preserve independent expectation files byte-for-byte. Build all workloads in memory from those immutable sources; do not commit 1,000 copied subject facts or derive expected semantics from a printer.

Run **two labeled families** at N=10, 100, 1,000; N is the number of actual authored declarations sent through the reader, type checker, project validator and printer, not the number of loops over one pre-parsed value:

1. **Registry family, compiler-only possible now:** cycle the seven real construction and seven feature record shapes in their authored order, retaining nested description, gloss, optional/null/empty and Unicode forms. Replace only identity tokens with deterministic alphabetic suffixes (`core.*.benchaa`, `CaseBenchaa`, etc.) that satisfy today's product name checks; rewrite a copied construction's axis to the corresponding copied feature where appropriate. Require at least one of each kind at every N. Check the original 14-row input separately against its frozen exact ledger. The scaled source must pass `validateRegistrySource`; no test-only parser or second authored registry table is allowed. Index/lookup and output comparisons assert N distinct facts, order and selected real field values. A generated Kotlin value may be compiled and checked by the real `CoreCatalog` in today's Gradle build only with the receipt marked **JSON-fed transitional**. The consumer should validate skills referencing copied identities rather than only count generated rows. No current Kotlin run can count toward the final no-JSON verdict.
2. **Curriculum family, after NJ03 for CoreCatalog; after complete no-JSON inputs for positive engine:** take the complete 16+16 real DSL records. Cycle their actual text shapes to N declarations; replace unique skill IDs and rewrite prerequisites to corresponding IDs within the workload, using deterministic forward/backward references and one acyclic order. Keep focus/fixed/lexical-filter contents, null/empty distinctions and both languages. Include a stable typed registry and lexicon catalog; map necessary identities consistently, never make unknown-reference failures disappear by dropping a prerequisite. The project validator must run its duplicate, construction, feature, noun and prerequisite/cycle traversals. The emitted `List<SkillSpec>` must compile and feed `CoreCatalog.checkCurriculum` for both languages. A positive `PackEngine.exerciseGenerator` benchmark waits until recipes, forms, realization and all its exercised inputs are non-JSON, and until Gradle no longer compiles JSON-embedded common sources. Record the count of each nested shape in every N sample. A separate deliberately wrong nested member, unknown reference and two-edge cycle at N=1,000 must still point to exact frozen code/UTF-16 positions; success-only timing is insufficient.

The 14 original facts and the 32 skills have separate provenance. A synthetic scale transform is a stress workload, never new course content or a replacement oracle. The 10/100/1,000 inputs are frozen before measuring; if a transform cannot preserve valid references or source coordinates, stop and repair the **fixture algorithm**, with an independent review of the changed workload. Do not edit expected outcomes to fit the candidate.

## Fixed protocol and admission limits

This document predeclares benchmark **admission envelopes**, not new production execution caps. A change to them requires a reviewed amendment committed **before** the first measured run; a slow result cannot be repaired by raising a limit. Keep the existing Core `PROGRAM` defaults and all production counters unchanged. For each family/stage, record exact input bytes, declarations, nested members, output bytes, compiler/toolchain versions, machine/OS, revision IDs and clean/dirty state in a plain-text receipt. Run with one worker and no competing Gradle or compiler jobs. Compilation of compiler packages, loading/importing Node and Gradle startup are separate columns; never add startup into per-record runtime or subtract it without reporting it.

| N=1,000 stage | Fixed envelope | Required ≥2× headroom verdict |
| --- | --- | --- |
| Warm Node reader + typed check + actual project validation + real printer(s): Kotlin for registry, Kotlin **and** TS for curriculum | 2,000 ms wall, 2,000 ms process CPU, 2,000,000 defined logical steps per family | Each observed measure ≤1,000 ms / ≤1,000 ms / ≤1,000,000 steps. Report each substage too; the registry's current validator covers identity/schema, while complete cross-reference validation waits for NJ03. |
| Kotlin `CoreCatalog.checkCurriculum` on generated values (in-process, after class load); later separately the positive engine path once all its inputs are non-JSON | 2,000 ms wall, 2,000 ms thread CPU, 100,000 defined logical steps **for each named consumer** | ≤1,000 ms / ≤1,000 ms / ≤50,000 steps for each; absent engine inputs or CPU are **NOT RUN**, not zero. |
| Fresh Kotlin Desktop Gradle compilation of generated N=1,000 source, then executable consumer test **on a proven JSON-free build** | 600 s wall and 600 s complete process-tree CPU; record Gradle configuration and Kotlin compile separately | ≤300 s each. A daemon or child process missing from CPU accounting invalidates the CPU verdict. Compilation has no claim to the reader's logical-step counter; current JSON-fed Gradle results are transitional only. |
| TS compile and Node execution of the real N=1,000 printer output (experimental lane) | 120 s wall and 120 s process-tree CPU | ≤60 s each. This does not authorize shipping TS. |

For steady-state CPU/wall use at least seven warm rounds across size: rotate `10→100→1000`, `100→1000→10`, `1000→10→100`. **Pair/alternate baseline and candidate only for the shared parse/type subset**; each pair sees identical text/type and 100/10/1 repetitions per 10/100/1,000 sample. Run the candidate-only full located-reader → typed check → project validation → real printer path in a separate interleaved series with the same N and repetitions. There is no baseline full pipeline with equal located/project guarantees, so never place its timing in a baseline/candidate pair or report a whole-pipeline speedup. Each timed batch handles roughly 1,000 declarations; disclose fixed setup work and divide by repeats. Measure `process.cpuUsage` and monotonic wall around the same batch, report all seven raw values for both series, median and minimum per call. Log output/assertions after each timed batch. Run a separate cold process per size for startup and separately record package build, Kotlin/TS compile and test launch, with at least three alternating cold samples where feasible. If runtime measurements are dominated by clock resolution or GC, enlarge **repetitions** equally in a predeclared new receipt; never weaken the envelope.

Linear checks use the same declared algorithmic work units: counted steps at N=100 ≤12× N=10, and N=1,000 ≤12× N=100; median wall and CPU per call meet the same growth with a fixed 1 ms noise allowance. Report per-declaration ratios and actual 10/100/1,000 source and output sizes. A measured pass also requires no hidden quadratic reference scan under 1,000, no budget rise, zero unclassified P14 differences and the frozen negative diagnostics. Compare the candidate with the accepted pre-change public reader only for their **shared parse/type subset**. Old-validator parity is supported by its frozen historical observations, not by reading its JSON files or timing it in this benchmark. Neither old path has all located guarantees, so no end-to-end baseline speedup factor exists. The later equal-guarantee A/B/C maintenance comparison has its own decision gate.

3. After NJ03 supplies all 32 DSL skills and typed language facts, run the curriculum compiler/printer and generated `CoreCatalog` cases, but keep any ordinary Gradle compilation transitional until its JSON-embedding tasks are removed/replaced. For final acceptance, first prove a clean production build graph and runtime reachability with **no application JSON**, including recipes, forms, realization and all exercised engine inputs; then compile and execute Kotlin generated skills and a positive engine case for Desktop, JS/Wasm and required Native hosts on one clean/fetchable compiler + product pair. Take controlled P23 timings on Desktop, record other hosts' behavior counts, run the real TS comparison printer in its isolated lane, and repeat full P14 and current gates on that immutable pair.
4. Independent tester reproduces the raw text receipt, mutates one reader location, one typed member, one project reference and one printer leaf to establish that each stage was traversed, and reviews step counter placement. Read-only reviewer checks P7/P8/P14/P17/P23 against exact file, line, failing case and observable consequence. A linked task or generated source is not execution evidence.

Stop Core promotion on any absent compiled/executed consumer, non-comparable workload, second authored fact authority, JSON input in the final benchmark/build/runtime path, unaccounted CPU child, stale compiler pin, omitted negative span, nonlinear growth or <2× envelope margin. A current JSON-fed Gradle run cannot be relabeled no-JSON by choosing only `CoreCatalogTest`; a guarded skill lookup cannot be relabeled positive engine execution. Preserve failures as evidence. This blueprint itself has not executed a benchmark, Kotlin/TS compiler, host or gate.
