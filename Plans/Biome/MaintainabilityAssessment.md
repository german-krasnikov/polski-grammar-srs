Status: **no full application port and no post-migration application-wide percentage**. Product branch `biome/full-port-2026` retains its native TypeScript/Kotlin/Swift sources and authored course JSON. The requested success criterion—every feature and test translated and exercised on the new DSL—is **NOT MET**. This report measures the two completed candidate changes against equal-behavior native controls; it does not extrapolate them to the whole app. The detailed plan and FP01–FP11 ledger are [FullPortPlan.md](FullPortPlan.md) and [FullPortAcceptance.md](FullPortAcceptance.md).

For the curriculum probe changing `fixed.Person`, one warm local edit–generate–validate run took **851.9 ms** with DSL and **127.6 ms** with direct JSON. For adding a valid prerequisite, the corresponding observations were **820.2 ms** and **117.1 ms**. These are one-off wall-time observations of different work, not controlled speed benchmarks; they show the extra generation step but cannot establish a stable 6–7× slowdown. The invalid-reference mutant was caught in both arms. The measured reduction in independent semantic edit sites for these two course changes is **0%**. That figure is a property of this candidate and these changes, **not** a claim that DSL improved or worsened maintenance of the whole application by 0%.

The first decision slice genuinely exercised generated TS/Kotlin code but failed its cost and clean-CI gates. The data slice passed direct `--check`, frozen semantic comparison, product validation, the full 268-test root suite and shared Kotlin Desktop/JS/Wasm suites (384/383/383 tests, zero failures/errors/skips); an independent tester reran the focused 34-test course suite and the freshness/invalid-prerequisite controls. A separate pre-port Kotlin browser baseline passed four selected Chromium scenarios on JS and four on Wasm. These passing subsets do not prove a DSL-translated app, its host UI, Android/iOS/macOS app interaction, or all FP01–FP11 cases. `npm run course:validate` runs the standalone curriculum validator for Polish by default; the English candidate also passed an explicit English curriculum validator.

The same-source baseline in [FullPortAcceptance.md](FullPortAcceptance.md) counts 22,991 physical lines of authored KMP production code and 882 lines of React production code, excluding course data and generated files. These are static size measures, not maintenance hours or LLM usage. No paired full-app change campaign, reviewer-time study, cold generation/compile comparison, startup latency, steady runtime, allocation profile, P23 N=10/100/1000 scaling, or provider usage measurement was performed. The compiler commit `2ab6275d59496e113cd2a17caf0f75d1c63174d2` remains local/unpublished, so clean-CI fetch and product artifact freshness are **NOT RUN**. Physical device and assistive-technology checks are likewise **NOT RUN**.

The current compiler can emit TS/Kotlin Logic and JSON from `.tables`, but Kotlin fact wiring for the tested decision remained handwritten, DECLARE/SURFACE reading is JS-only, FEATURE Kotlin/Python support is mostly portable/static, and there is no Swift Logic target. The app already uses one JSON pack to feed a generic Kotlin grammar/exercise engine; session lifetime, FSRS arithmetic, storage/recovery, Unicode physical operations and native UI belong to their current platform or model owners under [biome architecture](../../../../Python/biome-dsl/AI/ARCHITECTURE.md) and [principles](../../../../Python/biome-dsl/AI/PRINCIPLES.md). Translating those mechanisms or the nested pack data merely to raise DSL coverage would add an owner or copy without a demonstrated guarantee. The remaining small cross-language decisions (queue override and review-stat classification) also lack a credible P8 advantage over small native helpers at present.

The pragmatic restart condition is a **new, cohesive rule group** shared by real TS/Kotlin consumers, with independently frozen requirements, generated fact bindings/read plans for both languages, a compiler fetchable by clean CI at a verified immutable revision, and a paired native-helper comparison that actually reduces independent edit sites or catches a defect the equal-guarantee native implementation misses without unacceptable generation, review or runtime cost. Until such evidence exists, preserve existing owners and tests. Do not mark any FP row complete or report a post-transition maintenance saving.
