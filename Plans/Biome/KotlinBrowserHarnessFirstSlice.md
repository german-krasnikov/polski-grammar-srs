# Kotlin/JVM browser harness: first executable slice

Status: **architecture handoff; no harness, browser run, or Kotlin/DSL parity is claimed**. Product baseline `26f145d0af1e03bfbbca5040586a7bbc0ecd9d59` (2026-10-18). This plan implements step 3 of [KotlinOnlyCutoverAmendment.md](KotlinOnlyCutoverAmendment.md) and the B lane of [KotlinAssertionInventory.md](KotlinAssertionInventory.md) before any TypeScript browser spec is retired. The independent historical selection is [KotlinBrowserValidatorInventory.md](KotlinBrowserValidatorInventory.md): 171 Kotlin-web scenarios × 3 browsers per branch, plus 23 React/Chromium controls. Those are selected old cases, **not** replacement executions.

## First consumer and observed seam

The consumer is a **test-only** Kotlin/JVM process that drives the already built Kotlin browser app over loopback. `kotlin/composeApp/build.gradle.kts` declares both `js { browser(); binaries.executable() }` and `wasmJs { browser(); binaries.executable() }`; `kotlin/composeApp/src/{jsMain,wasmJsMain}/kotlin/polski/main.kt` mounts `TrainingWebApp` at `#root`. `:composeApp:jsBrowserDistribution` and `:composeApp:wasmJsBrowserDistribution` produce separate `build/dist/{js,wasmJs}/productionExecutable` directories. `:composeApp:composeCompatibilityBrowserDistribution` is the published dual-loader artifact but is **not** used to prove branch-specific execution in this slice. Web `kotlin/composeApp/src/webTest` and shared `jsBrowserTest`/`wasmJsBrowserTest` are useful unit/DOM evidence, not external Chromium/Firefox/WebKit UI evidence.

The accepted smoke requirement is: **from the Training page, activating the visible “Настройки” navigation button opens a visible “Настройки обучения” heading**. The independent historical control is `tests/browser/kotlin-native-web.spec.ts` (whole-file SHA-256 `fea98a7343b847372fb6676766c3de9a88f8147138f97b83d1`), whose 320-pixel navigation case observes this route and heading. The new test will own this expectation as a Kotlin-authored physical-host assertion, reviewed against the accepted behavior here; it will not read the heading from `SettingsWeb.kt`, generate the expected value from the built app, or reuse the old TS test at runtime. `WebNav.kt` gives the user-facing button label, `WebRouteController.kt` owns the transition, and `SettingsWeb.kt` renders the heading. Use the official [Java semantic locator and retrying assertion API](https://playwright.dev/java/docs/api/class-page): `page.getByRole(AriaRole.BUTTON, Page.GetByRoleOptions().setName("Настройки")).click()` followed by `assertThat(page.getByRole(AriaRole.HEADING, Page.GetByRoleOptions().setName("Настройки обучения"))).isVisible()`. Do not count the old spec's other viewport, layout, keyboard, focus, theme, or no-optics assertions as covered by this smoke.

Use the real Kotlin JVM plugin version `2.4.20` already pinned in the catalog. Register both `Test` tasks over the same compiled test classes with **separate** XML/report directories and branch-specific `polski.browser.dist`/`polski.browser.branch` system properties; each depends on its matching `:composeApp:*BrowserDistribution` task. Do not let the default `test` task accidentally discover browser cases without a distribution property; either a dedicated browser source set or an explicit test include plus a meaningful ordinary helper test must make `check` behavior unambiguous. The developer chooses the smaller verified Gradle wiring, records the actual task graph, and never treats an empty `test` result as a green browser gate. Set `maxParallelForks=1`, no retry, finite server/browser/assertion timeouts, and disable up-to-date reuse for the two browser execution tasks so every reported run truly executes. Local browser installation is an explicit task, not a test skip.

The driver pin is [Playwright Java `1.63.0`](https://playwright.dev/java/docs/test-runners). Its corresponding [tagged browser manifest](https://raw.githubusercontent.com/microsoft/playwright/v1.63.0/packages/playwright-core/browsers.json) pins Chromium **153.0.8010.12** (revision **1243**), Firefox **155.0** (revision **1543**) and WebKit **26.6** (revision **2359**, macOS 14 override 2251). Install through the same Maven/Gradle-resolved Java CLI, `./gradlew :browserAcceptance:playwright --args=install`, never a separately versioned root `npx playwright`; fail the task if a required executable is absent or its runtime version does not match the pin. Record the installed executable paths, the Playwright JAR SHA-256, each `Browser.version()`, OS/architecture and distribution hashes in a **plain-text** receipt. The browser cache is tool state, not product data. The Java implementation may use Playwright's internal transport; it must not author or persist application JSON, Playwright storage-state JSON, JSON reporters or traces in this lane.

## Lifecycle, freshness, and output rule

Each branch task resolves only its own `build/dist/<branch>/productionExecutable` beneath the current worktree. It first verifies `index.html` and `composeApp.js` exist and records SHA-256 of both; the JS and Wasm served `composeApp.js` hashes must differ. The server starts after the distribution task succeeds, binds a fresh loopback port, checks `/index.html` readiness with an HTTP request, then passes its actual URL to the page. It refuses an outside-worktree dist override, path traversal, missing file, or stale fixed port; there is no `reuseExistingServer`/unrelated browser tab. On failure, JUnit teardown closes each context and browser, stops the server and executor, and reports cleanup errors. One fresh context per engine uses `pl-PL` locale and `Europe/Warsaw` timezone. Observe the served `composeApp.js` response and compare its bytes/hash to the chosen on-disk branch artifact before counting the UI assertion; on Wasm, also prove the Kotlin app Wasm payload was fetched successfully rather than silently accepting a JS fallback. Do not infer branch execution merely from a build task name or the page title.

**Current source still produces JSON on an empty browser profile:** `TrainingStore.start()` queues a fresh save, and `WebProgressRepository` encodes and writes the old progress format. Merely denying `Storage.prototype.setItem` would still let the codec create a JSON string in memory, so it cannot satisfy the owner's full no-JSON rule. Implement the harness now, but gate the accepted six-case UI run on the product's text-wire startup/save replacement and its no-JSON source/bundle/storage check. Until then, a browser launch against this legacy build is at most an explicitly labelled historical driver diagnostic; it does not count as the first accepted smoke, no-JSON proof or Kotlin-only cutover evidence. Never seed JSON, waive storage errors broadly, or silently run a JSON-writing normal profile. Once the text path exists, use a fresh normal browser context, assert no application JSON bytes are written, and run the same route action; legacy JSON is supplied only to separate one-time read-only migration controls.

No root `npm ci`/TS config/test runner is required by this harness. Kotlin/JS and Wasm Gradle bundling still uses its own Node/Yarn build tools and lock; trace those as **build-only** dependencies before any root npm deletion. The harness never emits JSON application fixtures, save files or machine reports; Gradle JUnit XML plus a reviewed UTF-8 text receipt are sufficient. Existing `playwright.kotlin.config.ts` remains only a historical comparison until its assertions have Kotlin replacements.

## Acceptance sequence and evidence

1. **Compile/install probe (not UI proof).** From `kotlin/`, pin/resolution check for the JVM module and run `./gradlew :browserAcceptance:playwright --args=install --console=plain`. Record JAR and browser revisions. A missing launchable binary is FAIL, never SKIP. Do not call this a completed UI or no-JSON test.
2. **Fresh separate artifacts.** From `kotlin/`, run `./gradlew :composeApp:jsBrowserDistribution :composeApp:wasmJsBrowserDistribution --console=plain --max-workers=2` on the candidate SHA. Hash served `index.html`, `composeApp.js` and Wasm payload; a prior `*ProductionWebpack` run alone does not refresh `build/dist` (the historical stale-dist incident is documented in `Plans/Kotlin/Stage-InventoryCompletion-Tester.md`).
3. **One actual assertion, six executions after the text-wire gate.** From `kotlin/`, run `./gradlew :browserAcceptance:browserJsTest :browserAcceptance:browserWasmTest --console=plain --max-workers=2` on that same no-JSON product candidate. Require **3 selected / 3 executed / 0 skipped / 0 failed** for each branch, one in each Chromium/Firefox/WebKit, with the heading visible after a real click. A build, browser launch, HTTP 200, old TS `--list` or Kotlin DOM test cannot substitute for these six outcomes. Read both Gradle JUnit XML files and the plain-text browser/branch receipt.
4. **Negative controls.** In a disposable test copy or parameter, change the expected heading so one engine fails with an assertion (proves the check discriminates); remove/corrupt the selected branch bundle so the task fails before UI execution; deny launch of one pinned browser so the task fails without skip. Restore the candidate and run the focused six-case matrix again. Do not commit a broken expected value or rewrite it from rendered output.
5. **Independent review.** Reviewer checks source expectation against the old case and current product requirement, exact artifact/driver identity, raw selected/executed/skip/fail counts, cleanup and no-output proof. Only then mark **this one** navigational assertion mapped. The rest of 171×3 and 23 React controls remain NOT MAPPED/NOT RUN. Device, screen-reader, storage and DSL execution gates remain separate.

The detailed receipt must include command, cwd, product and compiler SHA, dist SHA per branch, OS/JDK, driver/browser versions and revision, test IDs, each engine's selected/executed/skipped/failed counts, normal-storage/no-JSON check, unexpected page/console errors, and teardown result. A failure artifact is local text or PNG only, never JSON. Any missing row, skipped engine, stale artifact or unavailable browser leaves the corresponding criterion **NOT RUN/FAIL**, not PASS.

## Scaling rule after the smoke

Before migrating the 171 Kotlin-web TS scenarios and triaging 23 React controls, decompose each old spec into observable assertions and map an independent accepted expectation to a Kotlin test ID and target branch/engine. Carry over semantic behavior, not obsolete React DOM or JSON export shape; mark any changed requirement explicitly. Use Biome `.contract` facts and independent `.examples`/`.sources` for reusable decisions, and generate typed Kotlin inputs only after a real executor is proved. Navigation, focus, downloads, storage failure/retry and browser lifecycle stay in the Kotlin host harness; a DSL PlayTest declaration without an executor does not count. Reuse `DistributionServer` only for HTTP mechanics, not for product policy or expected text.

Measure the first test-only native helper against a proposed DSL browser adapter: authored/maintained LOC, number of semantic edit sites for a changed heading or route, startup time, one-case runtime, and cost per additional accepted scenario. Keep the small JVM physical adapter if DSL adds no measured guarantee; extend the project DSL runner only if a second real consumer shares the semantic rule and the executor actually runs on Kotlin. This is P4/P8/P15/P17/P22 of `AI/ProjectMigratioPrincipals.md`, not a target percentage of DSL lines. No new browser DSL syntax is authorized by this first slice.
