# NJ05 Android progress admission: source-level correction

Status: **correction of a host-scope claim, not a changed legacy byte oracle or an executed Android result**. The independently reviewed `numeric-admission.cases` at `6d3b3ef` fixed six exact old-input recipes and hashes. Its PG-10000001 sentence incorrectly grouped Android with iOS/macOS as a repository-level pre-write rejection. The six recipes, hashes, common-decoder expectations, macOS execution evidence and A/C size arithmetic are unchanged. This correction is separate from any candidate codec and requires independent review before it is used as an Android host expectation (P15/P17).

At product source `d5b4446`, `kotlin/androidApp/src/main/java/dev/polski/grammarmatrix/AndroidSessionViewModel.kt:241-251` reads an imported URI through `readUtf8Limited` **before** calling the repository. That function in `AndroidProgressRepository.kt:126-134` rejects a stream over 10,000,000 bytes. This is the UI picker path. By contrast, `AndroidProgressRepository.kt:61-80` calls `ProgressCodec.decode(raw)` directly, then writes `raw` with `write(document, raw)` and only afterwards calls `read(document)`, which uses the limited reader. The direct repository method has no input-size check before write. From the source and the executed common-decoder admission of PG-10000001, a direct 10,000,001-byte call is expected to reach a write and fail on readback; **this is an inference**, not an observed Android-device result. A returned failure alone would not prove that the old bytes were preserved or that no new JSON was written.

The independently tested macOS path remains as reported: `MacProgressRepository.importJson` checks byte size before decode/write, and its 2/2 macOS Native plus-one tests passed. iOS and Android UI/direct-repository paths, existing old-file/backup behavior, and exact-at-limit readback are **NOT RUN** for this correction. Before N26 or NJ06 acceptance, an independent tester must execute Android UI-picker and direct-repository plus-one cases separately on an actual Android runner, with a fresh file and an existing old file. Assert full old/new/backup bytes, return result, write timing and recovery state; do not silently use the UI cap as the direct repository contract. The new migration must refuse unsafe writes before effects and must retain old bytes on failure.
