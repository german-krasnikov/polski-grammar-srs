Статус: **архитектурный кандидат для независимого ревью; byte-oracle NOT FROZEN, код не написан, браузерный прогон и полная P8/P23-приёмка NOT RUN**. База изолированной ветки — `biome/full-port-2026@ec9aeec1fbd02cea73e4feeaa145452a5eea56d3`. Нормы: `AI/ProjectMigratioPrincipals.md`, [NJ01PerformanceArchivePlan.md](NJ01PerformanceArchivePlan.md), независимые [NJ01PerformanceWriter.cases](NJ01PerformanceWriter.cases) и [NJ01PerformanceWriterFreeze.md](NJ01PerformanceWriterFreeze.md). Этот документ задаёт предлагаемый wire-контракт до принтера; он не заменяет независимые ожидания P01–P04/N01–N19 и не объявляет NJ01 завершённым.

## Выбор границы и владельцев

Проверенный [P8/Node probe](NJ01P8NodeFeasibilityProbe.md) дал **NO-GO для Kit A в текущей поставке**: продукт поддерживает Node `^20.19.0 || >=22.12.0`, Kit требует `>=22`, его локальный tarball не даёт публичный `exports`-импорт, а `formatDataValue(-0)` выдаёт `0`. Прямой импорт внутреннего `dist` не является контрактом поставки. Исправление Kit остаётся возможной отдельной задачей общего DSL, но сейчас не блокирует малый продуктовый опыт. Следующий кандидат — небольшой статичный нативный helper B; проба доказала только частичные run-row случаи, **не** полный отчёт и **не** превосходство по равным гарантиям. Выбор B для *эксперимента полного отчёта* не означает окончательный P8 GO или разрешение массовой замены writers.

Измерительный сценарий и физический эффект принадлежат `Plans/Kotlin/archive/scripts/benchmark-glass-rollout.mjs`: запуск браузера, сбор фактических интервалов, закрытие страниц/контекста/браузера, публикация файла. Проектный валидатор решает допустимость полного отчёта и проверяет производные числа; общий helper реализует только конечные binary64, строки, канонические строки/байты и строгий разбор. Не вводить новый синтаксис Biome DSL для одного механического benchmark-output (P4/P8/P13). Тестовые требования P01–P04/N01–N19 остаются независимыми от реализации; ни helper, ни writer не являются их оракулом (P15). В существующем файле есть два дефекта, которые нужно исправить по контракту: `intervals.filter(value => value > 0)` скрывает N19, а `writeFileSync(...json...)` после **каждого** engine публикует неполный результат. Новый writer проверяет весь список двигателей и пишет один раз после закрытия всех принадлежащих ресурсов.

Новые модули предложены по назначению, точные имена могут быть упрощены без смены контракта: `scripts/perf/measure-text.mjs` (NEW: чистая механика строк/чисел/UTF-8, без FS и Playwright), `scripts/perf/glass-rollout-measure.mjs` (NEW: схема v1, порядок, полные семантические проверки, `encodeGlassRollout(result) -> Uint8Array`, `decodeGlassRollout(bytes) -> result`, без FS), изменяемый `Plans/Kotlin/archive/scripts/benchmark-glass-rollout.mjs` (сбор и атомарная запись). Тесты `tests/perf/glass-rollout-measure.test.ts` (NEW) вызывают публичный кодек и не требуют браузера; отдельная проверка атомарного writer работает во временном каталоге. Нет глобального состояния, импорт-time I/O, зависимости от соседнего compiler checkout и скрытого JSON. Предметные пороги, порядок paired A/B и статистика имеют **одно** место в `glass-rollout-measure`; не повторять их в generic helper и тестовом адаптере. Для другой формы benchmark нужен её собственный schema adapter поверх общей механики, не расширение этого v1 случайными полями.

## Предлагаемая грамматика `.measure` v1

Файл — строгие UTF-8 байты без BOM, CR и пустых строк; каждая строка оканчивается LF (`0A`). Теги и разделители — ASCII; столбцы разделяет ровно один TAB (`09`). Внутри значения TAB/CR/LF не встречаются сырыми. Имя профиля в заголовке — `glass-rollout`; это не универсальный контейнер всех пяти writers. Никакого JSON-фрагмента, вложенного blob или неописанных полей нет. Неизвестная версия, тег, столбец, порядок или хвостовые байты — ошибка. Все индексы десятичные ASCII без знака и ведущих нулей, кроме самого `0`.

Порядок строк и количество столбцов фиксированы:

```text
measure<TAB>glass-rollout<TAB>1
date<TAB>s:<escaped ISO UTC timestamp>
url<TAB>baseline<TAB>s:<escaped URL>
url<TAB>candidate<TAB>s:<escaped URL>
rounds<TAB><positive integer>
duration-ms<TAB><positive finite binary64>
viewport-css-px<TAB><positive integer width><TAB><positive integer height>
dpr<TAB><positive finite binary64>
color-scheme<TAB>s:<escaped text>
reduced-motion<TAB>s:<escaped text>
units<TAB>viewport=css-px<TAB>interval=ms<TAB>percentile=ms<TAB>threshold=ms
engine-count<TAB><positive integer>
  engine<TAB><engine-index><TAB>s:<name><TAB>s:<browser version>
  run-count<TAB><engine-index><TAB><2 * rounds>
    run<TAB><engine-index><TAB><run-index><TAB><round><TAB><baseline|candidate><TAB><frames><TAB><p50-ms><TAB><p95-ms><TAB><p99-ms><TAB><over25><TAB><nav-filter><TAB><card-filter>
    interval-count<TAB><engine-index><TAB><run-index><TAB><frames>
      interval<TAB><engine-index><TAB><run-index><TAB><interval-index><TAB><positive finite binary64 ms>
  paired-delta-count<TAB><engine-index><TAB><rounds>
    paired-delta<TAB><engine-index><TAB><zero-based round-index><TAB><finite binary64 ms>
  summary<TAB><engine-index><TAB><baseline-median-p95-ms><TAB><candidate-median-p95-ms><TAB><paired-median-delta-p95-ms><TAB><paired-range-min-delta-p95-ms><TAB><paired-range-max-delta-p95-ms>
end<TAB>sha256<TAB><lowercase 64-hex digest>
```

Отступы в блоке выше показывают повторение, **не** входят в файл. `engine-index`, `run-index`, `interval-index`, индекс paired delta непрерывны с нуля и идут в указанном порядке. `engine-count` равен числу следующих engine-блоков; у каждого ровно `2 × rounds` run-блоков. В нечётном раунде baseline, candidate; в чётном candidate, baseline. Строка `run` задаёт `round` с единицы и обязательные поля. `frames` равен числу `interval`-строк; он строго положителен. `over25` — число интервалов строго `>25`. `p50/p95/p99` — nearest rank `ceil(n × fraction) − 1` после сортировки копии интервалов; delta — candidate p95 минус baseline p95 для каждого раунда. Median для чётного количества — нижний ранг. Сводка повторно проверяется из исходных runs/deltas; несовпадение, дубликат и пропуск — отказ, а не автоматическое исправление. Точная типизация: `nav-filter` и `card-filter` имеют `null` либо `s:<escaped>`; `s:` означает пустую строку, отсутствие столбца — ошибка. Остальные текстовые поля обязательны. Units-строка допускает только показанные литералы, так что N11 со `seconds` отвергается.

`s:` плюс буквальные Unicode scalar values образуют текст. `\\` означает один обратный слеш, `\t`, `\n`, `\r` — соответствующие управляющие символы; остальные U+0000–001F, U+007F–009F и U+2028/U+2029 записываются `\u{XXXX}` с **четырьмя прописными hex-цифрами**. U+0085 поэтому всегда `\u{0085}`. Остальные допустимые scalar values пишутся буквально в UTF-8 без нормализации. Одиночный UTF-16 surrogate и повреждённый UTF-8 отвергаются; replacement character не подставляется. Неизвестный, избыточный или иной вариант escape отвергается повторным каноническим сравнением. Так U+000A нельзя заменить на `\u{000A}` и скрыть неканонический вариант. Для чисел использовать конечный JS binary64 и `Number.prototype.toString()`, **кроме** `Object.is(value, -0) -> "-0"`; reader принимает лексему только если `Object.is(Number(token), parsed)` и повторная печать даёт в точности исходные ASCII байты. Это сохраняет 0/-0, длинные дроби и экстремальные P02; доменные поля интервалов дополнительно требуют `>0`. Нельзя округлять `toFixed` при сохранении.

Последняя строка ровно `end<TAB>sha256<TAB>...<LF>`; digest считается по всем байтам от начала заголовка до LF **перед** `end`, сам end в хеш не входит. Reader сначала применяет byte/row-пределы, затем проверяет UTF-8, структуру, canonical spellings, digest и семантику; нужен точный порядок ошибок лишь там, где независимые тесты его фиксируют. Digest обнаруживает случайное повреждение/усечение, **не** доказывает происхождение или подлинность. Отсутствующий end, второй end, extra data, испорченный digest и текст с повторно вычисленным digest, но неверной семантикой, все отвергаются. Output содержит один документ; в нём не допускается частичный успех после первого engine.

## Ресурсы, стоимость и безопасная публикация

N17 требует объявленных численных пределов; следующие значения — **проектные кандидаты, не утверждённые лимиты**. Заморозить их независимыми boundary/plus-one byte-cases до принтера и после замера полного P04, а не подобрать под его вывод: engines `1..3` (реальный available-map), rounds `1..1000`, runs `≤6000` суммарно, intervals `1..1000` на run и `≤120000` суммарно, канонически экранированный UTF-8 text-cell `≤4096` байт, line `≤16384` байт, полный файл `≤16 MiB`, число строк `≤150000`. Для P04 это даёт запас: rounds 2×, runs 6×, intervals 4×; байтовый/временной запас **не доказан**. `durationMs` сейчас не имеет верхней границы; если захват превысит предел интервалов, браузерный collector должен остановить этот run с ошибкой **до** публикации, не усечь его. Существенное сужение старого неограниченного `GLASS_ROLLOUT_ROUNDS`/duration из-за ресурсов описать в usage и регрессионных тестах как намеренное изменение контракта, не выдавать за полную совместимость. Пределы для других writers не наследуются автоматически.

До начала Playwright script проверяет настройки, непустой список *уникальных* engines и rounds; до накопления больших данных — верхние границы. На каждом событии collector проверяет предел, finite/positive interval и не фильтрует N19. После каждого engine закрывает его страницы/контекст/браузер даже при исключении, но файл ещё не публикует. Когда все engines готовы, валидатор заново проверяет полный result, кодек выдаёт один ограниченный `Uint8Array`, reader проверяет его обратно для acceptance, и физический writer пишет в случайно именованный temp **в той же директории** через `open(..., 'wx', 0o600)`, full write, `fsync`, close. Перед публикацией проверить байты temp readback против подготовленного buffer и digest. `link(temp, final)` публикует полностью записанный inode атомарно и без перезаписи существующего `web-matrix-scroll.measure`; затем temp удаляется и directory sync вызывается там, где поддержан. `rename` после отдельного `exists` не годится из-за гонки перезаписи. При неподдержанном hardlink — fail closed с ясной ошибкой, не писать сразу в final. Убой процесса во время temp-write оставляет только игнорируемый temp; сбой после link может оставить готовый final и temp, это не следует ложно объявлять отсутствием результата. Cleanup трогает только temp своего запуска. Ни старый `.json`, ни ранее опубликованный `.measure` не перезаписываются. По умолчанию final: `Plans/Kotlin/artifacts/glass-rollout/web-matrix-scroll.measure`; тесты и новые host-запуски задают отдельный временный `GLASS_ROLLOUT_OUT`.

N=10/100/1000 должен измерять **полный** schema validation + encode + decode/verify и действительную публикацию, с теми же семантическими требованиями и хотя бы чередующимися CPU-выборками на Node 20.19.0 и 22.12.0; отдельно startup, wall/CPU, allocation/peak RSS, число строк/байтов и стоимость ревью. Реальный browser Playwright измеряется отдельно и не подменяется синтетическим кодеком. Путь должен быть O(число строк + байты + суммарная сортировка интервалов); percentile сортировки дают O(k log k) на run, поэтому при фиксированном `intervals/run ≤1000` общая стоимость линейна по количеству runs. На N=1000 запас ≥2× к утверждённым лимитам по CPU/wall и логическим шагам подтверждается логом; провал — STOP и переработка или пересмотр плана с объяснением, **не** тихое поднятие лимита. Параллельное развитие Kit допустимо только отдельным проверяемым изменением пакета и повторной P8-пробой с чистой поставкой.
