## Why a numeric choice is still blocked

The executed old *common decoder* controls establish lower bounds, not maxima. A 10,000,000-byte progress input retains a 9,999,895-unit unknown string; another retains 32,768 ordered unknown maps, 65,545 preorder rows and a 9,617,777-unit padding string. A 616-byte input retains 256 nested arrays. A lossless projection of the first two requires respectively 10,000,112/10,196,726 A bytes and 40,000,022/39,214,145 C bytes by independent arithmetic, including digest. Thus any proposed common string/row/depth caps must exceed the relevant observed tree measure, and A/C physical caps must at least admit those examples. These figures are **minimum floors**, not recommended ceilings: no P23 memory or 2× time/step headroom has been measured, and a 10 MB old input can contain other shapes.

The earlier statement that Android progress import rejects 10,000,001 bytes *before writing* conflates entrypoints. `AndroidSessionViewModel.importFrom` reads the selected file through `readUtf8Limited` (10 MB) before `AndroidProgressRepository.importJson`; the repository's direct method decodes then writes, and applies the 10 MB `readUtf8Limited` only during readback. A direct plus-one call may therefore alter the primary file before returning `Failed`. No direct Android host experiment has run. Desktop `Main.kt` has a 10 MB file-picker limit for progress/vocabulary, while `DesktopProgressRepository.importJson` itself has no byte check; desktop preferences use 10 MB. iOS/macOS progress imports have explicit 10 MB checks, and iOS/macOS preferences imports 1 MB checks. Browser React/KMP progress and KMP web preferences have no fixed byte limit in source; actual origin quota and browser behavior constrain storage. The old *decoder* accepting a case does not prove that a named host imported, persisted and read it back.

There is also a semantic representability gate. `ProgressCodec.decode` retains an unknown `JsonObject`/`JsonPrimitive`; the proposed `WireTree` admits signed i64 and finite binary64 bits, but not every possible old JSON numeric token spelling/value. Do not coerce, round, normalize, or drop unknown data to fit A/C. Before claiming equal admission, determine whether old readers and actual hosts accept unknown `1e10000`, a wider-than-i64 integer, `1.0` versus `1e0`, negative zero, a very long unknown key, and escaped lone surrogates; inspect exact retained code units/token semantics and persistence readback. If an accepted value is outside `WireTree`, stop for a separately reviewed typed-model extension or a documented recovery decision that preserves original bytes. A silently lossy projection is forbidden by P5/P7/P14/P15/P24.

## Contract and ownership

The generic wire codec owns only bounded framing, exact UTF-8/UTF-16 conversion, ordered typed tree, canonical bytes and digest. Document owners own known-field schema, old-source projection, unknown-value policy and new-document admission. Host repositories own input gating, quota, backup, atomic write, readback, receipts and recovery. A test-only oracle owns independent expected trees/bytes. The codec must not infer a 10 MB generic output cap from a 10 MB legacy **input** cap; A and C may have distinct physical ceilings while admitting the same semantic trees. No new application JSON output is authorized. Historical old-host admission probes may execute the *old* importer only in throwaway isolated storage, inspect its temporary legacy bytes, and destroy that storage; those old writers must never be carried into the new application. The new one-time migration reads existing legacy bytes only.

An absolute finite generic document ceiling cannot be justified solely by observing examples on a source path with no fixed admission bound. For browser stores and direct desktop/Android entrypoints, first identify the actual supported path and contract. Either prove an upper envelope from source policy plus executed host behavior, or have the document/host owner define a separately reviewed compatibility decision, including preservation of old bytes and recovery. Do not call an arbitrary sample maximum “all accepted legacy.” If a fixed-size single-frame A/C cannot preserve an accepted old document under the agreed contract, leave NJ05 open; changing the schema or using a segmented/streaming representation needs its own design and corpus revision.

## Independent experiments, in order

1. **Lock the old inputs actually executed.** Extend `kotlin/shared/src/commonTest/kotlin/polski/textwire/LegacyBoundaryAdmissionTest.kt` and the macOS host test with a test-only generated constant/table sourced from the *single* readable `tests/fixtures/textwire/{legacy-boundary,numeric-admission}.cases` ledger. On each executed KMP target, hash the exact `raw.encodeToByteArray()` constructed by the test and compare it with the ledger SHA-256 before invoking the old reader; assert byte length too. A build-time embed may make these text ledger values available to browser/Native commonTest, provided an independent freshness check fails when ledger or recipe changes. Do not maintain a second handwritten Kotlin hash list, emit a JSON file, or use the candidate codec as oracle. Add mutation controls: one input byte change and one ledger hash change each fail freshness. Keep any test-only legacy inputs out of the shipped app.
2. **Separate entrypoints and persist/readback results.** For progress, vocabulary and preferences, create one host matrix with columns `common decode`, `UI/file-picker admission`, `repository/direct admission`, `backup/write`, `primary readback`, and `old bytes after failure`. Exercise valid `limit−1`, `limit`, and `limit+1` inputs on each path that claims a limit, using exact input hashes and isolated stores. For Android, specifically call `AndroidProgressRepository.importJson` directly with 10,000,001 bytes and a pre-existing sentinel file: report whether return value is `Failed`, whether the sentinel survives, and whether the oversized file is left behind. Also run the UI stream gate; the two results are distinct. For desktop, run both `Main.kt` picker boundary and direct repository boundary; for iOS/macOS, run actual import and storage readback at the limit, not just a decoder. For web, execute React and KMP browser storage paths in a real browser at the supported origin/quota, capturing existing-entry preservation on `QuotaExceededError`; do not generalize one browser's quota as a portable byte limit. Reuse exact-path/byte-hash old-user test inputs, not new JSON output snapshots.
3. **Characterize old semantic admission.** On each named target, verify the 256-deep and 65,545-row controls through the *host* path at exact old input ceiling where applicable, then read back and inspect every retained ordinal and string/code unit. Add independent sparse-map, many-small-keys, near-limit key, escaped controls/surrogate, arbitrary-number-token and valid domain-heavy vocabulary cases; distinguish parse rejection, domain rejection, host size rejection, storage failure and runtime stack/OOM. Keep near/exact/plus-one independent of A/C. The common decoder's 256 depth is a floor; determine a safe upper envelope by actual policy or a rigorous byte-budget bound, not by assuming that the next tested depth fails everywhere. Vocabulary's ignored unknown `padding` proves parser admission only; verify whether its exact preservation is a product requirement before using it as a lossless tree control. Preferences whitespace inflation has no retained semantic tree growth; use it for host admission, not a 1 MB wire lower bound.
4. **Define a pure projection and arithmetic oracle.** A separate test author writes a typed ordered-tree projection for each accepted retained legacy shape, including unknown keys, source order, exact UTF-16 units, null/absence and numeric meaning/lexeme policy. If any accepted shape is not representable, record the precise counterexample and stop. Without calling an encoder, calculate A/C header, each preorder row, escape/unit expansion, digest and final LF for the worst observed variants. Include keys as well as values, numeric and nested-node overhead, and separately distinguish legacy bytes, decoded heap, projected tree, encoded bytes and backup/temporary storage. For candidate semantic depth, define root depth and scalar depth explicitly to prevent an off-by-one N26 oracle.
5. **Measure host headroom before proposing numbers.** For the same accepted trees and N=10/100/1000 generated records, record per target cold/warm parse, projection, encode, decode, readback time, peak retained/temporary memory (or target-appropriate allocation proxy), logical steps, output bytes and storage quota. Alternate A/C order. Profile largest accepted trees on desktop JVM, Android actual emulator/device, JS browser, Wasm browser, iOS simulator and macOS Native; report selected/executed/skipped, build/runtime version, device memory and failure mode. Use P23's at least 2× scalable-step/time headroom, not just a successful single run. If 40 MB C plus backup/digest/readback cannot fit a required host, reject C or revise the representation under independent review; do not shrink the accepted old tree.
6. **Only then freeze N26.** Document owners set one common numeric depth, row and UTF-16 string-unit ceiling, plus A- and C-specific total-byte ceilings and their reason. For each dimension freeze exact-at and `+1` valid-tree byte recipes with SHA-256 and expected `Bound`, keeping every other limit satisfied; for physical cap include header/digest/final LF. If grammar cannot reach exactly `cap+1`, use and justify the smallest valid stream above cap. Verify preflight before UTF-8 decode/allocation, incremental row/depth/string limits, bounded memory, and no partial host write. Re-run full independent A/C corpus review after any new bounds; keep B NO-GO. A/C codec implementation is allowed only after this review, then actual cross-target generic tests and P8 equal-guarantee comparison follow.

The architect's current verdict is **no defensible numeric candidate**. Any depth cap below the retained 256 nested arrays, row cap below 65,545, string-unit cap below 9,999,895, A total-byte cap below 10,196,726, or C total-byte cap below 40,000,022 already fails a known decoder-accepted progress control; exact depth counting and host persistence still need proof. Raising these floors without measured headroom also does not make a safe ceiling. N26, A/C codec development, new host saves and all-target NJ05 acceptance remain **NOT FROZEN / NOT RUN** until the steps above are complete. Report failures, skips and recovery states explicitly; never substitute linked or compiled tests for execution (P17).
