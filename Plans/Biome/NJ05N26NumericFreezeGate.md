## Why a numeric choice is still blocked

The executed old *common decoder* controls establish lower bounds, not maxima. A 10,000,000-byte progress input retains a 9,999,895-unit unknown string; another retains 32,768 ordered unknown maps, 65,545 preorder rows and a 9,617,777-unit padding string. A 616-byte input retains 256 nested arrays. A lossless projection of the first two requires respectively 10,000,112/10,196,726 A bytes and 40,000,022/39,214,145 C bytes by independent arithmetic, including digest. Thus any proposed common string/row/depth caps must exceed the relevant observed tree measure, and A/C physical caps must at least admit those examples. These figures are **minimum floors**, not recommended ceilings: no P23 memory or 2× time/step headroom has been measured, and a 10 MB old input can contain other shapes.

The earlier statement that Android progress import rejects 10,000,001 bytes *before writing* conflates entrypoints. `AndroidSessionViewModel.importFrom` reads the selected file through `readUtf8Limited` (10 MB) before `AndroidProgressRepository.importJson`; the repository's direct method decodes then writes, and applies the 10 MB `readUtf8Limited` only during readback. A direct plus-one call may therefore alter the primary file before returning `Failed`. No direct Android host experiment has run. Desktop `Main.kt` has a 10 MB file-picker limit for progress/vocabulary, while `DesktopProgressRepository.importJson` itself has no byte check; desktop preferences use 10 MB. iOS/macOS progress imports have explicit 10 MB checks, and iOS/macOS preferences imports 1 MB checks. Browser React/KMP progress and KMP web preferences have no fixed byte limit in source; actual origin quota and browser behavior constrain storage. The old *decoder* accepting a case does not prove that a named host imported, persisted and read it back.

There is also a semantic representability gate. `ProgressCodec.decode` retains an unknown `JsonObject`/`JsonPrimitive`; the proposed `WireTree` admits signed i64 and finite binary64 bits, but not every possible old JSON numeric token spelling/value. Do not coerce, round, normalize, or drop unknown data to fit A/C. Before claiming equal admission, determine whether old readers and actual hosts accept unknown `1e10000`, a wider-than-i64 integer, `1.0` versus `1e0`, negative zero, a very long unknown key, and escaped lone surrogates; inspect exact retained code units/token semantics and read-only host load against unchanged injected sealed bytes. Historical persistence receipts are cited only at their own SHA; new-text persistence needs a later test. If an accepted value is outside `WireTree`, stop for a separately reviewed typed-model extension or a documented recovery decision that preserves original bytes. A silently lossy projection is forbidden by P5/P7/P14/P15/P24.

## Contract and ownership

The generic wire codec owns only bounded framing, exact UTF-8/UTF-16 conversion, ordered typed tree, canonical bytes and digest. Document owners own known-field schema, old-source projection, unknown-value policy and new-document admission. Host repositories own input gating, quota, backup, atomic write, readback, receipts and recovery in a later **new-text** slice. A test-only oracle owns independent expected trees/bytes. The codec must not infer a 10 MB generic output cap from a 10 MB legacy **input** cap; A and C may have distinct physical ceilings while admitting the same semantic trees. No new application JSON output is authorized. New admission tests may inject already sealed old bytes into a fresh isolated store and call only read-only decode/load/peek; they must not invoke old importers, JSON writers, saves, exports or backups. Historical old-host write receipts remain bounded to their recorded SHA. The new one-time migration reads existing legacy bytes only.

An absolute finite generic document ceiling cannot be justified solely by observing examples on a source path with no fixed admission bound. For browser stores and direct desktop/Android entrypoints, first identify the actual supported path and contract. Either prove an upper envelope from source policy plus executed host behavior, or have the document/host owner define a separately reviewed compatibility decision, including preservation of old bytes and recovery. Do not call an arbitrary sample maximum “all accepted legacy.” If a fixed-size single-frame A/C cannot preserve an accepted old document under the agreed contract, leave NJ05 open; changing the schema or using a segmented/streaming representation needs its own design and corpus revision.

## Independent experiments, in order

1. **Lock the old inputs for read-only tests.** Add a new focused commonTest class instead of extending `LegacyBoundaryAdmissionTest` or the macOS host admission class, because their whole-class runs include old `importJson`/write calls. Use the test-only generated constant/table sourced from the sealed `tests/fixtures/textwire/{legacy-boundary,numeric-admission}.cases` ledgers. On each executed KMP target, hash the exact `raw.encodeToByteArray()` constructed as input by the test and compare it with the ledger SHA-256 before invoking only an old *decoder*; assert byte length too. A build-time embed may make these text ledger values available to browser/Native commonTest, provided an independent freshness check fails when ledger or recipe changes. Do not maintain a second handwritten Kotlin hash list, emit a JSON file, or use the candidate codec as oracle. Add mutation controls: one input byte change and one ledger hash change each fail freshness. Keep test-only legacy inputs out of the shipped app.
2. **Separate read-only entrypoints from historical write paths.** For progress, vocabulary and preferences, create one host matrix with columns `common decode`, `read-only byte/picker preflight`, `host load/peek of injected sealed bytes`, `old-byte hash before/after`, and `old import/write behavior at historical SHA or NOT RUN`. Exercise `limit−1`, `limit`, and `limit+1` only through actual read-only gates using exact input hashes and fresh isolated stores. For Android, call `readUtf8Limited` on the sealed input and `AndroidProgressRepository.load` after fixture injection; do **not** call `AndroidSessionViewModel.importFrom` or `AndroidProgressRepository.importJson`. Source review identifies the direct import's possible 10,000,001-byte write-before-readback hazard, but its effect on the new SHA is NOT RUN. For Desktop, distinguish read-only repository load from the `Main.kt` picker callback and direct importer, both NOT RUN here. iOS/macOS read-only loads are distinct from their old imports. Preferences wrappers on web, Android and Desktop may save JSON if the primary document is absent: seed the sealed primary byte input first, audit the selected branch, or use only a raw getter and `UserPreferencesCodec.decode/peekTargetNative`; Apple snapshot builders are excluded. Web read-only load at a fresh origin does not prove quota, `QuotaExceededError` handling or old-tab safety. Reuse exact-path/byte-hash old-user test inputs, not new JSON output snapshots; future write/readback acceptance uses only new text and must preserve the sealed original.
3. **Characterize read-only semantic admission.** On each named target, verify the 256-deep and 65,545-row controls through a pure decoder or read-only host load where available, then inspect every retained ordinal and string/code unit while checking the injected old bytes are unchanged. Add independently sealed sparse-map, many-small-keys, near-limit key, escaped controls/surrogate, arbitrary-number-token and valid domain-heavy vocabulary inputs; distinguish parse rejection, domain rejection, read-size rejection and runtime stack/OOM. Do not infer import/persistence acceptance from load/peek; that write path remains historical or NOT RUN on this SHA. Keep near/exact/plus-one independent of A/C. The common decoder's 256 depth is a floor; determine a safe upper envelope by actual policy or a rigorous byte-budget bound, not by assuming that the next tested depth fails everywhere. Vocabulary's ignored unknown `padding` proves parser admission only; verify whether its exact preservation is a product requirement before using it as a lossless tree control. Preferences whitespace inflation has no retained semantic tree growth; use it for read admission, not a 1 MB wire lower bound.
4. **Define a pure projection and arithmetic oracle.** A separate test author writes a typed ordered-tree projection for each accepted retained legacy shape, including unknown keys, source order, exact UTF-16 units, null/absence and numeric meaning/lexeme policy. If any accepted shape is not representable, record the precise counterexample and stop. Without calling an encoder, calculate A/C header, each preorder row, escape/unit expansion, digest and final LF for the worst observed variants. Include keys as well as values, numeric and nested-node overhead, and separately distinguish legacy bytes, decoded heap, projected tree, encoded bytes and backup/temporary storage. For candidate semantic depth, define root depth and scalar depth explicitly to prevent an off-by-one N26 oracle.
5. **Run a narrow prerelease feasibility prototype, then measure provisional headroom.** After steps 1–4 have independently frozen old inputs, typed trees and A/C byte arithmetic, an isolated developer may implement *test-only* A/C encode/decode prototypes solely to estimate allocation, steps and runtime on those fixed inputs. The prototypes must not supply or rewrite expected bytes, set N26 limits, write user storage, enter production source sets, or count as a passing codec. Compare small outputs with already frozen positive bytes and large output *lengths* with independent arithmetic; report mismatches as prototype failures. For the same accepted trees and N=10/100/1000 generated records, record per target cold/warm parse, projection, prototype encode/decode, in-memory readback simulation, peak retained/temporary memory (or target-appropriate allocation proxy), logical steps and output bytes. Record source-defined host quotas separately; actual storage write/quota behavior belongs to later new-text acceptance. Alternate A/C order. Execute the largest accepted trees where possible on desktop JVM, Android actual emulator/device, JS browser, Wasm browser, iOS simulator and macOS Native; report selected/executed/skipped, build/runtime version, device memory and failure mode. This is **provisional feasibility**, not final P23: estimate whether at least 2× scalable-step/time headroom is plausible, but do not claim it from one run or a prototype. If 40 MB C plus backup/digest/readback cannot fit a required host, reject C or revise the representation under independent review; do not shrink the old tree.
6. **Independently freeze N26 after the feasibility evidence.** Document owners set one common numeric depth, row and UTF-16 string-unit ceiling, plus A- and C-specific total-byte ceilings and their reason. The independent test author, without calling the prototype, freezes exact-at and `+1` valid-tree byte recipes with SHA-256 and expected `Bound` for each dimension, keeping every other limit satisfied; for physical cap include header/digest/final LF. If grammar cannot reach exactly `cap+1`, use and justify the smallest valid stream above cap. The reviewer checks the numeric choice, byte recipes and old-host admission against the independent source; re-run full independent A/C corpus review after new bounds and keep B NO-GO. Prototype output is never the acceptance oracle.
7. **Implement and verify the production codec only after N26 review.** The developer may then place A/C codecs in production source sets. Execute frozen exact-at/plus-one cases, preflight before UTF-8 decode/allocation, incremental row/depth/string bounds, digest/canonical readback and no partial host write. Repeat step 5 on the final production implementation and actual host adapters: cross-target generic tests plus P23 N=10/100/1000 time, logical steps and allocation/peak-memory evidence with at least 2× headroom, and P8 equal-guarantee cost comparison. A favorable prototype result never substitutes for these final runs or host acceptance.

## Concrete handoff and exit gate

The independent tester starts from the existing sealed `tests/fixtures/textwire/{legacy-boundary,numeric-admission}.cases`; any missing input needs a separate exact-path, SHA-256-sealed input-only requirement fixture. The new focused common/Android/Desktop/iOS/macOS/browser classes exercise only pure decoders, byte readers or load/peek after sealed fixture injection, never an old importer/writer. Do not extend or rerun the whole existing `LegacyBoundaryAdmissionTest` or `LegacyHostSizeAdmissionTest` class for this slice: they include old `importJson`/write calls. A build-generated commonTest text-ledger embed is permitted only if a freshness check proves it derives from sealed files; keep generated test material outside app artifacts. The eventual N26 amendment updates `tests/fixtures/textwire/negative.cases` and `corpus.sha256` only after independent requirements review; `positive.cases` and old test hashes do not change to satisfy a codec. The source entrypoints above must be cited with revision and exact lines in the tester handoff. Android actual-device execution needs a discovered test task or instrumented host test; Robolectric and an empty `androidConnectedCheck` do not count as device execution. Available local tooling includes Android AVD definitions and an iOS 26.1 simulator, but availability is not execution.

The architect's current verdict is **no defensible numeric candidate**. Any depth cap below the retained 256 nested arrays, row cap below 65,545, string-unit cap below 9,999,895, A total-byte cap below 10,196,726, or C total-byte cap below 40,000,022 already fails a known decoder-accepted progress control; exact depth counting and host persistence still need proof. Raising these floors without measured headroom also does not make a safe ceiling. N26, production A/C codec development, new host saves and all-target NJ05 acceptance remain **NOT FROZEN / NOT RUN** until their respective gates above are complete; the isolated test-only prototype is permitted only after independent input/arithmetic freeze and never proves N26 or product readiness. Report failures, skips and recovery states explicitly; never substitute linked or compiled tests for execution (P17).
