# NJ05 N17: проверка дублированных ключей старого прогресса

Статус: **архитектурный handoff; Kotlin preflight, тесты и хостовые запуски NOT RUN**. Основа — `biome/full-port-2026@0283d83d5ef77a106e9cb1da3870d1513bf259ca`. Область — только одноразовое чтение старого пользовательского прогресса. Этот шаг не выбирает A/C, не вводит продуктовый JSON, не меняет запечатанные E2/E3 файлы, не разрешает старый writer, backup, import, save, export или новую миграционную транзакцию. Соседние E3/N14/N16/N26 и NJ06 остаются открытыми.

## Основание и владельцы

- [E3 oracle](NJ05E3IndependentOracleFreeze.md) запечатал 674-байтовый **input-only** [legacy-duplicate-key-progress.input](../../tests/fixtures/textwire/inputs/legacy-duplicate-key-progress.input): SHA-256 `8cc8e3335dce5e58c242b8dc9fbcd30fac2d156f03f534aa4ef79e207515be12`. Внутри `unknown` два ключа `wide`: кавычки занимают нулевые полуоткрытые интервалы UTF-16 `[103,109)` и `[112,118)`; байтовые позиции совпадают именно у этого ASCII-префикса. Python `object_pairs_hook` обнаруживает дубль; обычное отображение объекта оставляет последнее значение. Весь файл содержит также не-ASCII и должен оставаться неизменным.
- `ProgressCodec.decode` в `kotlin/shared/src/commonMain/kotlin/polski/progress/ProgressCodec.kt` первым делом вызывает `Json.parseToJsonElement(raw)` и получает `JsonObject`. `ProgressDocument.source` сохраняет полученное дерево, но после отображения уже не содержит оба вхождения одинакового ключа. `encodeLegacyV1` — действующий старый JSON writer, **не** инструмент N17. Тестовый `RetainedNumberProbe` находится только в `commonTest`; он не исправляет потерю ключа.
- `RawProgressRepository.migrateLegacy` в `.../progress/ProgressRepository.kt` сейчас пишет `BACKUP_KEY` до `ProgressCodec.decode(legacy)`; новая N17 граница должна предшествовать **любому** `put` на конкретном старом входе. `load()` при наличии только `LEGACY_KEY` возвращает сырой `LegacyAvailable`, не декодируя его; `save()` уже блокирует запись в этом состоянии. Старые `PREVIEW_KEY`, `BACKUP_KEY`, `MARKER_KEY` и JSON readback — переходный код, а не целевая транзакция без JSON.
- `WebProgressRepository` делегирует `RawProgressRepository`; Desktop/Android/iOS/macOS имеют `loadUnlocked()` с `ProgressCodec.decode`, отдельные текущие импорты/записи и свои старые пути. Новая общая проверка принадлежит чистому `commonMain` legacy-reader; файлы, `localStorage`, `NSUserDefaults`, лимит чтения, транзакция и восстановление принадлежат хостам/репозиториям. Нельзя переносить физическое состояние или запись в предикат/DSL.

## Контракт узкого компонента

**NEW** `kotlin/shared/src/commonMain/kotlin/polski/progress/LegacyObjectKeyPreflight.kt`: внутренний, синхронный, чистый `inspect(raw: String)` возвращает `Unique`, `Duplicate(pathSegments, firstKeySpanUtf16, secondKeySpanUtf16)` либо `UnsafeInput(reason, positionUtf16)`. Интервалы включают кавычки; индексы нулевые, по кодовым единицам Kotlin `String`. `pathSegments` — последовательность уже декодированных имён и индексов списков, без неоднозначного соединения через точку. Диагностика и список ключей не становятся частью сохраняемой модели. `Unique` означает только «сканер не обнаружил дубликатов и безопасно прошёл структуру», **не** успех доменного парсинга, версии или форматного admission. При `Duplicate`/`UnsafeInput` исходная строка остаётся нетронутой; в будущем read-only migration admission переводит их в `RecoveryRequired(raw, reason)` до эффектов. Чтение физического байтового файла обязано отвергнуть некорректный UTF-8 до создания `String`; при таком отказе host сохраняет исходный файл побайтно, а recovery API не должен выдавать придуманную строковую замену. Web `localStorage` уже выдаёт UTF-16 строку, где проверяются кодовые единицы без нормализации. Не сравнивать повторно UTF-8 кодирование строки с исходными файловыми байтами как доказательство их идентичности, если host decoder мог заменить ошибочные байты.

Один проход со стеком состояний объекта/массива, курсором по UTF-16 и отдельным набором **декодированных ключей в каждом объекте**. Для каждого ключа декодировать JSON string escapes (`\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX`) в точные UTF-16 code units; `"a"` и `"\u0061"` равны, `"\uD83D\uDE00"` и буквальный 😀 равны, два отдельных literal/escaped lone surrogate равны там, где старый reader их допускает. Не применять NFC, case-fold или locale. Не принимать ложные ключи внутри строковых значений; не путать одинаковые имена в разных объектах. Сканер проверяет расположение `:`, `,`, `{}`, `[]`, строк, литералов и токена числа ровно настолько, чтобы безопасно находить границы ключей; окончательное признание корректности и версии оставлено существующему старому декодеру. При неясной или неподдерживаемой последовательности — `UnsafeInput`/recovery, никогда `Unique` после пропуска байтов. Любое отклонение ранее принятого старым reader входа требует независимой классификации и исправления scanner либо явного отдельного требования, а не тихого сужения допуска. Порядок и первое/второе место дубликата определяются слева направо.

Реализация не должна рекурсивно обходить потенциально глубокий чужой документ, создавать второе `JsonObject`-дерево или копировать большие scalar values. Для активного объекта память ограничена его уникальными ключами, а стек — глубиной; закрытый объект освобождает набор ключей. Ожидаемое время линейно по числу кодовых единиц плюс хеширование ключей. Действующие допустимые входы 9 999 999 / 10 000 000 / 10 000 001 байт нельзя произвольно отклонить новым лимитом. Верхняя граница глубины, памяти, времени и отдельные хостовые пределы требуют N26/P23; истощение ресурсов должно стать recoverable отказом до записи, не причиной пропуска проверки. Как минимум измерить двойную стоимость полного прохода + старого parser на E2 и большом принятом входе.

Сначала проверить **в установленном `kotlinx-serialization-json 1.11.0`** существующий доступный потоковый/event API, который выдаёт каждое имя до map-collapsing. Если он действительно доступен на всех KMP targets и даёт сырые/декодированные ключи с позициями, использовать его вместо своего lexer. Обычный `JsonObject` и последующая проверка его `.keys` принципиально не годятся. Если событийного API с теми же гарантиями нет, маленький внутренний сканер выше — механическая Kotlin утилита (P4/P7/P22), а не новый синтаксис Biome: предметного правила здесь нет. Двойной parser допустим только после замера P23 и равных границ отказа. Не создавать общий «JSON framework» для иных документов без доказанной повторяемости.

## Где применять и как отказывать

1. **Сначала read-only admission.** На одноразовом пути с `LEGACY_KEY`/старым файлом/старым импортным входом запустить preflight до `ProgressCodec.decode`, проекции E3, создания нового текста и любого backup/preview/receipt/cleanup. Запрещённый дубль возвращает `RecoveryRequired` с тем же сырым старым значением и диапазонами; ни один writer не вызывается. Если текущий API хоста возвращает лишь `LoadResult.Invalid` или строку ошибки импорта, адаптировать только границу будущей миграции, сохранив смысл «требуется восстановление» и неизменность физического входа; не выдавать `Loaded` и не совершать импорт. Для `RawProgressRepository.migrateLegacy` текущий порядок backup-before-decode необходимо изменить при интеграции N17, иначе негатив не доказывает no-write.
2. **Затем старый parser и домен.** `Unique` передаёт тот же `raw` старому `ProgressCodec.decode`; `Invalid`/`Unsupported` тоже переходят в recovery на миграционной границе. Для accepted E2 прогресса проверить дерево неизвестных значений и E3 retained-number spelling/order без нормализации. Никакой `ProgressDocument.source: JsonObject` не должен попасть в обычную новую save API после переноса.
3. **Новый storage — другой этап.** Старые исходные байты/ключи остаются до успешной новой text-readback + durable receipt и отдельно проверенного удаления. Никакая ошибка preflight, парсинга, I/O или отмена не меняет старый вход. Уже существующие старые JSON preview/backup и host imports — исторический переходный код; N17 не запускает их ради теста. Для web проверять отсутствие любых дополнительных ключей; для файлов — имя, байты и отсутствие temp/backup; для `NSUserDefaults` — полный набор ключей. `RecoveryRequired` блокирует save/reset до явного восстановления, как в `TrainingStore`.
