## Scope, consumers and non-negotiable compatibility

The port must preserve the complete active Kotlin product and its shipped browser, Android, iPhone/iPad, native macOS SwiftUI, and retained Compose Desktop preview. The existing React baseline and root tests remain until a separately authorized cutover. Preserve `pl-ru` and `en-ru` packs, all currently available training and vocabulary flows, matrix/reference screens, styles/lifehacks, preferences, animation and reduced-motion behavior, import/export/recovery, and exact accepted Polish/English/Russian content. Preserve public Kotlin call sites and Swift bridges unless a measured seam needs a compatible adapter. Preserve skill/pack IDs, progress keys, serialized field names/defaults, FSRS states and timestamps, unknown/legacy document behavior, existing backup and migration safety. No destructive rewrite of user data or automatic migration.

Actual entrypoints and owners at this revision: `kotlin/core-model` holds shared feature and construction types; `kotlin/core-engine/src/commonMain/kotlin/polski/core/engine/{ConstructionRealizer,ExerciseGenerator,MatrixTableEngine}.kt` implements realization/generation/matrix logic; `kotlin/pack-format` and `kotlin/shared/src/commonMain/kotlin/polski/data/CoursePackLoader.kt` load packs. `kotlin/shared/src/commonMain/kotlin/polski/{core/PlEngine.kt,training/AnswerEvaluator.kt,training/SkillQueue.kt,srs/FsrsScheduler.kt,progress/ReviewReducer.kt,progress/ProgressCodec.kt,vocabulary/VocabularyDocument.kt,presentation/TrainingStore.kt,presentation/StyleComposer.kt}` serve actual consumers. `TrainingStore.start/dispatch/close` is the sole session owner; `ReviewReducer.recordReview` owns one review transition; `FsrsScheduler.review` owns FSRS calculations. Web entrypoints are `kotlin/composeApp/src/{jsMain,wasmJsMain}/kotlin/polski/main.kt`; Android is `kotlin/androidApp` with `kotlin/composeApp/src/androidMain`; native Apple apps are `kotlin/iosApp` and `kotlin/macosApp`, fed by `kotlin/shared/src/{iosMain,macosMain}` bridges. Compose Desktop lives in `kotlin/composeApp/src/desktopMain`. The browser retains both JS and Wasm branches. `courses/` and `tests/` are product inputs and independent tests, not generated truth.

## Sequential implementation and proof stages

The numbered stages below are historical design context, **not executable instructions** for the no-JSON migration. In particular, Stage 1 `.inputs.json` and Stage 2 `.tables`/generated JSON routes are superseded by the NJ plan and must not be restarted. The FP behavior and independent proof obligations remain.

Each stage is a reviewable slice. The Developer records actual RED before changes and GREEN after, including current source hash, command, cwd, target, case IDs, counts and skips. A failing test written after implementation is not reported as observed RED. Tester independently checks the acceptance matrix and may add test-only fixtures; Reviewer assesses final diff against biome `AI/PRINCIPLES.md`, naming violated P-number, file, trigger and observable consequence. Architecture returns only for contract changes. Stage completion requires no unclassified semantic differential or unresolved Critical/Major finding.

0. **Freeze baseline and quantify scope.** Inventory every production subsystem, course pack, Gradle/Xcode/browser target, current tests and expected fixture provenance. Record product and compiler SHAs, branch/worktree, supported toolchain, active feature flags and a read-only export fixture without personal data. Run the current baseline product tests/builds and available host smoke tests, recording PASS/FAIL/NOT RUN by case and device. Freeze accepted expectations; log known React/Kotlin differences and existing failing checks. Write the first maintainability baseline and native helper control before adding DSL.
1. **Prove project contract and one vertical slice.** Select one high-value pure decision currently consumed by real TS and Kotlin code (session rating/review classification is the initial candidate; inspect actual call paths before freezing). Create independent `.examples` and negative boundary rows, observe RED for the proposed missing DSL integration, then add the smallest line contract/Logic/project recipe. Generate read plans and a Kotlin target via real biome CLI; compile and execute the product consumer, test a deliberate stale fact/binding and stale artifact, and compare same outcomes with a small native helper. Establish actual Gradle generated-source wiring and source-of-truth rules. No mass transfer until this slice passes both function and cost criteria.
2. **Grammar and exercise content.** Start with a measured one-skill `.tables` fixture or the 16-row English curriculum as an authored-source pilot; existing `biome generate --authored [--check]` can emit the JSON interface consumed by current loaders. The current DECLARE reader does not establish a Kotlin multilingual course runtime, and a giant nested `SET` would merely move JSON syntax. Move stable declarations/recipes only after proving loaders accept generated or retained pack artifacts byte/semantically and all forms/IDs survive. Port decision rules by groups using existing Logic/DECLARE/TEMPLATE only where their actual compiler capability and native-helper comparison justify them; keep table traversal native if it is general mechanics. Observe RED on controlled variant/unknown-form and chain-boundary cases, GREEN on every skill and 12×5 corpus across real consumers. Do not duplicate the live `course.json` with separately authored v2 layers or add grammar syntax without shared Core conformance.
3. **Evaluation, queue, FSRS, progress, vocabulary.** Separate pure verdicts from reducers, codecs and stores. Keep accepted Unicode and FSRS numerical behavior under deterministic fixtures. Observe RED on stale/duplicate rating, typed-correct conflict, timezone/day boundary, invalid import and write-failure cases, then GREEN on TS/Kotlin product paths. Preserve backups and old keys; validate round trips and failed migration recovery before any migration is used in a live host.
4. **Session and platform integration.** Connect only proven generated policies to existing `TrainingStore` and host bridges. Preserve native screen implementations and host-specific gesture thresholds. Execute browser JS/Wasm, Android, iPhone/iPad and macOS app paths separately; include keyboard, IME, accessibility, reduced motion, file dialogs, lifecycle and failed persistence. A framework build, common test, emulator, simulator and physical device each gets its own evidence row. Do not rewrite command/snapshot wire by default: prior measured NO-GO remains the control.
5. **Regression, independent review and cost decision.** Run full product regression and compiler gates on the final unchanged revision, fill every FP row, perform independent Tester/Reviewer handoffs, and write **NEW** `Plans/Biome/FullPortMaintainability.md`. Recheck any corrected failed cases, then affected gates. Complete only if all required behavior and measurement criteria pass. Merge, deployment, publication and React removal are separate decisions.

## Separate maintainability and cost report design

`FullPortMaintainability.md` must compare the accepted DSL implementation with a **good** native TypeScript/Kotlin helper approach that uses the same product contract, typed inputs, generated or equally guarded adapters, independent expected cases, host coverage and regression protection. Do not compare against unrefactored legacy code or strip tests/guards from the control. Measure the vertical slice before scaling, then at least three representative changes: (a) change a grading or queue threshold/priority without changing an expectation; (b) add one grammar/exercise variant and its independently specified result; (c) add or change a pack fact while preserving old progress; optionally a real lifecycle change. Reset each arm to the same baseline, perform the same requirement, run the same gates, and record where one-sided edit mutants are detected. Separate a requirement change from a refactor in the ledger.

For each arm and scenario record authored DSL/native lines and files, generated lines/files separately, number of independent semantic edit sites, duplicated facts, concepts introduced, touched consumers and review locations, code-review defects, compile/generation cold and warm time, product startup time, steady runtime CPU/wall and allocations where instrumented, and logical steps. Record commands, versions, SHAs, warmup/sample count, machine and raw outputs. Use actual real printers/emitters/hosts for N=10/100/1000 growth and P23 headroom; do not raise limits or alter counters to pass. Record LLM usage only from actual provider logs, with compile/startup/runtime/review costs in separate columns; static token counts are source size, never usage. State unknowns as NOT MEASURED. A DSL win requires fewer independent rule/edit sites or a demonstrable guarantee while preserving equal behavior, and no unacceptable compile/runtime/review regression; lines alone cannot decide. If the native helper has the same guarantees at lower cost, keep it and report that subsystem as an intentional native boundary. Report product-level aggregate only after all subsystems are counted, including generated bindings and native remainder.

## Stop rules and handoff

Stop a slice before expanding when a claimed backend cannot compile **and execute** the decision in its required consumer; a project contract/read plan cannot describe the needed facts without duplicate manual bindings; expectations derive from generated output; a legacy document or pack round trip loses data; a predicate gains mutation; lifecycle cleanup/cancellation regresses; UTF-16/Unicode, day-boundary or FSRS differentials remain unexplained; test coverage is empty/skipped/stale; generated files are hand-patched; limits/gates are weakened; or the native control wins equal-guarantee upkeep. Record the finding, owner and smallest shared Core or product-boundary correction. `PORTABLE-STATIC` can be noted as compiler capability evidence but cannot close product runtime acceptance. An unsupported Swift backend does not authorize speculative compiler work; retain SwiftUI/native wire and prove Kotlin bridge behavior.

Developer handoff: use this plan and frozen FP ledger to produce a stage-1 blueprint with actual symbol signatures, contract facts, generated output paths and target tasks, then implement sequentially. Tester handoff: receive exact artifact/revision, FP IDs and developer evidence; execute independent acceptance and report PASS/FAIL/NOT RUN per runtime. Reviewer handoff: inspect diff, source/expectations/generator agreement, P1–P24 ownership and the measured native comparison. Main agent owns plan/evidence reconciliation and the later merge decision. There are no claimed current GREEN tests, device runs, or completed product DSL capabilities in this design-only branch.
