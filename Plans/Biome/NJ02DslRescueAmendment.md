## Decision boundary and observed consumers

The isolated Arm A project `SKILL` construct already uses `parseSurface`, `readProgramTypes`/`ExprTypeRegistry`, Kit `readData`, and Core `readExprValueResult`. E1–E3 and T1 reached executable typed TypeScript and Kotlin outputs. Its independent diagnostic audit ran **19/19**, with **10 PASS / 9 FAIL**: N1, N3a/b, N4, N5a/b, N6b, N7c, N9b. The bad references and typed leaves often locate the whole `SKILL` declaration; a cycle can omit its second edge. It remains **NO-GO**. The isolated native Arm C remains NO-GO on N9a's offending call location and has not covered every frozen authored-source mutation. Arm B's TOML diagnostic repairs remain experimental. No comparison winner or full NJ02 PASS follows from these observations; use the current receipts in their isolated worktrees, not a stale merged status.

The product's existing `courses/core/constructions.json` and `courses/core/features.json` are real registry facts. `scripts/validate-pack-v2.mjs` reads them, checks their schemas and resolves curriculum construction IDs, feature keys and values, and language `usesFeatures`; `tests/pack-v2.test.ts` covers parts of that path. They are **not yet** a second consumer of a generic located Biome reader: they are JSON, and `CoursePackLoader.kt` merges lexicon/pair layers, while `training/Curriculum.kt` parses embedded curriculum JSON and `core/PlEngine.kt` consumes the resulting skills. A second language output, another SKILL row, `TextProbe`, or a test-only registry fixture does not establish P13. A migrated registry is eligible as a second, separate authoring family only if its independently required nested diagnostic cases execute through the same generic API and the actual pack validator reads its one generated registry. Kotlin registry output must be compiled and executed too if claimed, but that alone is not a second consumer. If this production path cannot be shown without a second authority, stop Core promotion at **P13 NOT PROVED**.

## Smallest Core/Kit contract to test

Keep the current grammar and `SKILL <body:text>` project declaration. `packages/core/tests/fixtures/slots.construct` already demonstrates `HEAD`/`ITEM`, `UNIQUE` and `ref(TABLE)`; the typed record/list reader and `TYPE` catalog cover shape. Do not add a new keyword, Polish parser, recursive project type checker or application JSON. The measured missing guarantee is the source location of an offending nested value or typed member after successful literal parsing. Today `packages/kit/src/data-values.ts::tokenizeData` creates token positions and `readDataValue` uses them for syntax/duplicate-key errors, but its successful `DataValue` discards them. `packages/core/src/expr/value.ts::readExprValueResult` returns only `{ok:false}` for type refusal. `packages/core/src/expr/type-registry.ts` already owns canonical types; `packages/kit/src/diagnostics.ts` and `packages/core/src/diagnostics.ts` own generic diagnostic coordinates/shapes.

Propose **additive**, narrow APIs, subject to a small proof before implementation commitment:

- Kit `readLocatedData(text)` returns either the existing syntax error with its local span or a `LocatedData` tree containing the unchanged `DataValue`, a span for every scalar/container, record key and member value, and list index. Record and list order stays authored order. Its path is structural (`member name` / `list index`), never a curriculum concept. Existing `readData` and `readDataValue` signatures/results stay intact. The tree is compiler-owned immutable data; no source file IO or target printer belongs in Kit.
- Core `checkLocatedExprValue(type, located)` (name provisional) uses the existing `ExprType` validation semantics and returns success with the same raw value or a typed issue `{path, span, expected, actual}`. It must report the bad nested value, or the containing record for a missing member; it does not invent a Polish diagnostic code, resolve course references or materialize optional fields. Keep `readExprValueResult` and `checkExprValue` behavior compatible. Avoid a second recursive type walk: factor the existing checker if needed, or reject this API design if sharing cannot be done cleanly.
- The project build adapter composes body-local offsets with the `parseSurface` slot origin once, retaining source ID and physical line/column. A project-only complete-record rule iterates the declared `Skill` members and requires each authored member to be present before optional materialization. Product reference validation indexes located `id`, `construction`, `focus`, `fixed`, `lexicalFilter`, `prerequisites` leaves, and each prerequisite edge. It owns duplicate skill IDs (both origins), missing/wrong-kind references, and cycles (both edge origins). The validator reads generated registry facts; neither Kit nor Core knows `Skill`, `Case` or a lexicon.
- Preserve current data escape acceptance for existing APIs under P14. For the new course-authoring profile, the build boundary strictly decodes UTF-8 and refuses unpaired UTF-16 surrogates and unsupported escape spellings with locations before emission. T1 remains a separate printer-only exact 21-unit TS/Kotlin execution probe. Do not change the text-wire legacy preservation contract.

The first implementation step is a tiny failing proof for one nested wrong type, one duplicate nested member, one bad reference token and a two-edge cycle, then the minimum shared API that makes those cases pass. If Core's current `DECLARE`/`ref` bindings can locate a case directly, use them and omit the corresponding new API surface. The typed location API is a general mechanism only when both real authoring families require it.

## Equal-guarantee comparison and proof gates

The bounded A rescue, B TOML, and C static native builder use the **same** E1–E3, N1–N10, T1, test-only reference catalog, validated IR contract, TS/Kotlin output types, printers and source/binding/output freshness contract. When testing the registry as a second family, each arm also authors the same independently frozen mandatory R1/R2/R5–R9 cases once, uses the existing production pack-validator contract, and charges its own additional authoring/parser/builder cost; no arm borrows another arm's registry source. R3/R4 are outside this comparison unless separately accepted as new requirements for all arms. B and C must either meet the exact source-location and Unicode guarantees or remain NO-GO; a green generic rejection is not equal evidence. Keep parser, type, reference and printing costs separate. The native comparator is a serious build-time helper with one authored non-JSON fact source per family, explicit required/null/empty states and the same currently required relation checks; measure it rather than assigning hypothetical cost. The TOML parser is pinned directly and confined to build time; it is a comparator, not automatic fulfilment of primary subject facts' DSL home. No branch may emit application JSON or import an authoring parser in runtime.

For P4/P8, record fixed project definition/type/adapter/printer/check cost once and marginal authoring cost across **32 actual curriculum skills**, not three only. Apply the same three valid edits (scalar feature value, nested filter/list, nonempty-to-empty prerequisite list), plus registry edits (construction axis and feature value), and count semantic edit sites, duplicated facts, authored/generated LOC, new concepts, defects caught, review locations and time. Keep compile, startup, runtime and review cost separate; static tokens are not LLM usage. A DSL-first route remains justified only if it satisfies the frozen guarantees and offers a concrete ownership or maintenance gain against the equal-guarantee native helper. If native still wins, record the explicit P4/P8 exception decision separately; do not silently move primary course facts outside Biome.

For P14, baseline existing accepted trees **including spans** and rejected first diagnostic **code and position** from the current Kit/Core public readers and relevant `.sources`/project conformance. The new API is additive; use `constructs.lock`, host-additivity, and a semantic differential with **zero unclassified divergences**. Intentional changes require a separate owner requirement and independent expected-value revision, never a generated-output adjustment. Negative boundary tests prove no Kit/Core import of product names, FS or authoring loader in runtime. For P23, run N=10/100/1000 on the actual located reader, type check, reference validator and real TS/Kotlin printers/consumers. Measure wall/CPU with alternating comparable samples and logical steps, show linear growth and at least **2× headroom** at N=1000 under existing limits. Do not raise budgets or replace printers with stubs.
