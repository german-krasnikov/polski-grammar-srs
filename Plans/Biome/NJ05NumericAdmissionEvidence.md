## Accepted lower bounds and observed rejection

The earlier [legacy-boundary.cases](../../tests/fixtures/textwire/legacy-boundary.cases) fixes 9,999,999/10,000,000-byte progress and vocabulary decoder inputs and 999,999/1,000,000-byte preferences decoder inputs. The new [numeric-admission.cases](../../tests/fixtures/textwire/numeric-admission.cases) fixes their exact `limit + 1` counterparts. All three **common decoders** accept those plus-one values: they have no host import gate. The common `VocabularySession.importJson` rejects the 10,000,001-byte input before a repository write; macOS Native `MacProgressRepository.importJson` and `MacPreferencesRepository.importJson` reject their plus-one inputs before creating an old file. Exact-at-limit host import/readback was **not run** here. It cannot be inferred from a common decoder PASS or source comparison. Android progress/vocabulary and iOS host gates were inspected in the previous ledger, not executed by this supplement.

The old progress decoder retains a 256-array-deep unknown value, 32,768 ordered unknown array items (each a map with scalar `i`) plus 9,617,777 unknown `x` units at the exact 10,000,000-byte input ceiling. That tree has **65,545 preorder rows**, including root and its known fields. The full array and every ordinal, padding length and root field order are asserted. It also retains a literal Polish key, literal emoji, escaped surrogate pair as two UTF-16 units, TAB/LF and an unpaired high surrogate as one code unit on the executed targets. These are lower bounds on what old code accepts; no maximum depth/row/string count was discovered. Old `VocabularyCodec.decode` discards its unknown `padding`, so the vocabulary padding controls prove parsing but **not lossless migration**. Strict migration must retain representable unknowns through a separate adapter or return recovery without changing the old bytes.

Pure arithmetic in [check_numeric_sizes.py](../../tests/fixtures/textwire/check_numeric_sizes.py) counts header/row/key/payload/digest bytes from the typed progress tree. It does not call or implement a candidate encoder. For the accepted 10,000,000-byte single-string input the complete A document would be **10,000,112 bytes**, C **40,000,022 bytes**. For the accepted 32,768-item input A would be **10,196,726 bytes**, C **39,214,145 bytes**. Thus a 10,000,000-byte *output* cap would reject two already accepted progress trees; the withdrawn 64-depth cap rejects the depth-256 tree. B has a separately reviewed printer NO-GO and no byte oracle. These examples do not establish safe common semantic caps or physical ceilings for any arm.
