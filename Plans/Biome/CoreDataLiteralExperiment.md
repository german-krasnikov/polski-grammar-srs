Do not add language syntax merely because a product-specific implementation could be shorter; compare it with the same-guarantee native helper first.

## Bounded source and contract

Create proposed experiment-only files `courses/lang/en/curriculum.core-data` (values), `courses/lang/en/curriculum.construct` (surface definition) and `courses/lang/en/curriculum-types.program` (Core `TYPE` declarations). These are NEW paths, not existing APIs or accepted production sources. Keep the build adapter under `scripts/` as one build-only consumer of Core APIs. The value source has one `SKILL` declaration and **one complete Biome record literal per physical line**. The following is the exact candidate source text to test, in authored order E3, E1, E2. The older full curriculum order remains the independent 16-ID expectation; these three lines are a bounded selection, not a replacement ordering for all skills.

```text
SURFACE curriculum
SKILL {id: "en:role.object" construction: "core.argument.case-role" focus: {feature: Case from: Subj to: Obj} fixed: {Tense: Pres Person: "1" Number: Sing} lexicalFilter: null level: A1 prerequisites: []}
SKILL {id: "en:role.recipient" construction: "core.argument.case-role" focus: {feature: Case from: Obj to: To} fixed: {Tense: Pres Person: "1" Number: Sing} lexicalFilter: {slot: noun where: {nounId: [wife husband friend son dog cat child]}} level: A2 prerequisites: ["en:role.instrument"]}
SKILL {id: "en:mixed" construction: "core.composite" focus: null fixed: {} lexicalFilter: null level: B1 prerequisites: ["en:possessive.my" "en:verb.pastSimple"]}
```

Use one reusable **project-level** `SKILL` construct, not a curriculum lexer: `SURFACE curriculum CODES CURRICULUM CONSTRUCTS SKILL` and `CONSTRUCT SKILL VERSION 1 IR 1 SCOPE project` with `PATTERN SKILL <body:text>`, `DECLARE`, and an ordinary conformance `EXAMPLES` file. Build it from the established declaration examples in `packages/core/tests/fixtures/slots.construct` and `packages/core/tests/declaration-data.sources`; reuse existing project TEMPLATE/generation patterns where they can emit the required typed outputs and freshness checks. `parseDefinitions` owns the definition; `parseSurface` owns line recognition, unmatched-line errors and slot spans. The source uses the standard `SURFACE curriculum` header. The `body` slot remains raw until the shared Core data reader processes it. A newline inside a record is outside this experiment: current `readData` accepts space/tab between tokens, not layout newlines.

Put the sole structural type authority in a Core-readable `TYPE` source, consumed with `readProgramTypes` and `types.resolve('Skill')`. Its bounded declarations are `Focus = record{feature:text,from:text,to:text}`, `Fixed = record{Tense:optional<text>,Person:optional<text>,Number:optional<text>}`, `FilterWhere = record{nounId:list<text>}`, `LexicalFilter = record{slot:text,where:FilterWhere}`, and `Skill = record{id:text,construction:text,focus:optional<Focus>,fixed:Fixed,lexicalFilter:optional<LexicalFilter>,level:text,prerequisites:list<text>}`. Write each as a `TYPE Name = ...` line; do not maintain a second handwritten TS schema, Kotlin field list or printer schema. These `Fixed` members are only the E1/E2/E3 slice. Full feature-map coverage requires a separately proven general contract, not silent acceptance of other keys as untyped data.

The product build-time adapter calls `parseSurface`, then the existing `@biome-dsl/kit` `readData` on each `body.raw`, and Core `readExprValueResult`/`checkExprValue` against the resolved `Skill` type. It must not implement a second record/list parser or recursive type validator. `readData` returns the raw ordered value; do **not** call `materializeExprValue` before checking presence because optional materialization can turn an omitted member into `null`. Apply one generic **complete-record policy** to `Skill`: iterate its declared members and require `Object.hasOwn(raw, member.name)`, including optional nullable members. This one rule rejects omitted `focus`, `fixed`, `lexicalFilter` and `prerequisites` without a second field-name list. `fixed: null` fails the Core record type; `fixed: {}` passes because its three members are optional. Retain the parsed object/list insertion order in the validated IR and printers; never sort source records or prerequisite/filter lists.

After structural validation, one product contract/reference pass reads the independently frozen, text-only bounded catalog from the oracle: seven skill IDs and their declared edges, two construction IDs, selected feature/value sets and seven noun IDs. It checks unique skill IDs, construction/focus/fixed/filter references, missing prerequisites and prerequisite cycles. This pass owns domain relationships only; Core owns literal syntax, duplicate members and type shape. The catalog is test-only and is not generated from old application JSON or emitted as a second curriculum source. Production catalogs must later become single-authority declarations with freshness checks.

## Diagnostic ownership and current gaps

`parseSurface` reports unknown/malformed `SKILL` lines with declaration spans. `readData` reports literal syntax and duplicate record keys with an offset relative to `body.span`; translate that offset to the source line/column once. The complete-record policy reports a missing member at the containing record's span; freeze the chosen position in the independent syntax-specific test before running it. The domain pass reports duplicate IDs at both declarations and bad references/cycles at the relevant declaration. **Current Core `readExprValueResult` returns only `{ok:false}` for a type mismatch, and `readData` does not expose nested value spans after parsing.** N5/N7/N9's exact bad-field spans and N3/N4's nested reference spans are therefore an explicit experimental gap. If required diagnostics fail, extend the generic Core reader/checker to carry a path and source span from the same token stream; do not add a Polski-only parser, search strings to guess a span, or call a generic rejection proof of a precise relation. Freeze expected codes/positions after choosing the source and before implementation execution. Preserve DSL 1.x accepted/rejected behavior under P14 when changing Core.

Current data text escapes cover `\\`, `\"`, `\n` and `\t`; unknown escapes are preserved. Thus a textual `\uD800` is **not currently decoded or rejected as an unpaired surrogate**. N8 requires a general authoring-profile check or compatible Core rule, strict UTF-8 source decoding and spanful rejection of invalid surrogates before emission. Do not present existing Core parsing as satisfying N8. Raw valid astral Unicode must remain accepted. This authoring restriction does not change the separate legacy text-wire preservation requirement.

This experiment executes generated TypeScript and Kotlin value assertions, but **does not change live React or Kotlin curriculum loaders**, transcribe the other 13 English skills, adopt the source for production, or claim device/browser integration. Existing React `src/data/course.ts` is a Polish presentation `Skill` path, not an English `SkillSpec` consumer. Later live integration and full 16-skill reference resolution require their own gates.
