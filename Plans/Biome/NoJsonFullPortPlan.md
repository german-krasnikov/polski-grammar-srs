## Owner constraint and acceptance boundary

The owner has clarified **zero JSON for application-owned authored sources, generated artifacts, runtime/interchange messages, user storage, and new exports/imports**. The only application-data exception is **read-only, one-time parsing of an existing user's legacy JSON save to migrate it to the new text format**. A successful or failed migration must never write a new JSON document, export JSON, or store a newly serialized JSON backup. Preserve the exact original legacy bytes during a migration attempt so every failure can recover; after validated text readback and a durable text receipt, remove the old JSON key/file **and its old JSON backups**. A failed or unsupported migration keeps the original bytes in recovery without overwriting them and cannot be reported as a completed zero-JSON state. Existing `.json` course/test artifacts may be consulted read-only as historical controls during development, but cannot be active new-format sources or shipped with the accepted product. The sole accepted-test exception is an **exact-path, byte-hashed, immutable, input-only legacy-user JSON corpus** for clean-CI migration tests. It may be read only by the migration decoder (including crash retry), never generated, edited to match implementation, bundled, exported or written to user storage. All other active JSON fixtures are removed. List every legacy input path and hash before accepting NJ06; never disguise JSON under a different extension.

**Tool-required manifests/configuration are allowed exceptions**: `package.json`, `package-lock.json`, `tsconfig*.json`, Xcode asset-catalog `Contents.json`, and temporary manifests required by an external build tool. Their contents must be tool configuration, not a hiding place for app course facts, requirements, generated read plans or user data. List every exception and its requiring tool in the release inventory; a generic `*.json` exemption is disallowed. Third-party packages may use their own private formats; the app may not treat those as application interchange. If a build tool starts emitting an app-owned JSON file, this exception does not cover it.

This explicit owner constraint takes precedence over biome-dsl `AGENTS.md`'s prior allowance for generated/machine JSON. Preserve its independent expectations and execution rules, and apply `AI/PRINCIPLES.md` P4/P5/P7/P8/P10/P15–P18/P23: appropriate DSL source, one authority, measured native comparator, no silent expectation edits, no hand-fixed generator output, real executed gates. The target is a complete product preserving FP01–FP11 from [FullPortPlan.md](FullPortPlan.md), not a claim that every UI callback or codec operation becomes DSL. Native Kotlin/Swift/TypeScript may implement mechanical encoding, effects, scheduling arithmetic, input handling and platform lifecycle; authored domain rules and requirement examples need a justified DSL home.

The review-credit pilot tested only one rule: `typedCorrect ?: (rating != Rating.Again)` and its TypeScript equivalent. One reusable construct with two target templates could serve **many** decisions, so the one-rule NO-GO does not establish the cost of that family. Inventory actual cross-target decision sites and compare **three** implementations over the whole family: an existing DSL rule, one reusable semantic construct/template, and small static native helpers in the correct layer, all under the same independent expectations and consumer checks. Count one-time template cost once, then marginal cost per use, fact bindings, generated outputs and duplicate semantic decisions. Native static helpers are valid permanent owners for mechanical operations and low-value one-off work; do not hide recurring domain policy, state mutation or test expectations inside a helper (P4/P7/P8/P10). Keep the current review-credit reducers unchanged until that comparison demonstrates a guarantee or maintenance gain; do not extrapolate the isolated pilot to all small rules.

Use the [Biome capability map](BiomeCapabilityMap.md) to choose the language **by semantic owner before implementation**: Core declarations/contracts for authored types, structures and references; Logic for shared verdicts; FEATURE for model state and actions; FLOW for ordering, resource lifetime and cancellation where the target backend exists; TEMPLATE/project generation for target output; independent examples for requirements. Find the closest Biome example and try its existing public path first. If the shape is product-specific, compose a reusable project CONSTRUCT/PATTERN/TEMPLATE on those mechanisms and compare with a good static native helper. Extend general Core only for a demonstrated missing guarantee and prove a new general facility on a second real consumer; do not switch to a flat encoding or invent a project-only parser. Do not force codec bytes, FSRS arithmetic, platform IO, or UI gestures into a DSL solely to increase its usage count. The no-JSON requirement may also require replacing an existing compiler JSON output before that DSL can be accepted in this product.

## Proposed textual source and output contract

The current `.tables` `ROWS` grammar cannot satisfy this requirement. Its 16-row English pilot encoded `focus`, `fixed`, `lexicalFilter` and `prerequisites` as opaque cells, and `renderTablesJson` generates JSON. Parent/child columns conflict, while the curriculum needs both explicit null and nested values, plus an empty `fixed` record. The measured pilot retained one semantic edit site, increased review surfaces and failed P8. This result does **not** prohibit typed Biome record/list literals. Existing Core `readData`/`readExprValueResult`, `TYPE` and SURFACE examples must be tried directly in a project `SKILL` construct before general syntax work. A targeted experiment must still prove references, diagnostics, typed TS/Kotlin output and actual execution; no existing path is yet accepted for the whole course.

The isolated Stage 1 construct-only `.feature`/`DECLARE`/`ITEM ROW`/TS-Kotlin `TEMPLATE` probe has now run at product `8234880` and compiler `5c12f3a0` (see [acceptance ledger](NoJsonAcceptance.md)). It generated and executed flat rows, but could not represent typed nested/optional/empty curriculum values or validate references: **NO-GO for that flat path**, with full gates still open. Before adding syntax, inspect existing Biome patterns: `HEAD`/`ITEM` with `UNIQUE` and `ref` in `packages/core/tests/fixtures/slots.construct`; typed `list<record{...}>` runtime state in `corpus/labs/authoring-data` and `corpus/apps/booking`; and compiler-prepared typed declarations in `packages/languages/program-bindings.construct`. The owner clarified that Core record/list literals are valid Biome authoring syntax. First test them with the existing reader and a project `SKILL` construct; compare this with a strict established text format and a static native helper under the same independent cases in [NJ02Blueprint.md](NJ02Blueprint.md). Execute TS/Kotlin escaping checks for accepted `$`, quotes, backslashes and line separators, and execute rejection of unpaired surrogates in curriculum authoring; a separate printer-only code-unit round-trip is required only if that helper claims to support unpaired surrogates. The current **candidate**, not accepted product syntax, is one project `SKILL <body:text>` declaration binding a typed Biome record literal, with the exact bounded source example in [CoreDataLiteralExperiment.md](CoreDataLiteralExperiment.md), including all required fields. The exact grammar and diagnostics remain experimental. [NJ02Blueprint.md](NJ02Blueprint.md) is the detailed A/B/C contract; [CoreDataLiteralExperiment.md](CoreDataLiteralExperiment.md) is the canonical isolated Core-reader experiment. Neither licenses course transcription or a general Core change before the independent E1–E3/N1–N10 cases execute.

The selected mechanism must represent ordered records/lists, optional versus explicitly absent values, empty maps/lists, string values such as `Person = "1"`, Unicode and multiline explanatory/citation text without application JSON. Biome inline record/list literals are allowed when they meet those semantics. Text blocks require unambiguous escaping or length delimiters, source spans, validation and stable round-trip. Use separately named reusable constructs for nouns/paradigms, recipes, lifehacks, styles and editorial copy; do not flatten the 64,573-line human-classified inventory into one unreadable row or invent a Polish-only parser. Emit typed TS/KT values from a common validated IR, preferably sharded by pack/domain to avoid compiler or Kotlin constant limits. Generated files are build outputs, never edited; a text manifest pins compiler revision and checked generator inputs. Kotlin `:core-model`/`:pack-format` types and current public entrypoints remain compatible through adapters while JSON parsers are retired. Source order, null/empty distinction, exact Unicode and content strings, and all accepted invalid-reference diagnostics need independent expectations frozen **before** the first source move.

For acceptance, no generated course artifact or test fixture may contain an application-data JSON object encoded as a string. A source extension change alone is not migration. If a Core typed record capability is too costly or unavailable, evaluate an established non-JSON textual format with a strict shared schema and typed emitters against the same guarantees and P8 comparator; do not quietly build separate TS and Kotlin parsers. Record any Core change as general, independently conformed compiler work, with boundary and representative host checks required by biome P2/P9/P10.

## New text save, migration and bridge contract

Choose one versioned UTF-8 **text record wire** for new progress, vocabulary and preferences files and cross-host import/export only after the equal-guarantee A/B/C corpus in [TextWireExperimentBlueprint.md](TextWireExperimentBlueprint.md). The `.polski` extension and `POLSKI-TEXT` header in [TextWireDesign.md](TextWireDesign.md) are candidates; the earlier `POLSKI-DOC 2 <kind>` example is withdrawn and is not a selected protocol. The chosen wire needs canonical ordering and a specified escape/length rule for arbitrary text, tabs, newlines, backslashes, Unicode and user-authored words. Records must distinguish absent from empty, preserve integer/floating point FSRS values and timestamp precision, reject malformed/duplicate fields/IDs, and retain unknown extension fields where compatibility requires it. A checksum or digest must cover exact committed bytes; do not use locale-dependent formatting. The shared KMP codec serves Kotlin hosts; a TS codec for the retained React baseline uses the same versioned specification and independent cross-decoder corpus. The physical storage adapter remains platform-owned. Snapshot wire, if typed Swift bridging fails, is a separate `snapshot` kind with revision/effect IDs and bounded size, not a save-document parser reused blindly for UI.

A valid new text document with legacy bytes but no matching durable receipt returns `RecoveryRequired` before any write, delete or ordinary save; malformed or mismatched receipts do the same while preserving both byte sequences. A matching verified receipt after a crash permits only idempotent cleanup. These state decisions are independent [transaction cases](TextWireExperimentBlueprint.md), not codec evidence. The **sole legacy exception** is a read-only JSON decoder for an existing user's `progress-v1`, `vocabulary-v1` and preferences files/keys, invoked only when no valid new-format document exists or during explicit import of an old user save. No call path may serialize legacy JSON for new saves, backups or exports. Migration order: detect new document and receipt; if absent, read and preserve original old bytes without mutating them; strictly validate legacy version/content and all known and unknown fields; convert to typed model, including representable unknown fields as typed text extension records; reject unknown data that cannot be converted without loss; encode new text; write to a *new key/path*; read back and decode; compare every semantic field and extension plus checksum against the in-memory model; write a durable idempotent **text receipt**; then delete the old JSON key/file and any old JSON backup. A crash between receipt and deletion resumes cleanup without re-importing or duplicating reviews/custom words. On parse/write/readback/receipt/delete failure, do not overwrite old bytes or an earlier valid new document, and surface recovery; the presence of old JSON remains an incomplete migration, never a claimed successful zero-JSON state. The legacy decoder must have no normal read path after committed cleanup. Do not overwrite a legacy save with a fresh empty document. Never expose a newly generated JSON download. Old imports are read-only input to this path; exported downloads and file picker labels/MIME types are new text format only. The changed requirement for legacy byte-identical JSON export is recorded separately by ADR-51, not silently patched into old independent expectations (P15).

One-time migration must be proved for browser localStorage, Android app-private files, Compose Desktop, iOS and native macOS, plus cross-host text import/export. Test missing/unsupported/corrupt/truncated old bytes, duplicate IDs, unknown skills, all FSRS states and timestamps, local midnight/DST, partial marker/backup/readback failures, interrupted writes, retry, rollback and cancel. Preserve current user progress, vocabulary cards in both directions, preferences and existing old-format data until the transaction is recoverable. If a platform cannot safely read its existing legacy data and commit a new document, that platform blocks the release. Browser release also needs demonstrated quiescence or exclusion of old-version tabs: a new-tab lock cannot stop old code rewriting JSON after cleanup. An old-tab rewrite returns to recovery and blocks a completed zero-JSON claim. Track codec bytes, domain documents, and host transactions as three separate gates; a codec PASS closes neither document semantics nor host safety.

## Stop, rollback and review

Stop a slice if text authoring merely embeds JSON under a new extension; a second human-maintained fact copy appears; Kotlin/TS generation requires manual semantic bindings; a generated file is hand-fixed; null/empty/order/Unicode/forms differ; the legacy decoder writes JSON or destroys old bytes; an interrupted migration cannot safely retry; a compiler/backend cannot execute in a required consumer; an independent expectation is rewritten to match output; host execution is missing but reported PASS; an app-owned JSON artifact remains; or the equal-guarantee native solution wins P8. Retain NO-GO evidence. Roll back experimental source/build changes without touching legacy saves or unrelated inventory repair; after a released migration, never downgrade a new-format user document by writing JSON. Review each change against the named P principle, concrete file, failing case and consequence. A local prototype, clean compile, generated plan or linked test is not proof of FP01–FP11 or NJ01–NJ10 completion.
