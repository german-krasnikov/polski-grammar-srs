## Frozen contract before any arm changes code

Use the separately owned [NJ02IndependentCases.md](NJ02IndependentCases.md) at tester commit `77ddeadc6227e11dd7f1cc44659cbefc64663b5c`, SHA-256 `a989a5aa9e2c4efb8e73f585d726e61f900446412b7dd6b448710882688fd2a3`, as the frozen preimplementation oracle for the English values, a shared reference environment, and N1–N10 categories; do not modify it from an implementation arm. The independent tester froze exact reference IDs/values and old-source hashes. All arms inject the same test-only reference catalog into one validator; none may read legacy JSON at generation time, hardcode references inside a printer, or skip resolution for a partial slice. The tester must freeze any further syntax-specific source span and second-family cases independently before running them. Record exact product/compiler SHAs, read-only source hashes, requirement provenance, command, cwd, target, selected/executed/skipped counts, output hashes and owner. Historical application JSON may be read as an oracle during development; no new authored, generated, intermediate, fixture-output or runtime application JSON is permitted. The acceptance inputs and expected values must not be generated from the backend under test.

Start with E1 `en:role.recipient`: focus `Case Obj → To`, `fixed.Person` is the text `"1"`, and `lexicalFilter.where.nounId` contains seven ordered values. E2 `en:mixed` has **explicitly present null** focus and lexical filter, explicitly present empty fixed map and two ordered prerequisites. E3 `en:role.object` has an explicitly empty prerequisite list. For this curriculum schema, omitted `focus`, `fixed`, `lexicalFilter` or `prerequisites`, and `fixed = null`, are **rejected before lowering**; no generated `SkillSpec` may erase that difference. These three historical skills' references outside the bounded source resolve against the frozen, test-only reference catalog. A separate typed `TextProbe.text` printer case exercises the exact 21 code units frozen as T1: Polish and Cyrillic text, LF, `$`, a quote and backslash, U+2028/U+2029 and paired astral Unicode; it is **not** an invented `SkillSpec` field or an A/B/C course-authoring site. A backtick is a separate, currently unfrozen printer case and cannot be counted as T1 evidence. The curriculum authoring profile rejects raw invalid UTF-8 and any textual escape for an unpaired UTF-16 surrogate; the printer-only probe may separately require code-unit-preserving TS/Kotlin literals from an in-memory value. This is distinct from the user-data text wire, which must preserve existing UTF-16 code units. Frozen negative cases cover duplicate field and skill ID, unknown construction/prerequisite, cyclic prerequisites, wrong feature value, malformed quoted text and a bad reference at an exact source span. No arm may substitute a string marker such as `"EMPTY"` for an empty typed map.

The common output contract is one immutable, schema-validated IR preserving source order. It emits a TS `readonly SkillSpec[]` **with a new contract-generated TS `SkillSpec` type in the same output or a separately freshness-checked generated type**, plus Kotlin `List<polski.core.model.SkillSpec>`. There is no existing TS `SkillSpec` under `src/`; `src/types.ts::Skill` is presentation copy (`title/group/formula/theory/hint`) and is not this schema. Do not hand-maintain a second TS semantic type or miscast `Skill[]`. Kotlin uses the existing `FeatureFocus`, `FeatureKey`, `FeatureValue`, `LexicalFilter` and `FeatureBundle` in `kotlin/core-model/src/commonMain/kotlin/polski/core/model/FeatureBundle.kt`. `focus` and `lexicalFilter` are nullable, `fixed` is a typed map, `where` is `Map<String,List<String>>`, and prerequisites are an ordered list. Distinct omitted/explicit null/empty states are validated **before** lowering to any existing `SkillSpec` default; `training/Curriculum.kt::toSkillSpec` currently collapses those states. One shared IR and validation pass feeds the TS and Kotlin printers. No target parser duplicates semantic validation. Typed sources are static build outputs, never hand-edited or imported as authoring files by app runtime.

For the bounded spike, use **proposed, new** output paths `courses/build/generated/en/Curriculum.generated.ts` and `kotlin/shared/build/generated/course/kotlin/polski/data/GeneratedEnCurriculum.kt`; the latter follows the observed `generatedCourseDirectory = layout.buildDirectory.dir("generated/course/kotlin")` and `commonMain.kotlin.srcDir(generateCoursePackSource.map { it.outputs.files.singleFile })` convention, but needs its own task/output ownership if adopted. The build owns both paths and an exact non-JSON text manifest of input paths/hashes, compiler revision, output paths/hashes and a `--check` freshness command. This is a proposed contract, not an observed existing generator. Today English curriculum is embedded by `kotlin/shared/build.gradle.kts::generateCoursePackSource` into `generatedCurriculumJsonByLang`, read by `training/Curriculum.kt::parseCurriculum` and `core/PlEngine.kt::PackEngine.skills`; `plCurriculum` is the separate Polish accessor. React `src/data/course.ts` instead imports `courses/pl-ru/course.json` and maps its presentation `Skill[]`; it does **not** consume English `SkillSpec`. Direct TS generated-module execution is a compiler/output-contract test, not a live React consumer. Later live integration must name and actually replace the relevant Kotlin load path and any genuine TS consumer; it cannot claim a TS app path merely from a generated import. The NJ02 spike does not edit those live paths.

## Arm A — existing Core data literals with a project declaration

**Existing Biome patterns checked before adding syntax.** `packages/core/tests/fixtures/slots.construct` already uses `HEAD TABLE` plus repeatable `ITEM COLUMN`, `UNIQUE` and `ref(TABLE)`; reuse that binding, span and reference behavior. `corpus/labs/authoring-data/authoring-data.feature` and `corpus/apps/booking/booking.feature` use `list<record{...}>` as typed **runtime state**, not as initialized nested course source. `packages/core/src/expr/value.ts::readExprValueResult` and `packages/core/tests/expr-values.sources` validate nested typed data and distinguish optional absence from refusal. The owner subsequently clarified that these record/list literals are Biome DSL syntax and may author course data. `packages/languages/program-bindings.construct` emits records in TS/Python, and Kotlin test definitions add a Kotlin printer, but its `BODY <body:string>` is prepared by the compiler rather than authored nested values. First try the existing reader in a reusable project `SKILL` construct; the Stage 1 flat `ROW` failure does not test this path. The isolated `experiment/nj02-core-data` branch holds its bounded plan. Do not claim it is accepted until the independent cases execute.

**Candidate, not accepted syntax.** The isolated Stage 1 current-Core preflight tried construct-only `.feature`, `DECLARE`, `ITEM ROW` and TS/Kotlin `TEMPLATE` on E1/E2 and observed the failed flat-row semantic boundary; it did not test the existing Core data reader or prove the independent negative corpus. Use a project `SKILL <body:text>` declaration through Core `parseSurface`, a named `TYPE Skill = record{...}` contract through `readProgramTypes`, and `readData`/`readExprValueResult` for the nested value. The project owns only its semantic references and required-field policy; it does not reparse records or walk types. Test this direct composition before considering a general Core extension. Current Core returns no field path for typed refusal, permits omission of `optional` record members, and does not treat a textual `\uD800` as a Unicode escape; these are explicit cases to measure, not reasons to skip the existing path.

A proposed readable source has one `SKILL {id: ... focus: null fixed: {} lexicalFilter: null prerequisites: [...]}` Biome record literal per physical line. This is Biome data syntax, not JSON. The Core type owns shape, the project declaration owns the repeated course form, and a reference pass owns catalog/cycle relationships. Preserve explicit presence before any optional materialization. The TS/Kotlin printers receive one validated IR; they do not make domain decisions. No Polski-only record parser or `ROW` string decoding is allowed.

The first experiment needs no Core source edit: its new `.construct`, type source, literals, build adapter, shared IR and target printers live in the isolated product worktree. Only if an independent negative case exposes an unmet guarantee should a generic Core diagnostic or reader enhancement be proposed, with a second unrelated real consumer, compatibility evidence, architecture rationale and a negative boundary test before promotion. The project output step needs an exact text manifest and freshness check.

The isolated `ESCAPE ts|kt` extension at compiler `5c12f3a0` stays experimental. Two emitted target languages and the English/Polish datasets of this one product are **not** two independent real consumers of a new general Core capability under P13. Identify a separate genuine use family/project with independently frozen cases before promoting new syntax or a new target escape facility; otherwise leave it experimental. Execute generated TS **and** Kotlin for T1's exact `$`, quote, backslash and line separators in the typed `TextProbe.text` printer case; separately freeze and execute a backtick and unpaired-surrogate printer case if that helper claims to support them. The curriculum source validator must reject unpaired-surrogate input before generation. Those executions prove product target behavior only, not P13 reuse.

## Arm B — established textual format, one build-time parser

**Candidate comparator, not an automatic biome-dsl port:** TOML 1.0 authoring at new `courses/lang/en/curriculum.toml`, with one explicitly pinned build-only parser, one strict schema-to-IR validator and the same typed emitters as the other arms. TOML can be the sole textual course data source, but is a general data format rather than a subject-specific biome construct; P4/P7/P8 require an explicit measured reason to leave this primary subject fact family outside biome authoring. The parser package and its strict duplicate-key/source-position behavior require verification before selection; an incidental transitive package is not a dependency contract. The app runtime never loads TOML or its parser.

Use arrays of tables for ordered skills and prerequisite/filter values, nested tables for focus/fixed/filter records, and quoted strings for numeric-looking values. An empty `[skill.fixed]` table represents an explicit empty map. Require `focus_state = "null" | "value"` and `filter_state = "null" | "value"`; a missing state is invalid, and `value` without its record is invalid. **Require `prerequisites_state = "empty" | "items"`**: reject `items` without child tables and `empty` with children, so omission is not silently taken as empty. Likewise define exact empty versus absent behavior for every optional/list field in the frozen schema. Ban inline tables/arrays and every JSON-looking flow cell in authored content; reject implicit defaults, duplicate keys, coercion of `"1"` into a number, aliases or extensions outside the selected TOML profile. Validate exact order, Unicode, spans and source hashes through the same cases as A. TOML section nesting shown here is a design candidate; test the actual parser against a small source before authoring more rows.

Proposed product touchpoints: new `courses/lang/en/curriculum.toml`, a build-only parser/validator under `scripts/`, shared typed IR/printers, `courses/biome.project` or an equivalent existing project generation step, the two proposed build outputs and text manifest. A direct package manifest entry is a tool-required JSON exception containing dependency configuration only; no course facts may enter it.

## Arm C — static native build-time helper comparator

**Candidate equal-guarantee comparator, not an automatic biome-dsl port:** one authored, non-JSON `courses/lang/en/curriculum.source.ts` using a fluent static builder such as `skill("en:mixed").construction(...).focusNull().fixedEmpty().filterNull().requires(...)`. The concrete API is not approved. A generic `scripts/course-records.ts` helper validates cardinality, types and references into the **same** IR and invokes the **same** TS/Kotlin emitters used by A/B. It runs at build time; no parser, authored module or second hand-maintained Kotlin list enters runtime. Domain facts remain in exactly one authored source. This is a serious equal-guarantee native comparator, not a straw man; its builder owns mechanical validation and output, never exercise verdicts, mutation or requirements. If it measures best, record the explicit P4/P8 exception for native ownership of primary course facts and whether that still meets the owner's biome-dsl migration target; a low LOC count alone does not grant acceptance.

If C wins under equal tests and host checks, document the P4/P8 reason for native authoring and the explicit semantic edit site. If it duplicates a subject rule, hides a fact in the helper, or needs a separately maintained Kotlin copy, it fails P4/P7 regardless of line count.

## P8/P13 comparison and decision rule

The read-only base curricula have 16 English and 16 Polish skills: 32 actual potential SKILL construct uses, 24 nonempty focuses, 11 lexical filters, two empty fixed maps and 34 prerequisite values. Count one shared definition and target printer cost **once**, plus the marginal source cost for each of the 32 uses. Do not credit unimplemented noun, recipe, style or other format families as savings. Their future constructs would need their own consumers and measurements. A reusable SKILL construct may win even when a one-off predicate does not; the existing review-credit one-liner remains native.

| Cost or guarantee | A Core declaration | B TOML | C native helper |
| --- | --- | --- | --- |
| Semantic authoring sites per skill | One DSL block, if contract is complete | One TOML skill table | One builder chain |
| Fixed cost to measure | Project `SKILL` declaration, Core type binding, domain references, two printers, conformance | Pinned parser, strict schema, shared validation, two printers | Fluent builder, shared validation, two printers |
| Main risk to test | Core literal diagnostics and optional-member presence; general Core enhancement only if needed | Format restrictions, parser spans/coercion, explicit state tags | P4 subject-fact ownership, readability and native source dependence |
| Runtime data path | Generated typed modules | Generated typed modules | Generated typed modules |

These are expected **edit-site categories, not measured LOC or timings**. In separate branches run the same three **valid** requirement changes: scalar feature value, nested filter/list edit, and an explicitly present nonempty-to-empty prerequisite list. Rejection of an omitted prerequisite field is a separate negative check, not a valid edit. Record semantic edit sites, duplicate facts/adapters, authored and generated LOC, new concepts/review locations, defects, generation/typecheck time, startup/runtime allocations and check cost. N=10/100/1000 real-consumer runs must show linear growth and at least 2× budget headroom where the path scales. Distinguish compile, startup, runtime and review cost; static token counts are not LLM usage. Select an arm only after independent tests and equal checks. Subject facts use the appropriate existing Biome capability first; a general extension of that capability follows only a measured, independently reviewed gap. B and C are equal-guarantee P8 controls, not automatic substitutes for the owner's DSL migration goal. If no arm passes, stop before course transcription.

**Smallest first comparative experiment (internal GO, no adoption):** on isolated worktrees at the same pinned product/source and compiler baseline, author only E1 `en:role.recipient`, E2 `en:mixed` and E3 `en:role.object`; run separate T1 on the common printer without pretending it is a fourth course record. Share the independently frozen E1/E2/E3, reference catalog and N1–N10 expected semantics, a test-only schema/IR interface, and output contract; account for any common validator/printer cost in every arm. First test the existing Core typed record/list reader through a project `SKILL` declaration: the Stage 1 flat-row NO-GO did not cover it. Compare that result with B, a pinned TOML parser, and C, a static builder, keeping each arm's authored facts solely in its own source. Extend general Core only for a measured guarantee that project composition cannot supply. Each arm must generate/check its own non-JSON TS type+values, Kotlin `SkillSpec` values and text manifest, execute exact TS and Kotlin value assertions, reject duplicate identity/key and bad references at useful source locations, and demonstrate omission/null/empty behavior without an `EMPTY` marker. Execute T1's exact text independently for both targets. Perform the same three small source edits and record actual authoring/edit sites, generated LOC, diagnostics and wall-clock/build cost. **Stop the first comparison** if any arm emits application JSON, hand patches a generated file, omits independent negatives, cannot execute both targets, or silently changes E1/E2/E3; mark that arm NO-GO with its failing case. Do not transcribe the other 13 English rows, change live loaders, promote Core syntax or select a winner from generated text alone. Full live Kotlin integration, an actual TS product consumer (if one is claimed), a separate real Core consumer, 32-row amortization, clean-CI pin and host gates remain later acceptance, not results of this first comparison.

## Required executable checks and stopping conditions

For the chosen bounded slice, write positive and negative tests first, observe a behavioral RED, then GREEN in both target consumers. Run `npx biome check changed` from compiler `implementations/typescript` after each DSL edit and the named surface check for every `not checked` file; `npm run check:boundaries`, `npm run logic:grid:check`, relevant Core/conformance tests and `npm run typecheck`. Changes to `.construct` or definition packs require grammar conformance; Core changes read by ExpansionSites require its native-sites check. Generated outputs need their own `--check` and generated-coverage gate. Run `npm run gate:all` and the final fast gate only on a completed, immutable candidate before merge, never on this blueprint.

For the product slice, plan root `npm test`, `npm run typecheck`, `npm run build`, course validation/freshness checks until replaced by equal or stronger no-JSON checks, direct TS import/typecheck/runtime and Kotlin JVM compile/runtime of the generated modules. Discover Gradle tasks on the revision; the documented relevant tasks are `:shared:jsBrowserTest`, `:shared:wasmJsBrowserTest`, `:shared:desktopTest`, `:composeApp:compileKotlinJs` and `:composeApp:compileKotlinWasmJs` as dependencies warrant. A generated file's existence, compilation alone, and a test declaration are not proof of execution. Browser, Android, iOS, macOS app and accessibility checks belong to later live NJ03/NJ09 integration and remain NOT RUN here.

Stop this slice for an actual JSON document disguised as DSL data, app JSON intermediary/output, target-specific semantic parser, hand-edited generated file, lost null/empty/order/Unicode distinction, stale output, missing or displaced diagnostic, absent second real consumer for a new Core capability, or a measured equal-guarantee native advantage.
