## Decision and boundaries

**One authored authority:** `courses/core/registry.core-data`, with `registry.construct`, `registry-types.program` and independently authored `registry.examples`, replaces the seven construction and seven feature facts in `courses/core/{constructions,features}.json`. These three source companions define the Biome surface/type/test contract, not duplicate fact tables. The generic compiler `readLocatedData` / `readLocatedExprValueResult` remains in Kit/Core; the product build adapter owns core-registry identity, nonempty/unique values and source-reference policy. It may use the compiler's existing typed reader and location tree, but may not parse Biome records again, copy the feature catalog into code, or import product concepts into compiler Core. Keep accepted null, absent and empty distinctions, order, bilingual text and `Person` values as text. R3 unknown axis and R4 composition target/cycle are **outside** the accepted parity contract; do not strengthen them silently.

**One shipped runtime:** the generated course/registry/read-plan value is typed Kotlin under `kotlin/shared/build/generated/biome/kotlin/polski/data/GeneratedCoreRegistry.kt` (NEW path), plus later generated typed curriculum. The source, generated Kotlin and text freshness manifest are distinct stages of one authority. No JSON document, JSON-shaped cell, JSON embedding, runtime JSON parser, TS course module, React consumer or target-specific semantic parser is an output of this path. The external Biome compiler may still run on Node as a build tool; it is not a product backend. The current root Node validator is transitional historical evidence and must be retired when its accepted guarantees run in Kotlin/DSL. Tool-required manifests are the narrow exception stated in the Kotlin-only amendment.

**Product types and consumers:** keep `polski.core.model.FeatureKey`, `FeatureValue` and `SkillSpec` in `kotlin/core-model/src/commonMain/kotlin/polski/core/model/FeatureBundle.kt` as the existing gameplay types. Do not coerce source `axis` absence, explicit null and text into `Construction.axes: Set<FeatureKey>`; that existing class loses the source distinction. Add a small immutable registry declaration type (NEW, in `:core-model` only if two modules need it, otherwise `:shared`) with `axis = Absent | ExplicitNull | Text`, `composesOf = Absent | Present<List<Text>>`, and similarly precise presence for optional `gloss` and localized description fields; do not admit null where the old schema rejected it. Ordered lists have no mutable alias, and these types import no filesystem/compiler API. Generate the registry value against them. A single Kotlin catalog lookup/validation function (NEW `kotlin/shared/src/commonMain/kotlin/polski/core/CoreCatalog.kt`, proposed) resolves construction IDs and focus/fixed feature keys/values for a `SkillSpec` and a language's `usesFeatures`; it returns a decision/diagnostic value and mutates no game state. Its build-time caller attaches the retained Biome leaf span, while the live `PackEngine` obtains its accepted skills through the same checked catalog before `ExerciseGenerator` construction. This is a useful live invariant: an invalid skill cannot reach the exercise engine. Check the cost of this once-per-pack guard and omit duplicate runtime traversal if a compiler-owned generated proof can make the same guarantee; the developer must record that choice. The Kotlin host continues to own session state and effects.

The current actual seams are `scripts/validate-pack-v2.mjs::validatePackV2/checkConstructionsResolve/checkFeaturesResolve`, `tests/pack-v2.test.ts`, `kotlin/shared/build.gradle.kts::generateCoursePackSource`, `kotlin/shared/src/commonMain/kotlin/polski/training/Curriculum.kt::parseCurriculum/plCurriculum`, and `kotlin/shared/src/commonMain/kotlin/polski/core/PlEngine.kt::PackEngine.skills`. `CoursePackLoader.kt` still merges lexicon/pair JSON into an old pack; it is a later NJ03/NJ09 seam, not proof that this registry is live. A generated Kotlin test importing the registry alone is a value check, not a live second-family consumer. The second family counts for P13 only after the production Kotlin build/engine uses it and R5–R7 execute on that path.
