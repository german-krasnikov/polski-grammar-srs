## Решение по старому архиву: provenance, без перепечатки

Все 39 файлов в этой таблице классифицированы как H — исторические свидетельства. При поиске в отслеживаемых исходниках не найдено программного читателя ни одного из этих путей. Поэтому нет оснований переводить 1 408 493 старых байта в новые файлы .measure: это создало бы вторую копию фактов, добавило бы риск изменения многочисленных длинных десятичных значений и не улучшило бы работу приложения (P8/P15). Новое чтение старого JSON не вводить. Если при проверке конкретного пути всё же обнаружится действительный кодовый читатель, остановить удаление этого пути и отдельно обосновать его контракт; не объявлять все 39 безопасными по одному поиску.

Для каждого старого файла сделать текстовый индекс по образцу Plans/Kotlin/Stage5FinalVirtualArtifactProvenance.md и Plans/Kotlin/Stage6ArtifactProvenance.md: исходный путь, исходный коммит 729bfb4, Git blob, размер и SHA-256 **точных исходных байтов**, ссылка на исторический отчёт (или явная пометка, что ссылка не найдена), host/сценарий и предел старого свидетельства. Читатель отчёта восстанавливает байты командой git show 729bfb4:<исходный путь> и сверяет SHA-256. Человеческие ссылки на удаляемые файлы перенаправить на точный пункт индекса; опубликованные цифры и оценки не менять. После проверки восстановления, ссылок и отсутствия кодового читателя удалить старый H-файл из текущего дерева. Индекс не копирует сам набор метрик, не создаёт новый golden и не является текущим host PASS. История Git — архив старых результатов; новый формат служит **только будущим измерениям**.

## Контракт будущего измерения и выбор механизма

Новый output для каждой из пяти живых точек записи должен быть читаемым версионированным текстом, не JSON под другим расширением и не строкой со скрытым JSON. Он сохраняет реально собранные дату/ревизию и setup, порядок движков/профилей/раундов/пар, устройство, вариант, единицы, сырые интервалы/кадры, p50/p95/p99, пороговые счётчики, контроль A/A, сводку и ограничения. Для больших рядов нужны индексированные строки, чтобы запись/проверка были линейны. Пустой набор выбранных движков, пустые runs, неполная пара или замер меньше требуемого числа кадров — отказ, не успешный пустой отчёт (P17).

**Семантическая точность будущих чисел:** конечные значения IEEE-754 binary64 после чтения должны совпадать с источником по Object.is, включая -0; NaN и Infinity — явная ошибка до записи, а null допускается только как документированное отсутствие измерения. Обычное 0, false, null, отсутствие поля и пустая коллекция различаются. Строки сохраняют точные допустимые Unicode-символы и порядок; для переводов строк, табуляции и управляющих символов нужен определённый безопасный escape или явный отказ до записи. **Лексическая точность:** у нового формата одна каноническая запись каждого принятого значения, с независимыми byte-oracles для граничных десятичных чисел. Сохранение написания десятичной дроби из старого JSON не требуется, потому что старые байты восстанавливаются без изменения из Git. Новый writer не должен округлять ради красивого отчёта. Декодер/проверка отказывают на дубликате, неверном индексе, усечении, неизвестной версии и неверной размерности. Сначала заморозить эти случаи независимо от принтера.

Формат и библиотеку **не выбирать до P8-пробы**. Сравнить две реализации при одинаковых frozen случаях: (A) существующие Biome readData/formatDataValue с узкой проектной обвязкой строк; (B) небольшой статичный проектный text/TSV helper с собственным строгим чтением и печатью. Никакой третий общий DSL-синтаксис заранее не нужен. Kit сейчас объявляет Node >=22 в своём package.json, продукт — ^20.19.0 || >=22.12.0; прямой импорт Kit поэтому пока не является совместимым решением. В A отдельно доказать доступность из **чистого product checkout** с закреплённой поставкой компилятора и запуск под Node 20.19 и Node >=22.12; если доставка или поддержка не доказаны, A — NO-GO, не локальный импорт соседнего репозитория. Существующий formatDataValue печатает -0 как 0: A должен устранить эту семантическую потерю или отказаться. readData возвращает число без исходного лексического написания: поэтому он не доказывает сохранение старых байтов (оно обеспечено Git), а канонические новые байты нужно отдельно проверить независимыми ожиданиями и повторной печатью. B получает те же семантические и байтовые проверки; продуктовый helper допустим, если он проще и не скрывает предметные правила. Сравнить смысловые места правки, новые понятия, размер, startup, время записи/чтения и память на N=10/100/1000 записей с запасом не менее 2× до объявленного лимита на N=1000 (P8/P23). Испытать минимальные поддерживаемые Node 20.19.0 и 22.12.0; объявить выбранный механизм, зафиксированные зависимости и точный способ доставки до массовой замены writers.

Физическая запись принадлежит benchmark harness, не runtime приложения. Writer формирует новый файл в явном временном каталоге, проверяет полный результат и атомарно фиксирует его; запуск по умолчанию не перезаписывает старое свидетельство. Метаданные о host/версии не являются доказательством запуска; отчёт указывает действительную команду, cwd, SHA, выбранное/исполненное/пропущенное и PASS/FAIL/NOT RUN. Никакой benchmark output не добавлять в tool-required allowlist (P11/P17).
