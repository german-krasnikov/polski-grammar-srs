## Первый узкий срез: профиль языка

В проектном `CONSTRUCT LANGUAGE_PROFILE` используется та же проверенная форма `PATTERN ... <body:text>` и `DECLARE`, что у `SKILL`/`FEATURE`; `SURFACE language-profile` связывает ровно одну запись в каждом языковом файле. **NEW** `language-profile-types.program` объявляет:

```text
TYPE AnswerPolicy = enum(typed)
TYPE LanguageProfile = record{code:text,usesFeatures:list<text>,case:list<text>,answerPolicy:AnswerPolicy}
```

Типизированная запись en начинается как `LANGUAGE_PROFILE {code: en usesFeatures: [Case Number Person Tense Polarity Mood Aspect] case: [Subj Obj In With To About Of] answerPolicy: typed}`; pl отличается отсутствием `Aspect` и `case: [Nom Gen Dat Acc Inst Loc Voc]`. Это литерал **Biome**, а не документ JSON. Код языка и порядок массивов остаются значениями автора. `schemaVersion` — версия старого wire-документа, в новой DSL-семантике не дублируется; версия конструкции/manifest фиксирует новый контракт. Старый `$comment` остаётся объяснением в документации (`morphology-notes.md`/план), не полем runtime. English `Case` здесь означает семантическую роль; pl — падеж. `answerPolicy=typed` пока единственное принятое значение; новую политику нельзя добавить как неиспользуемый enum без требования.

Проектный `readLanguageProfile` (**NEW** `scripts/nj03/language-profile/validate.mjs`) вызывает публичные `core.parseDefinitions`, `core.parseSurface`, `core.readProgramTypes`, `core.readLocatedExprValueResult` из уже закреплённого NJ02 compiler API. Он сохраняет расположение каждого элемента списка, отклоняет несовпадение `code` с директорией, пустой/повторный `usesFeatures`, ключ вне валидированного `CoreCatalog.features`, пустой/повторный `case`, значение Case вне валидированного Core `FEATURE Case`, и отсутствие `Case` в `usesFeatures`. **Не** копирует глобальный список ключей или допустимых значений. Возвращает `LanguageProfile` и `Map`/`Set` для проверок как производные значения одного IR; принтер сохраняет авторский порядок. Точное первое место для повторного элемента — его второй токен, для неизвестного — сам токен. Регистр, Unicode, отсутствие/null/пустой список не нормализуются молча.

Нужная отрицательная граница: если в Core добавлен новый FEATURE, запись en/pl не получает его автоматически. Если skill ссылается на него до включения в `usesFeatures`, ошибка остаётся на `fixed.<key>`/`focus.feature`; после включения ссылка разрешается только при допустимом значении Core. Если Core удаляет Case/его значение, профиль отказывает до проверки навыков. Совместить этот контроль с уже запланированными двумя случаями [NJ03FeatureTypeSingleAuthorityPlan.md](NJ03FeatureTypeSingleAuthorityPlan.md), не заводя вторые независимые ожидаемые строки с иным смыслом.

## Лексикон: типы и границы срезов

Минимум для семантики 32 навыков — ordered noun IDs и пять польских родов. Полный no-JSON продукт требует **все** лексические семейства; нельзя назвать заменой `lexicon.json` генерат только из существительных. Сначала выполнить отдельно измеряемый [noun/form vertical slice](NJ03NounFormsVerticalSlice.md): `NOUN` с `TYPE PlNoun = record{id:text,lemma:text,meaning:text,gender:text,forms:PlNumbers}` / `TYPE EnNoun = record{id:text,lemma:text,meaning:text,forms:EnNumbers}`, `TYPE PlNumbers = record{sg:PlCases,pl:PlCases}`, `TYPE PlCases = record{nom:text,gen:text,dat:text,acc:text,inst:text,loc:text,voc:text}`, `TYPE EnNumbers = record{sg:text,pl:text}`. Допустимое множество польских родов выводится из проверенных `PlNoun.gender`, а независимый 14-row оракул фиксирует все пять существующих значений; не нужна вторая ручная таблица или Kotlin enum. Отсутствие английского `gender` отличается от `null`; для этих двух языков все перечисленные формы обязательны и непусты. Этот срез уже имеет независимые 14+14 и 196+28 форм в [NJ03SeedsNounsChains.cases](NJ03SeedsNounsChains.cases) и [NJ03EnglishNouns.cases](NJ03EnglishNouns.cases). Пока остальные семейства старого лексикона активны, noun-catalog остаётся изолированным кандидатом, а не второй live-authority.

Следующие **NEW**, проектные `ADJECTIVE`, `VERB`, `PRONOUN`, `POSSESSIVE`, `FUTURE_AUXILIARY`, `STEM_ALTERNATION` факты используют один общий `lexicon.construct` с typed body и **раздельные named types по форме языка**, а не `data`/произвольный словарь. В Core вложенный `record{...}` требует собственного канонического `TYPE`, поэтому каждую ниже названную форму объявить отдельно: `EnInvariantForms`, `PlGenderCases`, `PlAdjectiveForms`, `PlPersonForm`, `PlPresent`, `PlPastStem`, `EnRoleForms`, `PlPossessiveForms`, `PlFutureAuxiliaryForms`. `PlPersonForm = record{person:text,value:text}`; `PlPresent = record{sg:list<PlPersonForm>,pl:list<PlPersonForm>}`. Core не допускает цифровые имена полей `record`, поэтому `"1"/"2"/"3"` становятся значениями `person`, с проверкой полноты и уникальности. Конкретные смысловые контракты для blueprint разработчика:

| Факт / тип | Обязательная форма и старый объём | Инвариант валидатора |
| --- | --- | --- |

Литерал `m-personal` — значение `gender`, а не неподдерживаемое имя поля типа. |
| `EnVerb` | `id,lemma,meaning,present3sg:text` и optional `past,pastParticiple,ing,presentSg1,presentPl,pastPl`; 10 записей. | Отдельно зафиксировать три реально существующих варианта: обычный полный, `be` с дополнительными формами, `will` только с `present3sg`. Optional omission и explicit null не схлопывать. |
| `PlVerb` | `id,lemma,meaning,aspect:text,futureType:text,present:PlPresent,pastStem:PlPastStem,perfectivePair:optional<text>`; `PlPastStem=record{m:text,f:text,n:text,mp:text,np:text}`; 11 записей. | `aspect ∈ {imperfective,perfective}` и `futureType ∈ {compound,present}` проверяются проектом один раз; ссылка `perfectivePair` разрешается по тем же verb IDs. | `EnPronoun` / `PlPronoun` | `id` и `forms`: en `EnRoleForms=record{Subj:text,Obj:text}` (7), pl `PlCases` (9). | Порядок старых object entries фиксируется в ordered фактах, не сортируется. Английская матрица получает этот же каталог. |

Перед массовой транскрипцией выполнить небольшой Core-reader probe выбранных nested record/list, variant omission/null и исходных spans. `TYPE` объявления могут лежать в shared `lexicon-types.program` с двумя named root types; если нынешний Core parent registry это не позволяет без ослабления, оставить два узких языковых type-файла и одну project-композицию. Оба варианта сохраняют одну авторскую identity лексемы и один каталог значений. Старые schema `additionalProperties:true` не являются разрешением для нового typed источника выкинуть неизвестное старое поле: перед переключением перечислить все реальные поля и отклонить неотображённое. Общее `record`/список — форма фактов, а не ручной JSON под другим расширением.

Отдельная стадия покрывает старые `forms.generated.json`, seeds/recipes/prepositions, pair copy/styles/lifehacks/editorial data и `course.json`/`pair.json` по [NoJsonFullPortPlan.md](NoJsonFullPortPlan.md). Наличие typed лексикона не даёт права оставлять эти источники в принятом приложении или конвертировать его обратно в JSON для `CoursePack`. Новые fact surfaces/типовые файлы проектные; общий Core и новая грамматика не нужны, пока microprobe и P8 не покажут конкретный пробел на двух потребителях.

После DSL edits: из compiler `implementations/typescript` выполнить `npx biome check changed`; для `not checked` назвать и выполнить собственные `Core` surface/type/examples проверки. Продукт: generator `--check`, source/semantic/mutation suites, Gradle selected `:shared:desktopTest`, затем JS/Wasm и необходимые host compiler/browser/Android/iOS проверки на pin/revision без параллельных Gradle; `gate:all` компилятора перед его merge и финальный быстрый gate — отдельные обязательства. В квитанции указать cwd, SHA, inputs/output hashes, selected/executed/skipped/failed, PASS/FAIL/NOT RUN отдельно для parser, generation, Kotlin unit, браузера и устройств. Старый JSON scanner должен достичь нуля application-owned active paths; tool-required exact-path exceptions фиксируются отдельно. Build, ссылка на тест или 32 typed skill values сами по себе не означают live/no-JSON PASS.

## Измерение и условия остановки

Перед массовым переносом каждого следующего семейства сравнить существующий typed Biome reader + project construct/Kotlin printer с **исполненным** маленьким Kotlin build-time helper над одним читаемым не-JSON text source. Одинаковые 2 профиля/28 noun rows и затем семейство, те же ссылочные/variant проверки, точные diagnostics, freshness и реальный Kotlin consumer. Один раз считать цену конструкта/шаблона, отдельно — маргинальную правку формы/lexeme/языка, authored/generated LOC, места ручного решения, дефекты, review time, compile/startup/runtime. P23 для N=10/100/1000 использует реальные reader → validator → printer → Kotlin consumer, чередующиеся CPU выборки, неизменённые лимиты/счётчик, ≥2× запас на N=1000. Noun-specific бюджет уже задан в [NJ03NounFormsP23Blueprint.md](NJ03NounFormsP23Blueprint.md); для профиля и других лексических семейств зафиксировать свой workload/пределы **до** просмотра результатов. Если форма списков существенно дороже nested typed record или helper при равных гарантиях, пересмотреть проектный construct/тип до транскрипции; новую Core возможность добавлять только при общем пробеле и втором потребителе.

Остановить promotion при двух live-authorities, старом JSON input/fallback в build или Kotlin, потерянном поле/варианте/порядке/null/Unicode, `TYPE` с копией registry feature names, Kotlin printer с предметным default, локальном parser вместо Core, stale output, неисполненном host gate, изменении frozen expectations без отдельного требования либо непроверяемом compiler pin. За этой границей остаются прочие NJ03 content slices и application-wide FP/NJ gates.
