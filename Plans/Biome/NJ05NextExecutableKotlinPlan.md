## Product boundary and verified starting point

Kotlin Multiplatform is the sole target application and data owner. The former `src/textwire/*.ts`, `tests/textwire/*.test.ts` and paired TS/Kotlin product-codec instructions in the historical [TextWireExperimentBlueprint.md](TextWireExperimentBlueprint.md) are superseded. Existing React/TypeScript source and runs may identify historical behavior; an isolated compiler portability comparator may test a general Biome backend, but neither is an NJ05 product codec, an active app oracle, or a required runtime. The next mechanical A/C implementation, if admitted, belongs in **NEW** `kotlin/shared/src/commonMain/kotlin/polski/textwire/`, consumed by Kotlin/Swift-host adapters. No new DSL syntax is needed for framing, UTF-8, UTF-16, SHA-256 or storage (P4/P8).

The test-only inputs `tests/fixtures/textwire/{legacy-boundary,numeric-admission}.cases` have exact whole-file seals in `legacy-admission.sha256`: `e3550c49fc7ab34ef4ae08d751a51c9705a47839d801f84a804cb4387914d5d9` and `546ed10dcd69c4e2b4fb95a4194c383304aa0c8151415d1274204e803e692e11`. `positive.cases`, `negative.cases`, `document.cases`, `transaction.cases` have exact hashes in `corpus.sha256`. Twelve A and twelve C positive byte oracles and N16 A/C bytes are frozen; B bytes and N26 numeric bounds are not. **Do not edit any of these six `.cases` files or two hash files in the admission/prototype slice.** A later independent N26 requirements commit may change `negative.cases` and `corpus.sha256` with its own review and reason. The 10 MB accepted progress examples already imply A lengths 10,000,112/10,196,726 and C lengths 40,000,022/39,214,145; these are lower floors from pure arithmetic, not proposed caps or P23 headroom.

The old Kotlin codec is also the live JSON writer today: `ProgressCodec.decode/encodeLegacyV1` in `kotlin/shared/src/commonMain/kotlin/polski/progress/ProgressCodec.kt`, `VocabularyCodec.decode/encode` and `VocabularySession.start/importJson/exportJson/commit` in `.../vocabulary/{VocabularyDocument,VocabularySession}.kt`, and `UserPreferencesCodec.decode/encode/peekTargetNative` in `.../preferences/UserPreferencesCodec.kt`. `RawProgressRepository.save/migrateLegacy` in `.../progress/ProgressRepository.kt` writes JSON preview and compares JSON readback; `TrainingStore` can trigger the fresh save. This is the known old baseline, **not** an accepted no-JSON path. Existing tests that call `encodeLegacyV1`, `VocabularyCodec.encode` or `UserPreferencesCodec.encode` can remain historical behavior checks, but must not manufacture new NJ05 legacy oracle bytes or be counted as zero-JSON evidence.

The accepted exception is exact-path, byte-hashed, **input-only old-user JSON** for a one-time, read-only migration decoder and its isolated tests. The new app must never serialize JSON for a save, preview, backup, receipt, export, download, snapshot or test-generated acceptance artifact. A historical old-host admission probe may invoke the old writer only in disposable test storage to characterize its behavior; label it historical, compare exact old-file bytes and destroy the store. Candidate migration tests instead present frozen legacy input bytes to a read-only decoder and assert no JSON write at every failure point. Tool-required configuration JSON is separately inventoried by path and role; it is not permission for app data.

The first two recreate old input *in memory* and compare length/hash; the seal check must reject its deliberate byte/ledger mutations. Record each command result, not an inherited PASS. The existing generated test ledger in `kotlin/shared/build.gradle.kts` derives from the two sealed files; `LegacyBoundaryAdmissionTest`, `LegacyAdmissionDigestTest` and `macosTest/.../LegacyHostSizeAdmissionTest` are the only executed historical scopes presently documented. **E2 — freeze representability before size arithmetic.** The independent tester authors **NEW** `tests/fixtures/textwire/legacy-representability.cases` with expected ordered typed trees/code units and exact old input references, separate from candidate output. **E3 — calculate, then run only test-only mechanical prototypes.** After E1/E2 independent review, extend the existing pure arithmetic checker `tests/fixtures/textwire/check_numeric_sizes.py` or add a same-owner checker for accepted trees. **E4 — provisional resource and P8/P23 measurement.** On the same independently accepted trees, alternate A/C order and use N=10/100/1000 *actual progress/vocabulary/preferences record shapes* through the test-only projection/prototype, plus the largest admitted old trees. Establish each required host's fixed budget/quota from a real consumer or an explicit product requirement **before** declaring ≥2× headroom at N=1000. Do not raise a budget to make an arm pass. Static token counts are not LLM use. Compare the correctly layered small native A/C helpers with equal guarantees; no DSL feature is justified by a line count or by the isolated TS historical comparator. If C's approximately 40 MB examples plus backup/readback cannot fit a required host with headroom, mark C NO-GO or seek a reviewed representation change; do not trim the old tree.

**E5 — independent N26 freeze, then a separate production handoff.** Document/host owners first decide one shared semantic depth/row/string-unit ceiling and each remaining arm's physical byte ceiling from E1–E4, including an explicit policy for no-fixed-limit paths. The independent tester then freezes exact-at and valid-tree `+1` cases for each dimension, the digest/final LF and error `Bound`, with a byte recipe/hash and no other limit violated. If exact `cap+1` is arithmetically impossible, prove and freeze the smallest valid excess. Review old admission, representability, numerical headroom and all revised `negative.cases`/`corpus.sha256` **before** a developer receives a production task. Only then may A/C code enter `commonMain` and a later NJ05 slice own domain mapping, new text repositories and cross-host import/export. `document.cases`, `transaction.cases`, receipt grammar, cleanup/old-tab policy and Apple typed snapshots remain separate NJ05/NJ06 gates; a generic codec PASS cannot close them.

## Stop, evidence and next role

Stop this slice on any changed frozen input/hash or expectation derived from candidate output; a previously accepted old file overwritten, deleted or re-serialized as JSON; unrepresentable retained value without reviewed recovery; unjustified finite cap on an unbounded entrypoint; missing/empty target selection presented as PASS; use of Skiko/DOM/compiler output as storage-host proof; inadequate P23 headroom; or any new app-owned JSON writer/artifact. A historical old-host test write in deleted test storage must be reported as such and cannot be used for the new candidate's no-JSON result. Do not weaken current tests or infer proof from linked cases.

The next handoff is to an **independent tester** for E0–E2 frozen input, per-entrypoint host admission and representability, followed by read-only review. Only after that reviewed evidence should an isolated developer receive E3/E4 test-only prototypes. Each receipt includes product SHA, input and expected-tree hashes, target/browser/device, command/cwd, selected/executed/skipped/failed counts, exact old/new/backup bytes or hashes, limits, resource measurements and PASS/FAIL/NOT RUN by case. `git diff --check` and Markdown link checks validate this plan; application suites and host results are **NOT RUN** by its author.
