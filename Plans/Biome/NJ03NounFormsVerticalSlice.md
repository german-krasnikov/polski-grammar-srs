## DSL shape and layer choice

Proposed **NEW** `courses/lang/nouns.construct` declares a project `NOUN <body:text>` surface and independently authored examples. Proposed **NEW** `courses/lang/pl/nouns.core-data` and `courses/lang/en/nouns.core-data` contain one `NOUN {id: ... lemma: ... meaning: ... forms: ...}` record per old row, in old order. The shared declaration is a project pattern for 28 repeated records, not new compiler syntax. Proposed **NEW** `courses/lang/nouns-types.program` (or two narrow language-specific type declarations if the current Core type system cannot model their sum without weakening) checks `PlNoun = record{id:text,lemma:text,meaning:text,gender:text,forms:record{sg:Cases,pl:Cases}}` and `EnNoun = record{id:text,lemma:text,meaning:text,forms:record{sg:text,pl:text}}`; `Cases` has exactly `nom,gen,dat,acc,inst,loc,voc`. Type/shape checks use Kit/Core located records, not a project JSON parser or manual token walk. The project validator adds nonempty/unique IDs, legal five-way Polish gender, exact required form keys, nonempty strings, English absence of gender, and references from the already frozen 32 skills/seeds when those are typed. It reports source file, physical UTF-16 line/column and offending leaf or containing record for a missing field. It returns diagnostics; no training-state mutation.

The source **does not** include a synthesized flat forms table, a gender default for English, or a separate hand-authored `nounId → label` map. In the validated IR, absence of English `gender` is `Absent`, not `null`; all named noun fields/forms are required, so explicit `null` is rejected. An empty noun list is invalid for these two accepted packs; an empty form string is invalid, while identical values across cases are valid (e.g. Polish inanimate accusative). List/record order is preserved through Kotlin generation. A generic nullable `gender: String?` may be used only at a deliberately lossy final consumer boundary after validation, never as the source contract.

Shared `.given PORTS FROM .contract`/`LET`/`$name` is useful for repeated Logic and executable test setup, but this slice has static noun facts and no repeated decision context. Do not create a second fixture-variable dictionary merely to exercise that feature. If noun-reference decisions later appear in Logic, derive fact names and typed queries from one contract and keep the independent noun expectations in `.cases`/`.examples`.

Closest precedents inspected: compiler `packages/core/tests/fixtures/slots.construct` uses `HEAD`/`ITEM`, `UNIQUE` and `ref(...)`; `tests/tooling/kotlin-program/fixtures/definitions/records.construct` uses project `CONSTRUCT`/`TEMPLATE kt`; `packages/core/tests/expr-materialize.sources` exercises `record{...}` and `optional<...>`; the **ongoing isolated NJ03 candidate**, not this baseline, uses `curriculum.construct`/`curriculum-types.program` with one project `SKILL { ... }` body and typed Core reader. Reuse these mechanisms and the NJ02 located reader/printer after their own gates pass. No new shared `NOUN` language keyword or Polish grammar algorithm belongs in compiler Core. If literal shape/type/diagnostic cannot be expressed, demonstrate the general gap on a second consumer before editing Core (P10/P13). Kotlin printer owns spelling/escaping and static source emission; a small native build-time helper may flatten the already validated noun paradigms to `FeatureBundle` keys. That helper may not choose forms, default missing facts or maintain another noun table.
