## Renderer decision

The initial pure Compose canvas failed the browser gate: the textbox had no accessible name, the table had no table/row/header roles, and Playwright pointer clicks on Compose accessibility-overlay buttons were intercepted by the canvas. `HtmlElementView` compiled on both JS and Wasm and resolved these observed desktop blockers with real DOM text, input, actions and table. Enter respects `isComposing`; Shift+Enter remains a newline. The shared Kotlin state is still the only owner of reveal/rating/input state, with browser code limited to DOM events and isolated preview persistence. A separate Kotlin/JS DOM presenter was not needed for this measured slice.

This is a **provisional web rendering strategy**, not approval of the full Compose UI port. Physical mobile keyboard/IME, screen-reader reading order, zoom and slow-network behavior must pass before the stage-2 acceptance gate. If `HtmlElementView` fails one of those required hosts, use a thin DOM host for the affected controls/table while keeping the Kotlin state contract; return that architecture decision before the full UI port.
