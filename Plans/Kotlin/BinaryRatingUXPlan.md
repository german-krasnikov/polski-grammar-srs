# Две оценки, мобильные свайпы и обучающий оборот карточки

Дата: 2026-09-23. Статус: код реализован и проверен на виртуальных устройствах; физические устройства, assistive technology и независимый агентский review остаются открытыми. Это продуктовая UX-задача поверх существующего переноса; она не закрывает формальные gate [основного плана](Plan.md). Текущие React, Kotlin web, Compose Desktop, Android Compose и SwiftUI используют один FSRS-совместимый формат прогресса. Пользователь выбрал две оценки и задал направления жестов: влево — «Повторить», вправо — «Вспомнил». При неверном печатном ответе приложение показывает ошибку, но оценку выбирает пользователь.

## Архитектурное решение

- Видимые оценки: «Повторить» → существующий `Rating.Again`/`again` (wire `1`), «Вспомнил» → `Rating.Good`/`good` (wire `3`). `Hard`/`Easy`, параметры FSRS, `SchedulePreview`, reducer, schema v1, исторические карточки и экспорт остаются читаемыми и не переписываются. Это новая UI-политика, а не новый scheduler. Существующие интервалы для двух действий берутся из того же preview, что и review.
- `TrainingStore` остаётся единственным владельцем перехода и записи. Кнопка, клавиша и свайп отправляют тот же `AppAction.Rate(exercise.id, rating)`; повторное событие старой карточки отклоняется. Swift bridge продолжает принимать `"Again"`/`"Good"` через команду `rate`. React baseline обновляется как текущий продукт только вместе с локальными Kotlin-host UI, но pinned fixtures остаются историческим эталоном FSRS.
- На печатной карточке `evaluation.correct` продолжает отвечать за статистику точности, а выбранная пользователем оценка — за FSRS. Даже при неверном тексте обе кнопки остаются доступны; экран ясно разделяет «ответ не совпал» и «когда повторить». Автоматического `Again`, запрета `Good` или скрытого преобразования оценки нет.
- На Android и iOS свайп активен **только после раскрытия** на области выбора оценки. Влево отправляет `Again`, вправо `Good`; вертикальная прокрутка, системный edge-back, выделение текста, кнопки, клавиатура и жесты assistive technology остаются рабочими. Порог и преобладание горизонтального движения проверяются на эмуляторе/симуляторе; касание без порога ничего не оценивает. Один жест — максимум один review. Обе видимые кнопки сохраняются как равноправная доступная альтернатива свайпу. На web/Desktop жест не навязывается.
- После ответа читаемая иерархия: эталон, сравнение печатного ответа, «Что изменилось» с **новой формой** (`change.to`) жирным и изменёнными **окончаниями другим цветом и подчёркиванием**, отдельная выделенная карточка «Запомни» с формулой жирным и пояснением, затем две оценки с интервалами. Для надёжной подсветки сопоставлять слова по позиции и красить лишь короткий новый суффикс после общего начала; при замене слова, перестройке основы или неоднозначном выравнивании не угадывать окончание. Использовать существующие `Skill.formula`, `Exercise.changes` и `Exercise.explanation`; не вставлять HTML из данных, не дублировать правила по платформам и не менять грамматические строки. Цвет дополняется подчёркиванием. Скрытый до reveal ответ не попадает в accessibility tree.
- Мобильная подсказка в жестовой зоне показывает направление после reveal; короткие названия на кнопках не ломаются при увеличенном шрифте. Системные типографика, Dynamic Type, font scale, темы и reduced motion сохраняются; оценка/сохранение не зависят от конца анимации. Клавиатурные сокращения на web/Desktop становятся `1`/`2`, прежние `3`/`4` не должны скрыто оценивать карточку; в полях ввода они не срабатывают.

## Последовательность и критерии

1. **Зафиксировать контракт.** Снять текущие видимые тексты/shortcut/ratings на пяти hosts и текущие тесты; отметить пользовательское исключение для печатной ошибки. Выход: этот документ и проверенный список точек входа. Приёмка BR-01: описание оценки, прогресса и свайпа не противоречит коду/FSRS.
2. **Тесты поведения до правки.** Добавить тесты для двух видимых оценок и manual choice при неверном печатном ответе; проверить, что старый `Hard`/`Easy` JSON по-прежнему декодируется. Для свайпа добавить проверку направления, порога, невертикальности и защиты от двойного dispatch там, где target runner умеет исполнять жест. Зафиксировать наблюдаемый RED по поведению, setup failures отдельно. Приёмка BR-02: 1/2 выберут Again/Good, 3/4 не оценят; BR-03: typed wrong допускает оба решения без подмены; BR-04: legacy progress не меняется при загрузке.
3. **Обновить видимые оценки на всех hosts.** React `src/ui/App.tsx`, Kotlin web `TrainingWebApp.kt`, Compose Desktop `TrainingScreen.kt`, Android `AndroidTrainingScreen.kt`, SwiftUI `PolskiGrammarApp.swift`. Заменить только UI-кнопки/подписи/shortcuts, оставить domain enum/wire. Приёмка BR-05: preview совпадает с фактической датой после нажатия на каждом доступном target; быстрый повторный ввод даёт один review.
4. **Улучшить оборот карточки и правила.** На каждом host выделить формулу отдельной семантической зоной; `change.to` — жирным, а надёжно обнаруженные окончания — контрастным цветом с подчёркиванием; пояснение остаётся полностью читаемым. Печатное сравнение явно показывает исходный ввод и эталон, без обещания автоматической оценки. Проверить длинные русские/польские строки, 320 px, крупный шрифт, светлую/тёмную тему и экранную клавиатуру. Приёмка BR-06: главная учебная форма заметна и без цвета, текст не обрезан, старое правило не переписано.
5. **Добавить нативные свайпы.** Android — локальный horizontal drag detector на блоке оценок без захвата вертикальной прокрутки; iOS — локальный `DragGesture` на той же зоне, без перехвата системного back/текста. Фаза/ID карточки и порог проверяются до dispatch. Кнопки остаются. Приёмка BR-07: левый/правый свайп выбирают нужную оценку ровно один раз; короткий/вертикальный/до-reveal/после смены карточки не оценивают; scroll, back и VoiceOver/TalkBack не теряются.
6. **Проверить и довести UX.** Shared JS/Wasm/native tests по затронутому поведению, React unit/browser, Kotlin web Playwright на Wasm и JS, Compose Desktop, Android unit/UI на API 35 emulator, iPhone/iPad Simulator XCTest; физические устройства/AT — отдельные PASS/NOT RUN. Проверить ручной ввод при ошибке, условие большого текста, Reduce Motion, повторное действие и persistence/reload. Исправления возвращать разработчику, после чего повторить упавшие/затронутые проверки. Приёмка BR-08: нет новых Critical/Major, доказательства раздельны по target; старые fixture FSRS/progress остаются PASS.
7. **Независимые Tester и Reviewer, документация.** Tester повторяет BR-01–08 по фактическому diff и даёт PASS/FAIL/NOT RUN; Reviewer оценивает контракт, lifecycle/gesture conflicts, доступность и evidence без правок. При блокерах вернуться к шагу 3/5, затем повторить нужные проверки. Обновить README/product contract и платформенные отчёты, указать изменение UX и сохранение данных. Публикация/коммит не следуют автоматически.

## Проверенные основания

`ReviewReducer` использует выбранный rating для scheduler и отдельно `typedCorrect` для статистики; `Scheduler.Rating` сохраняет четыре wire-значения. Android и iOS уже имеют собственные нативные экраны; web использует DOM host, Desktop — Compose JVM. [Anki manual](https://docs.ankiweb.net/studying.html) допускает Again/Good; [FSRS tutorial](https://github.com/open-spaced-repetition/fsrs4anki/blob/main/docs/tutorial.md) подтверждает работоспособность такого режима. [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/gestures/) требует альтернативу жесту и избегать конфликта с системными жестами; [Android Compose gestures](https://developer.android.com/develop/ui/compose/touch-input/pointer-input/understand-gestures) рекомендует высокоуровневые controls/gestures прежде raw pointer input.
