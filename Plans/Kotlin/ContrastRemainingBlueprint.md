## Scope and consumers

The first incomplete group is `reference.russianSupport.rows` (`accusative`, `instrumental`, `locative`, `possessive`) in `courses/pl-ru/course.json`: React `GrammarTables.tsx`, Kotlin `MatrixWeb.kt`, Desktop `MatrixScreen.kt`, Android `AndroidMatrixScreen.kt`, and iOS `IosSnapshot.kt` → `PolskiGrammarApp.swift` all show the row's Polish construction without a labelled Polish baseline. Its Russian cue is a semantic prompt, **not** the `from` side of a Polish form comparison. The `possessive` construction contains alternatives, so a single prefix comparison is unsafe. Current `reference.systemCards` and `reference.pipeline` include arrows that may describe an operation or more than one transition; retain their explanatory text and annotate only explicitly authored, independently labelled Polish pairs.

Next incomplete group: native generated rows. React `CaseReference`/`GrammarTables` and Kotlin `renderCaseReferenceWeb`/`renderCases`/`renderVerbs`/`renderPronouns` already pass a baseline into `FormContrast` or `matrixContrast`. Desktop `MatrixTable` renders raw strings for case reference, seven-case phrase/sentence, seven-noun comparison, nine verb-subject rows, personal pronouns, and possessives. Android renders those groups as plain `Text`; iOS `matrixSnapshot` exports raw `cases`, `comparison`, `verbsRows`, `pronouns`, `possessives`, and SwiftUI shows raw values. Existing chain, male accusative, tense, and aspect comparisons already use labelled pairs on native hosts; preserve them and close cue/style gaps there, without rebuilding their content.

## Public contract

Use one display-only pair model, with no mutation or async work. Proposed **NEW** common presentation type `ContrastPair(from: String, to: String, beforeParts: List<EndingPart>, afterParts: List<EndingPart>)` in `kotlin/shared/src/commonMain/kotlin/polski/presentation/EndingHighlight.kt`, and a corresponding TS shape in `src/ui/endingHighlight.ts`. Exact names may follow existing conventions, but consumers must receive the literal `from` and `to` and a lossless segmentation for each side. Generated grammar forms use the existing `changeHighlightParts` as a conservative display fallback. Authored static examples use explicit segment arrays from the course pack, never the fallback for ambiguity. For every pair: concatenated before/after segment text equals `from`/`to` byte-for-byte in JS and code-point-for-code-point in Kotlin; order, spaces, case and punctuation remain unchanged. Reject invalid authored metadata at pack validation and Kotlin load; an invalid or unmatched sentence fragment renders its original plain text, without inserted words or colored guesses. A pair with no reliable changed span may still show fully labelled plain forms.

For `reference.russianSupport.rows`, add **NEW** optional `comparisons` containing ordered Polish `from`, `to`, and explicit segment arrays. Use existing Polish words/forms and row meaning; preserve all existing `cue`, host copy, `mobileLine`, and row order. `possessive` must use separate labelled comparisons for alternatives or mark each whole alternative, never compare a slash-separated group as a suffix. Do not promote translation, pipeline tokens (`widzę → Biernik`), or rule prose into a morphological pair. The four support rows require at least one valid concrete Polish pair each. If the editor cannot supply an accurate Polish baseline for a row, keep the row unchanged and leave that acceptance case open; do not invent a form in UI code.

The visual contract is visible text labels “Было” and “Стало” plus an arrow for each pair. Old fragments use the existing error/red family with a distinguishable dashed underline; new fragments use the existing accent family with a solid underline. Full replacements and insertions identify the whole affected word/group; only trustworthy short aligned suffixes may appear as endings. For identical forms, retain the pair and labels without implying a changed morpheme. DOM exposes a single meaningful accessible name `Было: … Стало: …`, hides duplicated decorative children, and keeps `lang=pl` on Polish content. Compose and SwiftUI expose full, ordered words and labels in semantics; the marked fragment is decoration and must not alter spoken text. Text wraps or the table scrolls within its labelled container at 320 CSS px and large native text sizes.

## Decisions and tradeoffs

Store explicit segments only for authored static examples where grammar cannot safely infer a baseline or focus. Generated rows already have stable grammar factories and a known nominative/lemma/pronoun baseline; compute them at render time as current web does. Avoid a universal parser for arrows in rule copy. For support rows, a new pair is additional teaching annotation, not a replacement for their existing Russian cue or host-specific prose. Reuse `EndingPart` internally, but never serialize Kotlin offsets across TS/Swift: explicit text segments avoid UTF-16/grapheme indexing disagreements around diacritics.

## Verification and acceptance

Implementation should start with focused RED tests, then GREEN, on the exact missing behavior. Tester owns independent browser acceptance in `tests/browser/kotlin-parity-matrix.spec.ts` or a separate test file; coordinate before editing that active suite. Developer owns pure/schema/UI unit tests and production fixes. Suggested cases:

1. **C1 static support:** all four authored support rows contain a visible, labelled Polish pair on React and Kotlin DOM; Russian cue and existing construction/check/mobile copy remain literal and ordered. `possessive` alternatives have independent safe focus or whole-group marking. Desktop, Android, iOS display the same authored pair(s).
2. **C2 native generated rows:** seven case-reference forms; seven case phrase and sentence rows; 7×7 noun comparison for both numbers; all nine subjects × three tenses for each selectable verb/gender; pronoun context rows; and possessive rows show the row-specific baseline and result. Preserve absent aspect present as an absence message, not a fabricated pair. Existing chain/tense/aspect/male accusative comparisons remain readable.
3. **C3 segment safety:** exact recomposition for Polish diacritics and punctuation; `moja piękna żona → moją piękną żonę`, `mojej → ich`, insertion of `Nie`, multiple changes, a whole-word boundary (`ona` inside `żona` must not match), and an invalid/missing segment. No text change or incorrect suffix claim is accepted. Reject malformed authored segment metadata with a field path and nonzero validator exit; runtime Kotlin must fail safely before displaying malformed built-in metadata.
4. **C4 accessibility/layout:** text labels and distinct dashed/solid underlines in light/dark browser and native system themes; DOM accessible names contain both full forms once; Compose/SwiftUI semantics read them in order. Check 320 px browser width, large text/native narrow simulator, and contained horizontal scrolling for wide tables. Before training reveal, no new form or answer appears; after reveal both sides are present. No change to FSRS/progress fixtures.

Run affected React unit/typecheck/build; Kotlin common tests for JVM/JS/Wasm and iOS snapshot tests, then targeted Desktop UI, Android emulator, iPhone/iPad Simulator and React/Kotlin Web Playwright in Chromium/Firefox/WebKit on JS/Wasm.
