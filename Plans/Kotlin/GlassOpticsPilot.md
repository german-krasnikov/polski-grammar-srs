# Module design: оптическая линза навигации (web и Android)

**Архив, 2026-09-25:** пилот отменён решением пользователя. Актуальный план — [PreGlassRollback.md](PreGlassRollback.md); ниже оставлены прежние условия эксперимента для истории.

Статус: дизайн-проход после визуального FAIL web-пилота, 2026-09-25. Выбор библиотек и основания — [GlassImplementationSelection.md](GlassImplementationSelection.md). Web Component 5.3.0 уже self-hosted; bounded surfaces, ambient baseline и контролируемая текстура функционально работают, но их вид отклонён в независимой оценке Luna. Предварительный benchmark не заменяет визуальную приёмку. Оптический режим остаётся **OFF по умолчанию** до прохождения gates ниже; Android-пилот ведётся отдельно.

## Scope and consumers

Проверить **одну** компактную линзу основной навигации на каждом host: `simple-liquid-glass` 5.3.0 Web Component в Kotlin DOM JS/Wasm и `io.github.kyant0:backdrop:2.0.1` в Android Compose. iPhone/iPad/Mac продолжают использовать штатный SwiftUI material. Учебные карточки, поля, таблицы и отдельные кнопки пока сохраняют текущий стиль. Оптический пилот меняет только presentation: `TrainingStore`, FSRS, прогресс, JSON, маршруты и семантика кнопок не меняются.

В web требуется **ограниченный срез реального учебного экрана под fixed bottom nav**: положение, цвет и кромки текущих карточек/таблиц должны меняться вместе с route и scroll. Декоративные полосы этого не дают: снимки [ON](artifacts/glass-optics/web/webkit-dark-on-390.png) и [OFF](artifacts/glass-optics/web/webkit-dark-off-390.png) почти не различаются по содержательному фону. Нельзя и указывать весь `.training-web-host` как источник: проба [Chromium](artifacts/glass-library-review/probe-whole-host-chromium.png)/[WebKit](artifacts/glass-library-review/probe-whole-host-webkit.png) показала нечитаемые копии текста и кнопок при `strength=0.16`. Поэтому срез сохраняет геометрию **реальных видимых поверхностей**, но не содержит glyphs, controls и shadow DOM линзы. На начальном 390×844 экране карточка заканчивается выше нижней панели: в отсутствие пересечения источник должен содержать тихую копию **фоновой ткани host**, иначе ON остаётся CSS fallback именно на первом кадре.

## Public contract

В домене общего API не появляется. Host-local контракт пилота:

| Хост | Входы | Наблюдаемый результат | Ошибка / выключение |
| --- | --- | --- | --- |
| Web `WebGlassNav` (EXISTING) + `WebGlassBackdropSlice` (EXISTING pilot) | стабильный DOM shell, текущий `WebRoute`, `navigate`, `glassTintPercent`, тема/контраст, фон host, видимые границы route surfaces и scroll/viewport | один `<liquid-glass>` над пятью обычными навигационными `<button>`; сохранённые `id=nav-…`, `aria-label`, selected/pressed и keyboard focus; sibling source по `backdrop-selector`, содержащий bounded ambient baseline и поверх него реальные surface shapes, когда они пересекают панель | CSS glass/непрозрачная панель той же геометрии при отсутствующем WebGL, неготовом capture, contrast/reduced transparency, context loss, длительном scroll или выключенном пилоте; route и кнопки работают всегда |
| Android `GlassNavigationBar` (**NEW**, имя условное) | `AppTab`, `onSelect`, `AndroidGlassAppearance`, наличие API 33+ и доступность эффекта | одна нижняя capsule-линза, под ней source без самозахвата, поверх неё прежние `NavigationBarItem` с Material semantics | существующий `NavigationBar`/`androidGlassColor` при API 24–32, high contrast, недоступном эффекте или выключенном пилоте; выбранная вкладка и insets те же |

Временный переключатель A/B задаётся только host-local build/debug параметром или тестовым URL-флагом; его не сохранять в `UserPreferencesV2` и не выдавать за настройку продукта. `glassTintPercent` продолжает управлять **плотностью цветной поверхности**, а не силой refraction. Вызовы `navigate`/`onSelect` происходят от нативной кнопки ровно один раз, без действия на окончание анимации.

## Components and dependencies

### Web (JS и Wasm)

Факты на 2026-09-25: `TrainingWebApp` в `kotlin/composeApp/src/webMain/kotlin/polski/ui/TrainingWebApp.kt` создаёт один `HtmlElementView`; `TrainingDomRenderer.render` сохраняет `.app` и `WebGlassNav`, пересоздавая header и `.route-content`. `.training-web-host` — scrolling owner. `WebGlassNav.kt` создаёт один `<liquid-glass>`, пять стабильных кнопок, fixed bottom placement до 600 CSS px и URL-gate `?glass-optics=on`; обычная загрузка/`off` задаёт `effect-mode="off"`. `WebGlassBackdropSlice.kt` уже проецирует видимые surface shapes и при их отсутствии захватывает ambient crop host (`data-slice=ambient`). Локальный asset `simple-liquid-glass-5.3.0.esm.js` подключён в `index.html`. Функциональные проверки и первый benchmark относятся к нынешней, визуально отклонённой композиции.

1. `kotlin/composeApp/src/webMain/kotlin/polski/ui/WebGlassBackdropSlice.kt`: сохранить текущий bounded viewport strip, ambient crop и проекцию **только пересекающихся** `.card`, `.matrix-section`, `.vocabulary-card`, `.vocabulary-catalog`, `.settings-panel`, `.settings-status` по `getBoundingClientRect`/computed surface styles. На первом 390×844 экране `data-slice=ambient` — валидный capture; при появлении пересекающейся карточки/таблицы её формы добавляются поверх того же baseline (`data-slice=surfaces`), без второго lens/context и без копирования текста, controls или длинного DOM. При превышении лимита shapes/candidates оставлять ambient baseline, не расширять HTML capture. Source остаётся коротким, `aria-hidden` и `pointer-events:none`. Текущий host-crop меняется вместе с CSS фоном; следующий проход ниже меняет саму фоновую композицию, а не модель source ownership.
   - Практическая разметка: постоянный `.glass-source-ambient` + отдельный контейнер `.glass-source-surfaces`; обновление формы очищает лишь второй. Baseline должен быть виден и на странице **под** линзой для честного A/B: совместная переменная фоновой композиции либо тот же self-hosted asset в host и source, а не картинка, существующая только внутри WebGL. Для совпадения рисунка source задаёт viewport-sized paint и offset `-stripLeft/-stripTop`; нельзя растянуть тот же градиент заново на 390×100 px, иначе сдвиг будет заметен. Проверить Safari при изменении `visualViewport`/safe area, темы и orientation.
   - Историческое решение для проверки: 2–3 рассеянных цветовых поля из `--ambient-*`/`--background`. **Не развивать прежнюю идею tile/зерна:** контролируемая сгенерированная текстура дала шумную мраморную рябь в оценке Luna ([кадр](artifacts/glass-optics/web/texture-trial/dark-initial-on.png)); baseline без неё выглядел как молочная плашка. Следующий визуальный проход ниже меняет композицию/placement, а не добавляет ещё шум.
2. `WebGlassNav.kt`: сохранить один lens/context и стабильные кнопки; `WebGlassBackdropSlice` остаётся owner scroll/resize подписок на время `HtmlElementView`, отключается в `close()`. `backdrop-version` или `refreshBackdrop()` вызывается после изменения baseline/surfaces, а stale refresh/capture reject не переключает приложение в неготовое состояние. `strength=0.12` — текущая пробная настройка, не утверждённый дизайн; регулировать умеренно, без цветной аберрации вокруг букв. Никакой буквенный контент не должен попасть в refraction source. Если Web Component с HTML-source по измерению дорог даже для slice, проверить его документированный direct `<canvas>` source, куда тот же adapter рисует baseline + формы; выбор подтвердить визуально и по производительности, не добавляя второй renderer.
3. `matrix-progress.css`: связать `.glass-source-ambient` с той же спокойной фоновой композицией host; убрать видимые искусственные полосы/дугу. Порядок слоёв в узкой bottom зоне: настоящий `.route-content` → локальная quiet scrim/fade, подавляющая glyphs непосредственно под nav → совпадающая с host ambient baseline и bounded проекция реальных поверхностей → WebGL lens → семантический `nav`/кнопки. Scrim не закрывает учебный экран выше панели и не меняет DOM/accessibility; `.app` сохраняет нижний scroll padding и safe-area, чтобы перекрытые действия можно было вывести выше nav. Проверить, что источник и scrim не ловят pointer. Desktop остаётся в обычном потоке, если fixed-placement там не утверждён.
4. В `WebGlassNav.applyMode()` сохранить **OFF по умолчанию**; даже явное `?glass-optics=on` отключается при forced colors, high contrast и reduced transparency. Отсутствие пересекающихся surfaces **не** отключает оптику, если валидная ambient baseline захвачена. Пока baseline/slice отсутствует или устарел, capture не готов, renderer не `webgl`, идёт быстрый scroll или возник context loss, показывать текущую читаемую CSS-панель. После успешного `refreshBackdrop` восстановить optics только если URL opt-in и accessibility позволяют. Для iOS Safari не заменять WebGL SVG `backdrop-filter:url(...)` fallback: он не преломляет произвольный background в WebKit.
5. Проверить self-hosted `simple-liquid-glass-5.3.0.esm.js` в JS/Wasm distribution: один и тот же asset, без CDN и React runtime. Записывать `data-glass-strategy`/`data-glass-reason`, число canvas/context, размер/время snapshot и причины fallback. Маршруты/30 циклов тренировки/тема не должны пересоздавать lens. Библиотечный direct canvas или DOM capture очищается при `WebGlassNav.close()` и не оставляет listeners/observers.

Источник библиотеки: [Web Component, `backdrop-selector` и teardown](https://github.com/lucaperullo/simple-liquid-glass#webgl-in-vue-svelte-astro-angular-or-plain-html); [source/capture limits](https://github.com/lucaperullo/simple-liquid-glass#ios-refraction-and-android-opt-in). Диагностическая метка — свидетельство выбранного renderer, **не** доказательство видимого эффекта.

### Следующий web-дизайн-проход: одна цветовая граница, меньшая капсула

В [публичном демо](https://glass.lucaperullo.it/) первая сцена держит нижний dock поверх полноэкранного `coast.mp4`/poster, то есть под стеклом есть **крупные пространственные границы**. Read-only инспекция DOM при 390×844: dock занимает около 269×50 CSS px, три действия; его наружный слой `rgba(18,25,22,.16)` с тонким внутренним светом. Для сравнения наш dock занимает 366×66 px и пять действий; у него поверх библиотеки есть собственные `nav` fill, border, shadow и массивный active-chip. В Playwright WebKit с desktop UA публичный dock сообщал `blur/missing-backdrop`, но композиция остаётся выразительной в уже полученном референсе. Это наблюдение **не** доказывает поведение iPhone Safari; оно показывает, что один shader без подходящего фона и размеров не решит дизайн.

Предлагается **один** экономный вариант, без новой фотографии/видео/шумной текстуры:

1. В `matrix-progress.css` добавить к настоящему фону `.training-web-host` единственное широкое мягкое цветовое поле, край которого пересекает нижние 54–60 px viewport по диагонали или пологой дуге. Это часть обычного page background и использует текущую тёмную/светлую палитру, а не отдельную «обложку» только под nav. Поле состоит из двух больших спокойных тональных областей с переходом порядка десятков пикселей; никаких повторяющихся полос, зерна, водяной ряби, букв или локального свечения вокруг каждой кнопки. `WebGlassBackdropSlice` берёт **точно тот же viewport-aligned paint** в bounded source и поверх него добавляет реальные surface shapes при пересечении. На начальном экране поле даёт линзе границу для мягкого смещения; при скролле связь с карточкой сохраняется. Вне зоны nav фон должен оставаться второстепенным и не мешать чтению правила/ответа.
2. Уменьшить мобильную `.glass-nav-shell` до одной капсулы примерно 330–340×54–58 px при 390×844, с адаптивной шириной `min(… , viewport − safe margins)` и `min-height:44px` у всех **пяти** кнопок. Не удалять Settings или другие маршруты ради сходства с демо. Уменьшить padding/gap, использовать существующие короткие видимые подписи и полные `aria-label`. Это оставляет вокруг стекла фон, на котором видна граница; оно не выглядит как широкая молочная полоса. При 320 CSS px проверить, что все пять touch targets и полные доступные названия остаются в пределах viewport.
3. Дать **одному** Web Component рисовать материал: убрать дублирующий светлый fill/толстую границу/тяжёлую тень с `.glass-nav-shell>nav`, убрать сплошную заливку active-chip; выделение активного раздела оставить через тонкую линию/малую точку и вес подписи плюс `aria-pressed`. На fallback (`off`, forced colors, contrast) прежняя плотная подложка/рамка возвращается. Для ON подбирать прозрачность/frost с отдельными light/dark значениями по кадрам, начиная с меньшего frost, а не добавлять blur; не делать текст полупрозрачным. Настройка `glassTintPercent` остаётся density token, не крутит силу преломления. Изменение одного параметра за сравнение: сначала размер и двойная заливка, затем расположение цветовой границы, затем тонкая оптика.
4. Никакого непрерывного движения поля: CSS static paint, один bounded source и один canvas. При route/theme/resize обновлять source; при scroll действует текущий coalescing/fallback. Сохранять bottom safe area, scroll padding, IME hiding, keyboard focus и контраст. Если вместо фото нельзя получить нужную глубину на спокойной схеме, честно зафиксировать визуальный предел и оставить `?glass-optics=on` лишь экспериментом.

Gate этого прохода: независимая Luna low сравнивает **на одинаковом 390×844 начальном экране** dark/light ON и OFF, затем карточку, проходящую за nav, и 320 CSS px. ON должен отличаться видимым смещением **одного общего фонового края** на кромке линзы, а не белой заливкой или текстурным шумом; источник за и вне линзы непрерывен, без шва. Кнопки/польский текст читаются, нет копий glyphs и CSS/WebGL-двойной окантовки. После визуального PASS повторить JS/Wasm × Chromium/Firefox/WebKit функциональные проверки и A/B perf на новом CSS/source: прежний benchmark от предыдущей композиции к новому проходу не относится. iPhone Safari и физическая производительность остаются отдельными gates.

### Android

Факты: `kotlin/androidApp/src/main/java/dev/polski/grammarmatrix/MainActivity.kt` рисует фоновый градиент в `MainActivity.setContent`, затем прозрачный `Surface` и `AndroidScreen`. `AndroidScreen` использует `Scaffold` с прозрачным container; экспериментальный `GlassNavigationBar` включается только через `glass_optics=true`, по умолчанию остаётся обычная навигация. Источник под экспериментальной панелью пока декоративный, а не скроллируемое содержимое. Оформление/контраст находятся в `kotlin/composeApp/src/androidMain/kotlin/polski/ui/screens/AndroidGlass.kt`. `androidApp` имеет minSdk 24, Compose 1.12.1 и Android-only зависимость Backdrop 2.0.1.

1. `kotlin/gradle/libs.versions.toml`, `kotlin/androidApp/build.gradle.kts`: `Backdrop` 2.0.1 уже закреплён как **Android-only implementation** и собран на API 35 emulator с Compose 1.12.1; не переносить зависимость в `commonMain`/web/iOS.
2. `kotlin/androidApp/src/main/java/dev/polski/grammarmatrix/GlassNavigationBar.kt`: компактный source/lens owner уже добавлен в пределах экрана. `rememberLayerBackdrop` существует на время composition, а реальные `NavigationBarItem` остаются поверх оптического слоя с прежней selected/label semantics. При расширении source сохранять разделение слоёв: `layerBackdrop` не должен оборачивать саму линзу или её interactive children, чтобы исключить круговую выборку и самозахват.
3. В `MainActivity.kt` определить геометрию source и overlay явно. Для первой функциональной проверки допустим стабильный локальный градиент/контрастный рисунок за capsule. Если пилот должен преломлять **живую матрицу**, вывести bottom bar из `Scaffold.bottomBar` в sibling overlay внутри общего `Box`, пометить фон/route content `layerBackdrop`, дать scroll content нижний отступ для доступности; не продолжать считать `innerPadding` старого `Scaffold` подходящим. Этот переход требует отдельного layout/IME/insets теста. В обоих случаях источник обязан покрывать края capsule, иначе будут прозрачные пиксели (показано в [официальном bottom-bar tutorial](https://kyant.gitbook.io/backdrop/tutorials/glass-bottom-bar)).
4. На API 33+ включать `lens`; `shape` должен быть `CornerBasedShape`, высоту преломления ограничить радиусом угла и размером панели. На API 24–32 и при high contrast не создавать оптический путь. На Android 12/API 31–32 один blur возможен, но это не тот же эффект; для чистого A/B использовать существующий fallback. Проверить live изменение `glassTintPercent` без пересоздания session/FSRS. При уходе composable remembered backdrop освобождается его composition owner; никаких activity-global shader/timer/graphics resource.

API и порядок эффектов: [Backdrop bottom bar](https://kyant.gitbook.io/backdrop/tutorials/glass-bottom-bar), [source types](https://kyant.gitbook.io/backdrop/api/backdrops), [effects](https://kyant.gitbook.io/backdrop/api/backdrop-effects). Не добавлять вторую линзу или второй source в пилот: [известный circular-rendering report](https://github.com/Kyant0/AndroidLiquidGlass/issues/100) делает это отдельной проверкой.

## State and resource ownership

Учебное состояние остаётся за `TrainingStore`/`AndroidSessionViewModel`. Навигационные узлы держат только presentation state: route/tab, appearance и renderer status. Web lens живёт ровно один `HtmlElementView` mount; смена упражнения/route обновляет атрибуты и route slot, не размонтирует lens. Android backdrop/lens живут в одной composition, не запускают отдельный frame loop. Потеря WebGL/context или исключение capture не блокирует route/кнопки, не сбрасывает draft/focus/scroll и не меняет сохранённые preferences. Forced colors/contrast/Reduce Transparency имеют приоритет над пользовательской прозрачностью; значение настройки сохраняется.

## Decisions and tradeoffs

Web-пробы прояснили разные ограничения: весь `.training-web-host` создаёт буквенные дубликаты; одни декоративные полосы не связаны с учебным экраном; bounded shapes + ambient baseline без выраженной границы дают молочную панель; шумная текстура превращается в мраморную рябь. Проблема следующего прохода прежде всего **композиционная**: большой dock закрывает почти всю ширину ровного нижнего фона, а второй нарисованный glass-слой поверх WebGL усиливает мутность. Поэтому план меняет один фоновый цветовой край и геометрию/слои dock, сохраняя bounded capture и один renderer. Не увеличивать площадь/силу shader для маскировки плохого source. Если даже этот проход выглядит как отдельная «наклейка» или capture дорог, оставить оптику OFF. На Android живой content capture ближе к системному виду, но требует перестроить overlap и insets; его gate независим от web.

## Verification

1. **Функциональность web:** focused Playwright на production JS и Wasm в Chromium/Firefox/WebKit: nav остаётся тем же DOM узлом после route/reveal/rate/theme change; одна линза и один ограниченный sibling source; пять кнопок доступны role/name/keyboard, `aria-pressed`/focus сохранены; текстовое поле/IME, 320 CSS px, zoom/reflow, Matrix scroll работают; context loss/capture error/forced colors и активный scroll ведут к читаемому fallback. Контрактные тесты: на начальном 390×844 без пересекающейся карточки `data-slice=ambient`, source имеет ненулевой размер, один captured WebGL canvas и `data-glass-ready=true` после загрузки; при скролле карточка/матрица меняет source geometry/color согласно конкретному видимому surface, но baseline сохраняется; в source нет текста, интерактивных узлов и дублированной семантики. Asset отказ — градиентный fallback без pageerror. Собирать `pageerror`/console. Отдельно проверить реальный iPhone Safari: Playwright WebKit не закрывает этот gate.
2. **Визуальная разница:** одинаковые ON/OFF пары light/dark при 320/390 CSS px и desktop; два состояния контента: начальный 390×844 без пересечения и карточка/таблица пересекает зону nav. На первом кадре B должна показывать мягкую пространственную деформацию ambient baseline (не только прозрачность/blur), при этом источник совпадает с видимым фоном без шва, полос, громкого зерна или «наклейки». При пересечении B *чуть* преломляет реальную кромку/цвет surface и меняется вслед за scroll, но ни одна буква/кнопка не появляется второй раз. Оценить кадр при покое, после скролла, во время взаимодействия и по сравнению с [демо выбранной библиотеки](https://glass.lucaperullo.it/). Human approval визуального результата обязателен до смены default OFF; автоматический pixel delta/`data-glass-strategy=webgl` его не заменяет. Проверить contrast, selected state, focus и названия поверх линзы.
3. **Функциональность Android:** focused test/семантика навигации + API 33+ emulator screenshot/recording с контрастным source, смена tab/theme/tint, IME, insets, landscape и API 24–32 fallback. Линза не ловит touch поверх `NavigationBarItem` и не перехватывает TalkBack; screenshot не доказывает TalkBack. Проверить route/content screen и отсутствие circular-rendering errors.
4. **Стоимость:** одинаковый production/release A/B, прогретые не менее пяти повторов, одинаковый fixture, тема, viewport, площадь линзы; web — расширить `Plans/Kotlin/archive/scripts/benchmark-glass-rollout.mjs` (или **NEW** отдельный optics benchmark) для matrix scroll, 30 reveal/rate, route switch, typing, записать actual `data-glass-strategy`, context count, capture failures, snapshot dimensions/bytes/time и p50/p95/кадры >25ms, GPU/peak memory там, где инструмент позволяет. Считать только раунды, в которых B реально использовала новый source и WebGL; прежние `artifacts/glass-optics/web/performance*/web-matrix-scroll.json` относятся к декоративному/полному source и не закрывают новый gate. Android — profile/release `FrameTimingMetric`/Perfetto, p50/p95/hitches, GPU и peak memory. Gate из [GlassPerformanceDecision.md](GlassPerformanceDecision.md): дополнительный median paired p95 ≤1 мс на 60 Гц или ≤0,5 мс на 120 Гц, без новых заметных хичей; физическое устройство для battery/thermal и окончательного performance решения. Эмулятор и Playwright предварительны. Если gate не пройден, оставить CSS/Compose tinted fallback; не объявлять оптический пилот rollout success.
5. **Сборка и regression:** Kotlin JS+Wasm compatibility production distribution; Android assembleDebug/testDebugUnitTest и release/benchmark build; прежние web parity сценарии, сохранение настроек и прогресса. Разделить PASS / FAIL / NOT RUN для browser/device/performance; ранние CSS A/B цифры из `artifacts/glass-rollout/web-matrix-scroll-final.json` — исходная справка, не результат этих библиотек.
