# Module design: progress and legacy migration (stage 7)

## Scope and consumers

Stage 7 transfers `src/progress/storage.ts` (`localDay`, `freshProgress`, `loadProgress`, `saveProgress`, `resetProgress`, `exportProgress`, `importProgress`) and `src/progress/review.ts` (`recordReview`). The future `TrainingStore` consumes a shared progress snapshot, pure reducer, codec and repository; the browser host supplies LocalStorage and the current local calendar day. `src/ui/App.tsx` currently loads on mount, calls `recordReview` once after reveal, keeps the new snapshot in memory even if `saveProgress` throws, exports that memory state, and confirms reset before replacing progress. Stage 7 supplies these contracts and a migration/recovery harness; full progress UI and the UDF store arrive in stages 8/10. No new import UI is in scope: React has an `importProgress` function but no import control.

Actual build: `kotlin/shared/build.gradle.kts` declares JS browser and Wasm/JS browser plus `commonTest`; `kotlin/composeApp/build.gradle.kts` has `commonMain`, `webMain`, and both browser targets. `webMain` already uses `kotlinx.browser` in `SpikeHtmlControls.kt`; existing JS and Wasm `main.kt` use separate raw `js(...)` LocalStorage calls. Kotlin 2.4.20 is pinned in `kotlin/gradle/libs.versions.toml`. No Android/iOS/JVM target or progress code exists yet. Both browser variants must compile and run the adapter; later native adapters implement the same repository boundary without sharing browser storage.

React wire shape is `Progress` in `src/types.ts`: `version`, ordered `cards: [{skillId, card}]`, `stats` keyed by skill ID, `reviewsToday`, `lastDay`, `totalReviews`. A card has ISO string `due`/optional `last_review`, numeric FSRS fields and numeric state. The legacy LocalStorage key is `polski-grammar-srs-v1`. Source of behavioral examples is `tests/fixtures/kotlin-parity/progress.json` (20 cases), `tests/sentences.test.ts`, `tests/parity-acceptance.test.ts`, `tests/app.test.tsx`, and `Plans/Kotlin/{Parity,FsrsDecision}.md`. Historical React PASS is not Kotlin evidence. In particular React accepts version 99 and silently creates fresh state on read error; these are documented defects, not migration requirements.

`ProgressCodec` validates JSON before domain mapping: `version` must be integer 1; required top-level shapes and counters must be present and valid; card fields have valid finite numbers, nonnegative integral counts, numeric state 0–3, parseable ISO instants within JS Date's millisecond range, and unique nonempty `skillId`. Validate `lastDay` as a real `YYYY-MM-DD` calendar date. Missing `last_review` and JSON `null` both map to absent; writer omits it. Preserve unknown top-level/card/stats properties and well-formed unknown skill IDs through decode → review → export. Reject duplicate cards, incompatible known field types, and unsupported versions without writing. Retain the parsed JSON tree as the document's opaque extension source; encode overlays current known fields so updated values win without discarding unknown properties. Explicitly test what to do with any unknown property that conflicts with a known schema key: known validated value wins. A JSON library with JS/Wasm variants must be added to `shared` build/catalog only after dependency resolution; `kotlinx.serialization-json` is the preferred small AST dependency, not yet present in the build.

`encodeLegacyV1` is the export for React rollback, including reviews made after KMP migration. Stage 7 must exercise that output through the existing React `importProgress` decoder and an actual React load/browser path. `JSON.stringify` byte identity is unnecessary; data values, card order, ISO millisecond dates, field names and absence of optional `last_review` are necessary. The existing stage-6 `SrsCardWire` remains the sole card mapper; avoid a second FSRS serializer.

## State and resources

The future `TrainingStore` is the sole in-memory owner of the active `ProgressDocument`; the repository owns durable preview-key writes. One `at` is captured by the caller for a review, local day is computed once from that same `at`, and both values go into `ReviewReducer`. `Scheduler` does not read the clock. On reload/migration, normalize `reviewsToday` to zero and `lastDay` to the supplied local day when the stored day differs; preserve `totalReviews`, skill counts, streaks and card dates. A timezone change can cause a different `lastDay` even for the same instant; the same rule applies. Calls to display due/today capture a new instant but never rewrite a review in progress.

Migration runs only on an explicit recovery/cutover action, not on ordinary `load()`. Keys on the **same origin**: legacy `polski-grammar-srs-v1`; preview `polski-grammar-srs-kmp-preview-v1`; immutable raw backup `polski-grammar-srs-kmp-legacy-backup-v1`; completion marker `polski-grammar-srs-kmp-migrated-v1`. URL paths do not isolate LocalStorage, so React and KMP writers must be separated operationally at cutover. The adapter never writes/removes the legacy key, including reset. `resetConfirmed` means UI already obtained affirmative confirmation; cancellation never calls it. Reset writes a fresh preview snapshot and retains backup/legacy for recovery. If this write fails, keep the current memory snapshot and error; never report reset success.

Protocol, sequential on one host owner:

1. Read legacy raw and preview/backup/marker with explicit unavailable errors. If a valid marker and decodable preview already exist, return `AlreadyMigrated` and use preview, never reapply stale legacy. Missing legacy yields `Missing` only when no recoverable partial state exists.
2. Write the exact legacy raw to backup, then read it back byte-for-byte. If backup already exists and differs from current legacy raw, return `RecoveryRequired` (possible second writer), preserving all keys. Backup write/read failure stops migration. The backup remains exportable as exact raw bytes even when validation later fails.
3. Decode and validate legacy. On invalid JSON/version/card/shape, return `RecoveryRequired` with raw and reason; do not write preview/marker. Complete missing known skills and normalize local day in a new document. Re-read legacy and require exact equality before committing the preview.
4. If an unmarked preview is present, decode and compare it with the expected migration result. If equal, resume at read-back/marker; if different, stop for recovery, never overwrite it. Otherwise write encoded v1 document to preview, read it back, decode it and compare semantic known+retained fields with the intended document. A read-back failure/mismatch stops before marker.
5. Write marker last. Marker binds this migration to the saved backup/preview identity (e.g. exact raw strings or checked digests plus lengths and schema version); on reload verify marker and preview rather than trusting marker alone. Retry after failure is idempotent. Marker write failure leaves an unmarked preview for step 4 to resume. Normal reviews thereafter update only preview; marker identifies completed migration, not a frozen preview checksum.

No two-key atomic transaction exists in LocalStorage. This protocol preserves the legacy original under quota/private-mode/readback/interruption failures and makes each partial state recoverable; it cannot itself arbitrate two live clients on the same origin. Cutover must stop React writing before KMP becomes active. Do not silently start a fresh document when a key exists but cannot be decoded/read. The save result must identify unavailable/quota/security failures without throwing away the document; unhandled platform exceptions and Kotlin cancellation are not folded into `Missing`.

## Decisions and tradeoffs

Use one shared progress capability plus one web adapter, rather than a new Gradle module or global service. `ProgressDocument` holds a parsed extension tree because silently dropping unknown fields/cards can make rollback lossy. A malformed unknown card still blocks migration: preserving an opaque invalid entry while allowing review could produce a file React cannot use. All known skills are completed once using current catalog order, but existing cards keep their order and data. The codec should preserve raw backup separately from the normalized document so rollback can choose exact pre-migration bytes or current React-compatible export. The latter is mandatory after new reviews.

Do not make storage availability a precondition for answering: the UI can retain and export in-memory progress after save failure, matching `App.tsx`. The repository's suspend API leaves room for later native storage, although LocalStorage operations are synchronous internally. The caller serializes save revisions in stage 8 so an older write cannot replace a newer review; stage 7 adapter must not launch independent jobs. UI owns confirmation/download effects; the repository must never show dialogs.
