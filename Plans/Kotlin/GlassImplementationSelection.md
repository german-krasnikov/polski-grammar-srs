# Выбор реализации Liquid Glass для проекта

**Архив, 2026-09-25:** пользователь отменил внедрение собственного стекла. Актуальный план — [PreGlassRollback.md](PreGlassRollback.md); этот документ фиксирует прежний выбор и его ограничения, не задаёт текущую реализацию.

Статус: реализации выбраны и подключены в экспериментальных web/Android-пилотах, 2026-09-25. В обоих хостах оптика выключена по умолчанию; визуальная приёмка и целевой бюджет производительности не подтверждены. Цель и прежние измерения описаны в [LiquidGlassRollout.md](LiquidGlassRollout.md) и [GlassPerformanceDecision.md](GlassPerformanceDecision.md), контракт доработки — в [GlassOpticsPilot.md](GlassOpticsPilot.md).

Пользователь просмотрел [живое демо `simple-liquid-glass`](https://glass.lucaperullo.it/) и подтвердил, что сама реализация подходит. Его замечание к нашему web-прототипу относится к стилям и композиции панели; визуальная приёмка локальной интеграции ещё не пройдена.

## Почему нынешний результат отличается от iOS

Текущие web и Android поверхности рисуют прозрачную заливку, границу, световой край и тень. Они не преломляют изображение **под** панелью. Кроме того, на web крупные текстовые scrim и относительно ровная подложка закрывают или почти не показывают то, что должно проходить сквозь материал. Поэтому простое увеличение `blur` или прозрачности не создаст оптику системного Liquid Glass; оно лишь уменьшит читаемость. Это вывод по текущим `matrix-progress.css`, `AndroidGlass.kt` и снимкам [web](artifacts/glass-library-review/current-web.png), [Android](artifacts/glass-library-review/current-android.png), а не измерение выбранных библиотек. Пробное наложение выбранной web-библиотеки с источником **всего** приложения и `strength=0.16` успешно запустило WebGL, но некрасиво продублировало и исказило текст под линзой: [Chromium](artifacts/glass-library-review/probe-whole-host-chromium.png), [WebKit](artifacts/glass-library-review/probe-whole-host-webkit.png). Значит, для приложения критичны правильный backdrop и более мягкая оптика, а не только наличие shader.

## Решение по хостам

| Хост | Выбор | Причина и граница |
| --- | --- | --- |
| Kotlin DOM web, включая Safari на iPhone | [`simple-liquid-glass` 5.3.x](https://github.com/lucaperullo/simple-liquid-glass), Web Component/низкоуровневый WebGL renderer | Даёт настоящее преломление явно указанного соседнего backdrop в iOS Safari через WebGL, имеет отдельный Web Component без React runtime, CSS fallback и browser tests. В визуальном просмотре публичного демо 2026-09-25 на мобильном viewport Chromium и Playwright WebKit материал выглядел ближе к iOS, чем текущий CSS. Это **кандидат для небольшого количества видимых линз**, а не готовая обёртка для каждой кнопки и строки таблицы: каждый видимый WebGL lens имеет свой context, снимок HTML ограничен бюджетом и требует правильной структуры источника. [README/стратегии](https://github.com/lucaperullo/simple-liquid-glass#browser-support--rendering-strategies), [ограничения renderer](https://github.com/lucaperullo/simple-liquid-glass#webgl-in-vue-svelte-astro-angular-or-plain-html). |
| Android Jetpack Compose | [`Kyant0/Backdrop` 2.0.1](https://github.com/Kyant0/AndroidLiquidGlass/releases/tag/2.0.1) | Библиотека отделяет backdrop от линзы и действительно рисует преломление, blur, vibrancy и поверхность для читаемости. Есть подробный [пример нижней панели](https://kyant.gitbook.io/backdrop/tutorials/glass-bottom-bar), [API источников](https://kyant.gitbook.io/backdrop/api/backdrops), Apache-2.0 и [публикация Maven Central](https://central.sonatype.com/artifact/io.github.kyant0/backdrop); 2.0.1 перешла на Compose 1.12.0, рядом с закреплённой у нас 1.12.1. `lens` требует Android 13/API 33; на старых устройствах оставить нынешний читаемый `AndroidGlassSurface`, не обещая рефракцию. [Эффекты/API](https://kyant.gitbook.io/backdrop/api/backdrop-effects). |
| iPhone, iPad, Mac | Штатные SwiftUI `glassEffect`, `.buttonStyle(.glass)` и `GlassEffectContainer` | Это реальный системный материал и системная реакция на настройки внешнего вида/доступности. Сторонняя SwiftUI-библиотека поверх этих API не улучшает сам материал. Образцы вроде [SwiftUI showcase](https://github.com/sk1gl4a/LiquidGlass-SwiftUI-Showcase) использовать как пример композиции, не как зависимость. [Apple custom views](https://developer.apple.com/documentation/SwiftUI/Applying-Liquid-Glass-to-custom-views), [WWDC25](https://developer.apple.com/videos/play/wwdc2025/323/). |

Слово «лучший» относится к **нашему стеку и этой задаче**, а не к универсальному рейтингу библиотек. Пользователь хочет схожий визуальный язык на всех платформах; один общий renderer не заменит штатный SwiftUI на Apple и не даст одинаковую стоимость на DOM и Compose.

## Что проверено среди альтернатив

| Кандидат | Почему не выбран первым |
| --- | --- |
| [`naughtyduk/liquidGL`](https://github.com/naughtyduk/liquidGL) | Хорошая демонстрация и общий canvas для многих линз, но встроенный rasterizer снимает DOM; автор сообщает о медиане 55,5 мс для полного снимка своей страницы и нестабильности Safari при линзе больше половины viewport. Наши длинные таблицы и частые DOM rebuild делают это особенно рискованным. Подойдёт как резервный web-кандидат, если ограниченный прототип `simple-liquid-glass` не пройдёт кадры или визуальную оценку. |
| [`samasante/liquid-glass`](https://github.com/samasante/liquid-glass/blob/main/BROWSERS.md) | Его `filter: url()` работает в WebKit над **обёрнутым содержимым**, но произвольный живой фон за фиксированной панелью в WebKit не преломляет; сам автор отмечает ограничение `backdrop-filter: url()`. React API также не подходит напрямую для Kotlin DOM. |
| [`skydoves/Cloudy`](https://github.com/skydoves/Cloudy) | Качественный KMP набор blur/эффектов и запасной Android-кандидат. Для нашей задачи пример `liquidGlass()` работает как lens над собственным content; получение фона позади навигации требует отдельной связки `Sky`. У Backdrop источник и накладная линза представлены прямо в API/учебном примере. |
| CSS/SVG библиотеки с `backdrop-filter: url()` | WebKit не поддерживает этот способ преломления arbitrary backdrop; пользователь особенно сравнивает с iPhone. [Таблица браузеров simple-liquid-glass](https://github.com/lucaperullo/simple-liquid-glass#browser-support--rendering-strategies). |

## Последовательность внедрения и gates

1. **Web:** выделить устойчивый DOM-узел для одной навигационной линзы и отдельный sibling-backdrop. Сейчас `TrainingDomRenderer.render` очищает `root.textContent` при значимом обновлении состояния; монтирование Web Component внутри этого дерева пересоздавало бы WebGL context и HTML capture. Сначала устранить это в узком слое навигации, сохранив `nav`/кнопки, focus, route и accessibility. Затем подключить выбранный renderer в **одной** компактной линзе с явной диагностикой `webgl`/fallback. Не указывать весь `.training-web-host` как источник: проба исказила учебный текст и кнопку. Подобрать локальный фон/placement и силу преломления так, чтобы линза воспринималась стеклом, но не дублировала читаемый текст. Не включать на каждой таблице/карточке автоматически. Сравнить одинаковый production artifact с нынешним CSS в Chromium, Firefox, WebKit и мобильном Safari: внешний вид, p95/hitches, memory/context loss, ввод, scroll, темы и reduced-transparency. Снимок Playwright WebKit — только предварительная визуальная проверка, не физический iPhone.
2. **Android:** подключить Backdrop только в Android host, расположить capture source и одну нижнюю навигационную линзу как siblings по официальному примеру. Держать текст/семантику Material 3 над линзой, не захватывать собственную линзу в backdrop. На API 33+ проверить refraction и lifecycle; ниже 33 оставить текущий fallback. Проверить эмулятор и физическое устройство с теми же сценариями, сравнить frame timing, overdraw, battery/thermal при продолжительной тренировке. У Backdrop есть [открытый отчёт о circular-rendering crash при нескольких источниках](https://github.com/Kyant0/AndroidLiquidGlass/issues/100), поэтому несколько панелей добавлять только после изоляции этой схемы.
3. **Apple:** оставить штатный SwiftUI. Повысить видимость настоящего материала через корректный фон **за** control/navigation layer и группировку близких элементов в `GlassEffectContainer`; проверить, что локальные scrim не закрывают всю линзу. На iPhone/iPad/Mac проверить Clear/Tinted, Reduce Transparency/Contrast, Dynamic Type и Instruments. Apple прямо предупреждает, что множество независимых glass effects ухудшает производительность. [Руководство Apple](https://developer.apple.com/documentation/SwiftUI/Applying-Liquid-Glass-to-custom-views).
4. Для крупных учебных карточек, таблиц и полей сохранить прозрачный визуальный язык, но отдельно решать по измерениям, нужна ли им **оптическая** линза. Критерий — учебный текст остаётся читаемым, а стоимость проходит [gate проекта](GlassPerformanceDecision.md). Это не отменяет заказанное оформление всех поверхностей.

**Наблюдаемая проверка выбора:** 2026-09-25 открыты и сфотографированы публичные демо `simple-liquid-glass` в Playwright [Chromium](artifacts/glass-library-review/simple-chromium.png)/[WebKit](artifacts/glass-library-review/simple-webkit.png) при 390×844, scale 2; ошибок страницы не было. Временная инъекция Web Component 5.3.0 в текущий локальный production web artifact создала WebGL canvas и `data-glass-strategy=webgl` в Chromium/WebKit без ошибок, но визуальный вариант с целым app как backdrop **отклонён** по читаемости (снимки выше). Демо `liquidGL` в WebKit сначала показывало [загрузочный экран](artifacts/glass-library-review/liquidgl-webkit-load.png), а спустя 15 секунд [нарисовало линзу](artifacts/glass-library-review/liquidgl-webkit-15s.png) без ошибок страницы; ранний кадр не считается провалом совместимости. После выбора добавлены self-hosted Web Component в web и Android-only Backdrop в Android: браузерные и эмуляторные проверки подтверждают запуск. В web ограниченный source уже отражает формы видимых учебных поверхностей поверх фонового слоя без повторного текста, но скриншотные A/B всё ещё не проходят визуальный критерий iOS-подобного преломления; Android-пилот пока использует декоративный source. Производительный gate ещё не подтверждён. На iPhone и Mac остаются штатные SwiftUI материалы; физическое профилирование этих пилотов ещё не проводилось.
