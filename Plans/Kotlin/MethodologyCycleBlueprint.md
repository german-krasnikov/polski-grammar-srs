# Полный цикл двух методик · архитектурный handoff

Дата: 2026-09-24. Это проектирование шага 4 [CoursePacksPlan.md](CoursePacksPlan.md); реализация и проверки отмечаются отдельно. Первый курс — только `pl-ru`. Основа: существующие `skills[].methods.logic/situations` в `courses/pl-ru/course.json`, селекторы React/Kotlin/нативных хостов и одна очередь FSRS. Методика — предпочтение подачи, а не диагноз или отдельный учебный элемент.

## Фактические границы

- React: `src/ui/App.tsx` владеет текущим `exercise`, `answer`, `revealed`, `mode` и `explanationMethod`; `rate()` — единственный переход к `recordReview`. `src/data/course.ts` читает оба варианта текста. Предпочтение живёт в `polski-explanation-method-v1`, отдельно от JSON прогресса.
- Kotlin: `kotlin/shared/src/commonMain/kotlin/polski/presentation/{AppUiState,AppAction,TrainingStore}.kt` владеет вопросом/раскрытием/оценкой. `CourseData.kt` читает `MethodPresentation`; Web `TrainingWebApp.kt` и нативные `TrainingScreen.kt`, `AndroidTrainingScreen.kt`, SwiftUI host показывают выбранный вариант. Смена методики уже не вызывает review и не меняет введённый ответ.
- Существующие `introduction` и `promptLead` — разные авторские тексты для 16 навыков. На лицевой стороне сейчас только ситуационный `introduction`; после ответа оба варианта показывают `introduction`. Это ещё не управляемая последовательность четырёх этапов.

## Контракт содержания

Для каждого `skills[].methods.{logic,situations}` добавить явные поля `introduce`, `retrieve`, `feedback`, `review` в schema, валидатор, TS и Kotlin reader. Поля содержат **подсказки/порядок**, а не правильные формы, FSRS ID или генератор. Нынешние `introduction` и `promptLead` оставить читаемыми на переходе; редактор переносит/уточняет их после сверки всех 16 навыков. Отсутствующий или пустой этап отвергается при сборке и загрузке. Версию pack менять только при несовместимом wire-формате; прогресс v1 не менять.

`introduce` описывает смысл или вопрос наблюдения, согласованный с **любой** фразой соответствующего навыка, либо явно привязан к ID/условию примера, выбранного генератором. Для «Живых ситуаций» это короткая сцена и вопрос о намерении говорящего; для «Схем и логики» — структура/вопрос о признаке. Оба текста обходятся без целевой польской формы и без готового окончания до раскрытия. `retrieve` формулирует действие перед самостоятельным ответом; смысл упражнения по-прежнему задаёт `exercise.prompt`, его польский эталон не меняется. `feedback` после раскрытия направляет внимание на `exercise.changes`, объяснение и явную пару «было → стало». `review` после раскрытия объясняет выбор «Повторить»/«Вспомнил» и следующую самостоятельную попытку; никакой новой оценки не создаёт.

Не закреплять образ «книги друга», «вчера», имя/число/род или конкретный глагол за навыком, если `generateForSkill` может выдавать другой контекст. Контентная проверка должна перебрать детерминированные seeds/варианты `generateForSkill` и `generateChain`, сверить каждую сцену с источником и prompt, а не только искать запрещённые слова. Эксплицитное правило сохраняется после ответа в обоих вариантах. Подача не утверждает «нейроподстройку».

Уже найденные редакторские расхождения: `agreement.my` говорит о «книге друга», хотя генератор выбирает разные существительные и шесть новых владельцев; `sentence.question` говорит о «предмете», хотя seed может быть человеком; `verb.future` упоминает `będę` как универсальную связку при карточке с формой третьего лица. Эти тексты требуют правки в pack до показа как вводной сцены. `case.dat` с подарком и `case.inst` с движением соответствуют текущим `datStart`/`instStart`, но цепочка может давать другой контекст; проверять оба пути.

## Цикл экрана и состояние

1. `introduce`: на **первой** встрече навыка (`stats[skillId].reviews == 0`) пользователь видит короткое вводное наблюдение и переходит к тому же упражнению; повторения сразу открывают retrieval, сохраняя краткую вводную подсказку без дополнительного обязательного клика. Этот шаг не раскрывает эталон и не пишет прогресс.
2. `retrieve`: исходное предложение, действие и устный/печатный ответ. Нажатие reveal замораживает введённый ответ как сейчас. Смена методики оставляет `exercise.id`, draft, режим ответа и текущий этап; меняется только подача доступных на этом этапе текстов.
3. `feedback`: после reveal показать эталон, правильность печатного ответа, авторское объяснение, контраст и текст выбранного метода. Тексты из другого метода не должны оставаться в DOM/семантическом дереве как скрытая подсказка. Смена метода после reveal не повторяет раскрытие и не стирает ответ.
4. `review`: те же две оценки и один вызов прежнего `recordReview`/`TrainingStore.rate`. Объяснение оценки может отличаться по методу; сохранённая карточка, время, очередь, skill ID и направленность повторения не зависят от метода. Кнопка оценки остаётся доступной без лишнего перехода после обратной связи.

Для Kotlin `TrainingStore` — единственный владелец эфемерного этапа и события продолжения; новый enum/поле допускается только если необходимо для первого знакомства. Нельзя создавать отдельные progress/FSRS документы для методов. Для React локальный этап карточки сбрасывается только при **новом** упражнении/наборе, но не при выборе методики, вкладки или переключении устного/печатного ввода. Предпочтение остаётся в текущем platform preference key; не добавлять его в экспорт прогресса.

## Порядок реализации

1. Сначала редакторский аудит 16 навыков и schema/reader: утвердить тексты этапов, найти сцены с ложной конкретикой, добавить негативные тесты пустых полей/раннего раскрытия. Один источник — course pack; platform UI не хранит учебный текст.
2. Реализовать чистую подготовку отображения этапа для React и Kotlin common, затем React и Kotlin Web. Наблюдать RED→GREEN для первой встречи, смены метода с draft до/после reveal, reload предпочтения, отсутствия второго review, равных ответов/FSRS. Browser Playwright проверить keyboard/focus, 320 px, доступность текста и отсутствие целевого ответа до reveal в обоих методах.
3. Подключить общие данные к Desktop/Android Compose и SwiftUI host; каждый target проверять отдельно. Использовать нативные контролы. На iPhone/Android simulator проверить первый шаг, смену метода с незавершённым ответом, feedback и ровно один review. Физические устройства и screen readers — `NOT RUN`, пока реально не использованы.
4. Независимый Tester принимает A1–A7, Reviewer проверяет контентный инвариант, границы состояния, совместимость и доказательства. После них обновить `CoursePacksPlan.md`, `Evidence.md`, продуктовые документы и inventory решений.

## Критерии приёмки

| ID | Наблюдаемое условие |
| --- | --- |
| A1 | Оба метода имеют четыре авторских этапа для всех 16 навыков; невалидный pack отвергается по точному пути. |
| A2 | На первой встрече вводный этап не показывает `exercise.expected` или целевую часть; после перехода source/prompt/answer остаются теми же. |
| A3 | Смена метода на текущей карточке до/после reveal сохраняет draft/frozen answer, exercise ID и phase; reload сохраняет предпочтение. |
| A4 | Одни и те же упражнения/ответы/FSRS fixture и skill IDs при обеих методиках; reveal и смена методики сами не записывают review. |
| A5 | Все 16 ситуаций и логических подсказок верны для каждого проверенного варианта генератора и не обещают обучение по «типу мозга». |
| A6 | React и Kotlin Web в Chromium/Firefox/WebKit показывают порядок, focus/keyboard, 320 px и доступные текстовые подсказки без ранней утечки. |
| A7 | Desktop, Android Emulator и iPhone Simulator показывают тот же цикл с нативными контролами; отдельные build/test/launch результаты записаны. |

Измерение отложенного удержания требует одинаковых заданий, интервалов и реальных сессий пользователей. Это будущая продуктовая аналитика; локальные тесты не доказывают превосходства методики.
