# Решение: нативный интерфейс каждой платформы, общее Kotlin-ядро

Статус: архитектурное изменение курса от 2026-09-25 по прямому требованию пользователя. Этот документ уточняет [основной план](Plan.md) и [UX0–UX6](PlatformUXPlan.md). Ранее реализованные web UX2 и Mac Compose Desktop остаются рабочими превью, тестовым эталоном и источником данных; их не удалять до приёмки замены. Публикация React и формальные device/accessibility gates остаются отдельными решениями.

Визуальные материалы и их ресурсный предел определяются отдельно в [GlassPerformanceDecision.md](GlassPerformanceDecision.md). Производственное расширение стеклянных эффектов приостановлено до сравнения с непрозрачным вариантом.

## Одно решение

Оставить `kotlin/shared` владельцем польской грамматики, генерации заданий, двух оценок, FSRS, очередей, версионированных progress/vocabulary/preferences JSON и семантических действий сессии. Интерфейс каждого host строить его обычными средствами:

| Host | Итоговый UI и текущая база | Решение |
| --- | --- | --- |
| Web | Семантический HTML/DOM/CSS; сейчас `composeApp/src/webMain/kotlin/polski/ui/TrainingWebApp.kt` строит DOM через `HtmlElementView`, Kotlin JS/Wasm проходят browser parity; React/Vite остаётся опубликованным эталоном | Сохранить текущий Kotlin DOM UI как web host и завершать UX2/паритет на нём. Compose здесь лишь временный mount/runtime wrapper, не общий визуальный компонент и не архитектурный шаблон для других host. Убирать wrapper только отдельным доказанным переходом без потери JS/Wasm/IME/семантики. |
| Android | `androidApp/src/main/java/dev/polski/grammarmatrix/MainActivity.kt` и `.../ui/screens/` уже Jetpack Compose/Material 3 | Продолжать UX4 как Android-native Compose, адаптивная навигация, системные темы/разрешения/уведомления через Android API. Общий Compose UI модуль для мобильных экранов не вводить. |
| iPhone/iPad | `iosApp/PolskiGrammar/PolskiGrammarApp.swift` уже SwiftUI поверх `shared/src/iosMain/.../IosSession.kt`, `IosVocabularySession.kt` | Продолжать UX5 в SwiftUI; Kotlin/Native bridge экспортирует состояние и принимает семантические команды, UIKit/SwiftUI владеет layout, accessibility, Files и notifications. |
| macOS | `composeApp/src/desktopMain/.../Main.kt` — Compose Desktop/JVM preview и локальный package | Сделать **новый macOS SwiftUI app** поверх Kotlin/Native `macosArm64` framework; `macosX64` добавить для Intel только с отдельной сборкой/проверкой. Native `WindowGroup`, `NavigationSplitView`/toolbar, `Settings` scene/`SettingsLink`, AppKit file/notification integration. Старое `.app` не выдавать за конечный native Mac host. |

Это соответствует возможности Kotlin/Native использовать общее Kotlin из Swift/macOS/iOS ([Kotlin/Native](https://kotlinlang.org/docs/native-overview.html)) и реальным target DSL ([macosArm64](https://kotlinlang.org/docs/multiplatform/multiplatform-dsl-reference.html)). Ключевой обмен — **снимок состояния + семантическая команда**, не попытка экспортировать весь `StateFlow`, Compose modifier или platform control через Objective-C/Swift границу.

## Web: сравнение вариантов и решение

**Выбран Kotlin DOM host.** Он уже использует `shared` напрямую: `TrainingStore`, `VocabularySession`, `WebProgressRepository` и `WebPreferencesRepository`, а `TrainingWebApp.kt`, `SettingsWeb.kt`, `WebRouteController.kt`, CSS создают настоящий DOM с семантикой. Существующая compatibility distribution проверяла и JS, и Wasm в трёх браузерных движках; пользовательские данные/ключи и browser routes уже интегрированы. Выбор сохраняет инвестицию UX2 и обязательный Kotlin browser target.

Альтернатива — оставить React/TypeScript presentation из `src/ui/App.tsx` и подключить к `shared` через новый Kotlin/JS экспорт. Она облегчила бы React UI сопровождение, но потребовала бы отдельного экспортируемого facade: `TrainingStore`, `StateFlow`, `AppAction` и Native/Compose типы не являются готовым TypeScript API; пришлось бы определить стабильные plain JSON/primitive команды, подписку/отписку, ошибки и отдельную webpack/Vite сборку. `@JsExport` доступен в Kotlin/JS с ограничениями экспортируемых типов ([официальная документация](https://kotlinlang.org/docs/js-to-kotlin-interop.html)); эта интеграция не подключает автоматически Wasm output к React и создала бы второй presentation owner. React сохраняется как работающая публикация и независимый oracle, а не становится новой обязательной прослойкой. Если Kotlin DOM проиграет реальный screen-reader/IME/device gate, вернуться к React+Kotlin/JS facade как **явно отдельному** решению, не склеивать два UI в один экран.

## Kotlin/Swift boundary для нового Mac

В `kotlin/shared/build.gradle.kts` сейчас объявлены `desktop` JVM, Android, JS/Wasm, `iosArm64` и `iosSimulatorArm64` с `PolskiShared` static framework; **macOS Kotlin/Native target отсутствует**. Добавить `macosArm64()` и framework `PolskiShared` в том же модуле, не в `composeApp`. До переноса UI проверить compile/link `:shared:linkDebugFrameworkMacosArm64` и минимальный Swift consumer. macOS Gradle target не превращает `iosMain` в общий: `IosSession.kt` хранит прогресс в `NSUserDefaults`, а Mac preview — в файлах Application Support. Создать **NEW** `kotlin/shared/src/macosMain/kotlin/polski/macos/MacSession.kt`, `MacVocabularySession.kt`, `MacProgressRepository.kt`, `MacVocabularyRepository.kt`, `MacPreferencesRepository.kt` (объединять файлы по ответственности можно). `commonMain` остаётся без `java.*`/AppKit; переносить лишь общую чистую сериализацию и правила действий. SwiftUI не должен самостоятельно рассчитывать FSRS.

Для первого вертикального среза сохранить существующий проверенный iOS bridge pattern: `MacSession.currentSnapshot(): String`, `onState: ((String)->Unit)?`, `dispatch(command: String, value: String)`, `acknowledgeEffect(id, outcome)`, `close()`; словарь — отдельный bridge, пока `VocabularySession` самостоятельный. Snapshot — версионированный host DTO с `schemaVersion`, активной карточкой/фазой/черновиком, двумя рейтингами и следующими сроками, ошибкой и одноразовыми effect IDs; неизменные большие справочные данные запрашивать отдельно/кэшировать, если измерения покажут цену полного JSON. Неверная команда/ID не оценивает карточку; Swift dispatch вызывает только семантическое действие `TrainingStore`. Swift `@MainActor ObservableObject`/современный Observation wrapper принимает callbacks, парсит/валидирует DTO и снимает подписку/закрывает Kotlin owner при завершении window scene. Один owner на окно; импорт может перезапустить store внутри bridge с новым snapshot, как iOS, но appearance/Settings/resize — нет. `onState` не должен удерживать закрытое окно. Проверить API, экспортируемые Objective-C типы и release framework в реальном Swift target; не обещать прямой экспорт `StateFlow` или `suspend` в SwiftUI.

**Файлы и миграция.** Mac JVM preview хранит `progress-v1.json`, `vocabulary-v1.json` в `~/Library/Application Support/Polski Grammar Matrix/`; UX3 Preferences должен хранить `preferences-v1.json` рядом. Новый Mac Kotlin/Native repository читает те же форматы через Foundation/file APIs, валидирует `ProgressCodec`, `VocabularyCodec`, `UserPreferencesCodec`, сохраняет исходный raw на ошибке и делает backup + атомарную замену/readback для явного импорта. На первом запуске показать обнаруженный старый progress/preferences и идемпотентно перенести или открыть его с backup; **не запускать JVM и SwiftUI app одновременно как двух writers одного файла**. Не считать старый Java `Preferences[explanationMethod]` доступным Swift напрямую: если `preferences-v1.json` ещё нет, предложить явный импорт/экспорт прежнего метода из старого preview либо выполнить одноразовый migration bridge до замены JVM host. Предпочтения, FSRS и словарь остаются тремя отдельными документами. Если новый bundle sandbox меняет доступ к прежнему каталогу, использовать пользовательский file importer и сохранить оригиналы; не молча создавать пустой прогресс.

**NEW** `kotlin/macosApp/PolskiGrammarMac.xcodeproj` (генератор проекта по аналогии с `iosApp/generate_project.rb` допустим), SwiftUI App/Model/Training/Matrix/Vocabulary/Progress/Settings файлы и UITests. `kotlin/settings.gradle.kts` не обязан включать Xcode проект: Gradle владеет framework, Xcode — app. Xcode build phase собирает `PolskiShared` для `macosArm64` и подключает конкретный build output; выбирает архитектуру по destination, не копирует iOS binary. Для `macosX64` — отдельная Gradle target/framework и Intel или Rosetta smoke, прежде чем объявлять поддержку. Совпадающее framework имя для разных платформ означает разные артефакты, не один смешанный framework.

Native Mac System/Light/Dark/Reduce Motion теперь реализует SwiftUI `@Environment(\.colorScheme)`, `@Environment(\.accessibilityReduceMotion)` и `.preferredColorScheme` для ручного override; `Settings` scene и `SettingsLink` дают системный путь к настройкам ([Apple SettingsLink](https://developer.apple.com/documentation/swiftui/settingslink)). Предыдущий [UX3 Compose Desktop blueprint](UX3MacBlueprint.md), включая Swift sidecar observer, относится к **сохранённому preview**; sidecar не переносить в SwiftUI app, где AppKit/SwiftUI доступны напрямую. До доказанной системной доставки напоминания остаются честно недоступными.

## Что меняется в сроках и gates

1. Зафиксировать текущий UX2 Kotlin DOM + React oracle и Mac JVM package как read-only compatibility baselines, включая JSON fixtures/скриншоты и известные NOT RUN. Не удалять эти исходники и не переписывать исторические отчёты.
2. Завершить web Kotlin DOM проверку P01–P12/UX2 на доступных браузерах и отдельно отметить реальный Safari/IME/screen reader как NOT RUN, если канала нет. Android UX4 и iOS UX5 могут идти после web по исходному плану, но Mac native SwiftUI — новый обязательный UX3 gate вместо дальнейшей полировки Compose Desktop как конечного UI.
3. Сделать Mac framework + минимальный SwiftUI вертикальный срез: открыть сохранённую карточку, ввести польский ответ, раскрыть, поставить ровно одну оценку, перезапустить app и получить тот же FSRS JSON; открыть Settings и сменить System/Light/Dark без изменения карточки. Только после этого переносить матрицы, словарь, data controls, sidebar/menus и notifications capability.
4. Выполнить Mac UX3 полностью в SwiftUI, затем Android UX4 и iOS UX5 с платформенными экранами; завершить UX6 общими сценариями данных/FSRS, но UI/accessibility проверять на каждом host отдельно. Параллельность допустима только на непересекающихся platform файлах и после закрепления snapshot/command contract.

| ID | Приёмка архитектурного перехода |
| --- | --- |
| NH1 | Kotlin/JS и Wasm DOM production build сохраняют текущие P01–P12/UX2 сценарии, storage keys, Back/Forward, light/dark, keyboard/IME и browser semantics; React baseline и JSON progress не изменены. Web UI не импортирует Android/iOS/Mac виджеты. |
| NH2 | Android host остаётся `androidApp` Jetpack Compose Material 3; две оценки/свайпы/Settings и адаптивная навигация проверены в compact/expanded emulator, а Kotlin shared FSRS JSON совпадает с эталоном. |
| NH3 | iPhone/iPad host остаётся SwiftUI, Kotlin `IosSession` — единственный владелец обучения; legacy progress/vocabulary и обе оценки сохраняются после restart. Смена темы/метода/Settings не пишет review. |
| NH4 | Mac `macosArm64` framework загружается новым Xcode SwiftUI target; один полный review + restart сохраняет progress/FSRS. На одинаковом входном JSON, skill, rating и зафиксированном времени serialized FSRS исход совпадает с JVM preview; случайно сгенерированное предложение не сравнивать по ID между запусками. Повреждённый/новой версии файл остаётся экспортируемым без замены. |
| NH5 | Mac SwiftUI `WindowGroup`, sidebar/toolbar, Settings scene/`⌘,`, Files dialogs, System/Light/Dark, Reduce Motion, узкое окно/крупный текст и VoiceOver проверяются **в новом `.app`**, а не по JVM Compose tests. macOS уведомления включать только после permission/delivery/click routing. |
| NH6 | Для каждой платформы записаны отдельно unit/domain tests, target compilation, package, живой UI, accessibility и device **PASS/FAIL/NOT RUN**; исторические UX2/Mac Compose доказательства не повышают native Mac gate. Независимый Tester и Reviewer читают финальный diff по workflow. |

Главная цена решения — новый macOS Kotlin/Native adapter и SwiftUI UI вместо использования уже собранного Compose Desktop окна. Она оправдана прямым требованием нативного интерфейса Mac. Реальный риск — framework/Swift interop, файловая миграция и новые Xcode/архитектурные сборки; первый вертикальный срез из пункта 3 проверяет их до полной верстки. Разработка не требует удаления React или Compose preview и не подразумевает публикацию/подпись.
