## Объём, потребители и подтверждённая основа

Потребитель сейчас — браузерное приложение; позднее те же `shared` и общий Compose UI должны обслуживать native Android/iOS. React в `src/**` остаётся эталоном. Два Gradle-модуля: `kotlin/shared` (модели, словари, чистая грамматика, генерация, FSRS, прогресс) и `kotlin/composeApp` (состояние сессии, UI и web host). Направление зависимости: `composeApp → shared`; `shared` не импортирует Compose, DOM или localStorage. Новые native targets и shells относятся к этапам 13–16.

Подтверждённые исходные символы: `src/types.ts` задаёт `Exercise`, `Progress`, `SerializedCard`, `Skill`; `src/data/{nouns,adjectives,verbs,pronouns}.ts` — формы; `src/grammar/engine.ts` — `nounPhrase`, `verbForm`, `normalize`; `src/training/{skills,generator,evaluator,queue}.ts` — 16 навыков, 12 seeds, пять связанных шагов, accepted варианты и due queue; `src/srs/scheduler.ts` — `ts-fsrs` 5.4.2; `src/progress/{storage,review}.ts` — legacy JSON и counters; `src/ui/{App,GrammarTables}.tsx` — три вкладки и четыре раздела матрицы. В `src/main.tsx`, `vite.config.ts` и `.github/workflows/deploy.yml` остаётся действующий React entry/deploy. Новых Kotlin-файлов ещё нет.

Эталон — **2141 portable JSON cases** в `tests/fixtures/kotlin-parity/`: grammar 1979, exercises 112, evaluation 9, scheduler 21, progress 20; provenance и хэши — `manifest.json`. Browser baseline включает Chromium-сценарии и снимки, но Safari/Android/IME/screen reader не проверены. Три обнаруженные ошибки React (focus после rating, навигация при 320 px и крупном шрифте, принятие import version 99) не переносятся как желаемое поведение; расхождения фиксируются явно.

## Решение браузерного spike — этап 2

Кандидат по официальным документам на 2026-09-23: Kotlin **2.4.20**, Compose Multiplatform **1.12.1**, Compose compiler plugin той же версии **2.4.20**, Gradle **8.14.2** как установленный и внутри документированного для Kotlin диапазона **7.6.3–9.7.0**, JDK **21** как выбранный toolchain. Это **кандидат**, не доказанная совместная сборка проекта; lock, wrapper, dependency versions и фактические tasks фиксируются этапом 3 после spike. Compose web остаётся Beta. Источники: [Compose compatibility](https://kotlinlang.org/docs/multiplatform/compose-compatibility-and-versioning.html), [KMP compatibility](https://kotlinlang.org/docs/multiplatform/multiplatform-compatibility-guide.html), [compiler plugin](https://kotlinlang.org/docs/multiplatform/compose-compiler.html).

Начальный host: `wasmJs` с `ComposeViewport` внутри явно стилизованного HTML container; `js` собирается для compatibility distribution. Официальный `composeCompatibilityBrowserDistribution` объединяет обе ветви, но успешная сборка не доказывает выбор JS runtime. Для WasmGC документированные нижние границы: Chrome/Chromium **119**, Firefox **120**, Safari/WebKit **18.2**; это границы Wasm, не обещание полного поведения приложения. Проверить актуальные версии/ОС тестовых устройств и загрузку обеих ветвей; JS fallback нужен для браузеров ниже WasmGC minimum и проверяется принудительно на подходящей конфигурации. Источники: [Kotlin/Wasm browser versions](https://kotlinlang.org/docs/wasm-configuration.html), [web compatibility mode](https://kotlinlang.org/docs/web-overview.html), [unified distribution](https://kotlinlang.org/docs/multiplatform/whats-new-compose-190.html).

**Вертикальный slice** в NEW `kotlin/composeApp/src/commonMain/kotlin/polski/ui/SpikeScreen.kt`: польское/русское предложение и hidden answer, typed input с Enter/Shift+Enter/IME, reveal, четыре rating, 7-строчная таблица с row/column headers и горизонтальным scroll, localStorage save/reload. Данные можно держать временными; spike не претендует на grammar/FSRS parity. NEW `kotlin/composeApp/src/{wasmJsMain,jsMain}/kotlin/polski/main.kt` запускают одинаковый slice и измеримый runtime. NEW `kotlin/composeApp/src/webMain/kotlin/polski/platform/` содержит только действительно общие web adapters, если source-set hierarchy поддержана фактическим Gradle. NEW `Plans/Kotlin/WebCompatibility.md` фиксирует browser/OS/version, branch (Wasm или JS), bundle bytes, startup до интерактивности, ввод/scroll latency, screenshots и assistive-technology наблюдения. Замеры проводить на production artifact и одном менее мощном мобильном браузере; пороги задать по измеренной React-базе на том же устройстве до полного UI переноса.

Матрица проверки: desktop Chromium/Firefox/Safari, физический Chrome на Android и Safari на iPhone, польские символы/русский текст offline и с медленной сетью, native keyboard/IME composition, soft-keyboard resize, Tab/Space/Enter/Shift+Enter, focus после rating, pointer/touch и wheel, zoom/крупный текст при 320 CSS px и landscape, reduced motion. Зафиксировать DOM/accessibility tree, фактическое чтение VoiceOver/TalkBack или эквивалентным screen reader, скрытость ответа до reveal, связь заголовков и ячеек таблицы, взаимодействие со scroll container. `ComposeViewport` рисует canvas; общий Compose accessibility guide не доказывает web table semantics. В 1.9.3 web accessibility была initial, без interop/scroll container support; заметки 1.12 не утверждают, что это исправлено. Проверить 1.12.1 поведением, а не предположением. [Viewport](https://kotlinlang.org/docs/multiplatform/compose-css-styles.html), [Compose 1.9.3 web accessibility](https://kotlinlang.org/docs/multiplatform/whats-new-compose-190.html), [Compose 1.12](https://kotlinlang.org/docs/multiplatform/whats-new-compose-112.html).

Текущая инфраструктура не даёт объявить device gate пройденным: `adb` отсутствует, а `xcrun simctl` блокируется непринятой Xcode license. Developer продолжает независимые desktop/web и fixture проверки; Tester отмечает физические устройства и связанные IME/screen reader сценарии `NOT RUN`, пока host не доступен. Desktop browser и эмуляция не заменяют эти строки. Это ограничивает **приёмку этапов 2/11**, но не блокирует этапы 3–8 и подготовку desktop/browser реализации этапов 9–10. До физической проверки нельзя объявить P04/P07/P08/P12 или WEB PARITY GATE закрытыми и переходить к production cutover.

**Наблюдаемое решение renderer после production Chromium/Wasm spike:** canvas-ветвь сейчас отдаёт textbox без доступного имени и таблицу как generic без `row`/`columnheader`; Playwright role overlay находится под canvas, поэтому обычный click перехватывает canvas. Это фактический blocker для pure-canvas browser UI, а не предположение из старой документации. JS fallback запрашивает `originJsComposeApp.js`; его загрузка/исполнение и соответствующее поведение требуют отдельной runtime проверки. Зафиксировать точные artifact/browser/trace и результаты в `WebCompatibility.md` после проверки Developer/Tester.

Для browser host **обязательны настоящие DOM-элементы** для typed answer (`<textarea>` с именем/label и composition handling), reveal и четырёх rating (`<button>`), основной/внутренней навигации (`<nav>` и кнопки с текущим состоянием), feedback/errors (`role=status`/`role=alert` по смыслу) и всех учебных/progress таблиц (`<table>`, `<caption>` при необходимости, `<th scope=col|row>`, ячейки и собственный scroll container). Нужны видимый focus, нативная Tab/Space/Enter активация, правильный keyboard/IME порядок, scroll/zoom и screen-reader чтение заголовков с данными. Невидимые overlays, дублирующие интерактивные элементы над canvas, неприемлемы: браузерный accessibility tree и hit testing должны относиться к тем же видимым controls. Compose canvas можно оставить для неинтерактивных областей только если он не перекрывает DOM hit targets и не создаёт дублирующую озвучку.

Developer сначала проверяет `HtmlElementView` (актуальное имя после `WebElementView` в Compose 1.11) как способ разместить эти DOM-элементы в обеих web ветвях и подтвердить z-order, focus, semantics и lifecycle на production artifact. Если любой обязательный control/table остаётся под canvas, теряет смысловую структуру или конфликтует с IME/scroll, browser UI реализуется как тонкий DOM host/presenter, который отображает `AppUiState` и отправляет `AppAction` в **тот же Kotlin `TrainingStore` и `shared` domain**. Для Kotlin/JS использовать браузерные DOM API; если Wasm interop не даёт безопасного пути, обосновать и зафиксировать supported browser distribution/branch без заявления о Wasm parity. Compose UI остаётся возможным общим/native presentation для будущих Android/iOS, но browser DOM не должен дублировать генератор, scheduler, reducer или storage policy. [Compose 1.11 HTML interop](https://kotlinlang.org/docs/multiplatform/whats-new-compose-111.html). Блокирующий сценарий нельзя закрыть тестовым backdoor или screenshot.

**Порядок работы:** core/toolchain (этапы 3–8) можно вести без ожидания HTML probe, сохраняя renderer-independent `AppUiState`/`AppAction`. Полный browser UI этапов 9–10 должен опираться на результат probe; до этого допустимы только независимые элементы/сценарии, которые не закрепляют canvas как обязательный renderer. Отсутствие физических устройств также не останавливает coding и desktop tests, но оставляет mobile/IME/assistive evidence `NOT RUN` и web gate открытым.

Три фактических альтернативных generated ответа относятся к future/aspect/mixed. Проверить эти края отдельно от общих fixture cases, не выводить число альтернатив из названия case.

Граф: `data/model → grammar → training`; `model → scheduler`; `training + scheduler + progress → TrainingStore → UI`; platform adapters реализуют порты `shared`, wiring только в web entrypoint. `GrammarReference` использует grammar/data и не знает текущую сессию. Kotlin `data class copy()` с вложенными коллекциями не обещает deep copy: на границах state/repository делать независимые snapshots, иначе preview/reducer могут незаметно мутировать старое состояние.

## Состояние, время, FSRS и сохранность данных

`TrainingStore` — один владелец сессии; текущая карточка/answer/reveal живут в памяти, durable только progress. `Rate(exerciseId, rating)` допускается после reveal и только для текущего ещё не оценённого ID; принятая оценка помечается до запуска сохранения. Последующие click/key и старые async completion не создают второй review. Один `at` и local day используются для FSRS, counters и due; tick/visibility resumption пересчитывают due/today. Coroutine scope и timer принадлежат browser host и отменяются при dispose; saves сериализованы по revision, устаревший completion не очищает новую ошибку. На save failure in-memory snapshot остаётся доступным для JSON export и UI показывает ошибку.

FSRS настройки из `src/srs/scheduler.ts`: retention **0.9**, maximum interval **3650**, fuzz **on**, short term **on**, learning **1m/10m**, relearning **10m**. Фактический `Card` wire имеет `due`, `stability`, `difficulty`, `elapsed_days`, `scheduled_days`, `reps`, `lapses`, `learning_steps`, numeric `state`, optional `last_review`; сравнить дополнительные поля, defaults/weights и exact serialized values с установленным package, не выводить их из другого FSRS major. Проверка установленного `node_modules/ts-fsrs` **5.4.2** через `dist/index.cjs.map` выявила 21 вес FSRS-6 в `src/constant.ts`, `BasicScheduler`, learning-step strategy, seeded Alea/Mash fuzz и UTC-day расчёт; путь `src/...` здесь обозначает вложенный `sourcesContent` sourcemap, а не отдельные файлы checkout. Для точного порта исследовать `src/{default,models,convert,fsrs,abstract_scheduler,impl/basic_scheduler,strategies/learning_steps,strategies/seed,algorithm,alea,help}.ts` внутри этой карты; особенно JS-формат seed `${reviewEpochMs}_${reps}_${difficulty*stability}`, округление и порядок cap → fuzz → Hard/Good/Easy. [Upstream FSRS implementations list](https://github.com/open-spaced-repetition/awesome-fsrs) показывает Kotlin FSRS-Kotlin v6 и android-fsrs v4: это кандидаты для аудита, не доказанная совместимость с `ts-fsrs` 5.4.2 и browser/native targets. Этап 6 фиксирует license, версию формулы/weights, короткие шаги, fuzz/Alea, округление и differential results в NEW `Plans/Kotlin/FsrsDecision.md`; если совместимой реализации нет, ограниченный Kotlin port необходимой v5.4.2 логики с атрибуцией. JS bridge не закрывает общий scheduler. Сначала все 21 case, затем дополнительные boundary/golden случаи для state/rating, preview/review при одном `at`, fuzz/short steps/overdue; допустимую числовую погрешность записать **до** оценки реализации, даты/enum и JSON shape сравнивать точно. Production fuzz остаётся включённым.

Legacy key — `polski-grammar-srs-v1` (`src/progress/storage.ts`), preview key — `polski-grammar-srs-kmp-preview-v1`. LocalStorage изолирован origin, не URL path. Этап 7: (1) явный запуск миграции, raw legacy backup без изменения и его export; (2) validation version/shape/dates/non-finite numbers/skill IDs/duplicates, unknown fields/skills не терять молча; (3) дополнение missing known skills и local-day normalization без потери history; (4) write в новый key, read-back compare, marker последним; (5) idempotent retry и error/recovery при quota/private-mode/interruption; (6) legacy оригинал не перезаписывать до cutover. Для rollback экспортировать **текущее** KMP состояние в legacy v1 и реально проверить React decoder/загрузку; старый backup не содержит новых reviews. Concurrent writers исключаются на cutover. Импорт через UI React отсутствует (`importProgress` — API), поэтому новый import screen не требуется; recovery harness/compatible export обязателен. Unsupported version 99 — ошибка codec, с зафиксированным отличием от baseline defect.
