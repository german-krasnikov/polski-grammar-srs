# Blueprint этапа 1: воспроизводимый эталон React

## Scope и исходная точка

Этап 1 [основного плана](Plan.md) фиксирует наблюдаемое поведение действующего React/TypeScript/Vite-приложения для будущего сравнения с Kotlin web. Production-код, публикация и Kotlin-модули в этот этап не входят. Исходная ревизия приложения — `df59774e153a5bdf590fe27bd8780c7bd5457a26`; незакоммиченные README, инструкции, skills и план сохранить, а в evidence указать точные changed paths и ревизию, на которой получены результаты. Исторический [отчёт](../../docs/verification.md) не заменяет свежий запуск.

Реальные команды из `package.json`: `npm test` (Vitest), `npm run typecheck` (`tsc -b`), `npm run build` (`tsc -b && vite build`), `npm run dev`, `npm run preview`; lockfile — `package-lock.json`, `ts-fsrs` в нём 5.4.2. `tests/app.test.tsx` работает в jsdom. Playwright и браузерного script сейчас нет; Browser/Playwright-проверка требует явной установки, конфигурации и lockfile-изменения в реализации этапа. Не называть jsdom результатом браузера. Текущий deploy `.github/workflows/deploy.yml` публикует React после push в `main`; не менять его на этом этапе.

## Контракт fixture

Предлагаемые файлы **NEW** `tests/fixtures/kotlin-parity/manifest.json`, `grammar.json`, `exercises.json`, `evaluation.json`, `scheduler.json`, `progress.json`. Это переносимые JSON-данные, без функций и зависимостей от TypeScript. Для каждого файла: `schemaVersion: 1`, `sourceRevision`, `cases: [{id, input, expected}]`. У каждого case стабильный смысловой `id` и, где нужен, `context` (`nowIso`, `timeZone`, `randomDraws`, `fsrsParameters`, `sourceSymbol`). `expected` хранит полный наблюдаемый результат, включая порядок массивов; ошибки задаются `{error: {kind, message?}}`, не через стек. JSON не содержит личного LocalStorage. Manifest перечисляет файлы и case IDs, версию Node/npm/пакета, способ генерации, locale/zone, контрольные суммы исходных JSON, а также правила сравнения: строки и enum — точно, даты — ISO UTC, числа FSRS — точные JSON значения из эталона с отдельно оговорённой допустимой погрешностью при Kotlin-переносе, если она будет подтверждена анализом. Не округлять wire-поля ради удобного сравнения.

Генератор фикстур **NEW** `tests/fixtures/kotlin-parity/generate.ts` (или отдельный CLI-файл вне Vitest discovery) читает существующие exports и записывает JSON в стабильном порядке. Проверка **NEW** `tests/parity-fixtures.test.ts` повторно вычисляет outputs по checked-in fixtures и сообщает устаревший case; она не заменяет независимых assertions существующих тестов. Выход генератора должен быть побайтно одинаков при двух запусках на одинаковой ревизии/окружении. Никакого вызова `loadProgress()` для создания fixture из пользовательского браузера: используется `freshProgress()` и вручную сконструированные нейтральные legacy snapshots.

Часы контролируются **до** импорта/вызова модулей там, где создаются карточки или scheduler: фиксированный instant, например `2026-02-03T12:00:00.000Z`; для local-day cases задаются IANA zone и обе стороны полуночи/DST. `newSkillCard`, `preview`, `review`, `isDue`, `recordReview` и `localDay` сейчас читают `Date`/`Date.now()` внутри, поэтому тестовый harness использует fake clock с восстановлением в `finally`; браузерная конфигурация также фиксирует timezone/locale context и clock, не меняя production API. `generateForSkill` использует `Math.random` для seed и владельца, `card` — ещё один вызов для ID. Для каждого сценария задаётся последовательность `randomDraws` и проверяется число потреблённых draws; предпочтительно брать явный `preferred` seed, но отдельно проверить fallback/ограничения кандидатов. В semantic fixture `Exercise.id` заменяется на стабильный маркер или исключается сравнителем, а raw ID проверяется только как непустой и уникальный для упражнений в одной сессии. Не утверждать, что один и тот же numeric seed создаст ту же последовательность в Kotlin.

Для FSRS fuzz установленный `ts-fsrs` использует собственный Alea, seed которого выводится из карточки/момента review; `Math.random` не управляет этим fuzz. Зафиксировать полный входной `SerializedCard`, `nowIso` и настройки `request_retention: 0.9`, `maximum_interval: 3650`, `enable_fuzz: true`, `enable_short_term: true`, `learning_steps: ['1m','10m']`, `relearning_steps: ['10m']`; сравнивать результаты production settings. Дополнительные fuzz-off исследования можно хранить отдельно и нельзя выдавать за production parity.

Генератор не должен «исправлять» выход React. В частности `importProgress` проверяет только наличие `cards`/`stats`, UI не имеет кнопки импорта; не добавлять новую возможность для соответствия. Если current code падает на некорректном snapshot или молча создаёт fresh progress, зафиксировать факт и ожидаемое исправленное поведение в `Parity.md`/`Evidence.md`, не превращать его в требование к Kotlin.

## Browser baseline и ресурсы

**NEW** `tests/browser/react-baseline.spec.ts`, `playwright.config.ts`, соответствующие `package.json`/`package-lock.json` изменения, только после выбора совместимой версии Playwright. Вынести browser spec за пределы Vitest discovery и включить config/spec в реальную проверку типов. Playwright `webServer` запускает существующий `npm run dev` или `npm run preview` с loopback URL, с фиксированными timeout/readiness, нулём retries для acceptance, `forbidOnly` в CI и failure trace/screenshot. `npm ci` остаётся способом восстановления lockfile. Browser version/project/artifact пишутся в evidence; Playwright WebKit не маркировать как iOS Safari.

Каждый сценарий получает новый context с пустым storage; для reload используется тот же context/origin. Нейтральный `Progress` загружается в `polski-grammar-srs-v1` **до** page navigation, затем через UI выполняется действие и проверяются видимый результат и фактический сохранённый JSON. Для export проверяется download и содержимое файла; reset проверяется подтверждением и отменой. Ошибка записи воспроизводится только на реальной границе LocalStorage, без mock grading/reducer. Слушатели `pageerror`/console устанавливаются до загрузки. Context, server и временные файлы закрываются в teardown.

Сценарии: начальная скрытая карточка, пять шагов/четыре оценки, typed correct/incorrect/accepted, mode/queue, shortcut и повторная оценка, IME, таблицы/селекторы/drill, контекстная справка, progress/reload/export/reset/write failure. Проверять focus после перехода к следующей карточке; `App.tsx` сейчас вызывает `revealButton.current?.focus()` непосредственно после `showExercise`, что требует наблюдения, а не предварительного объявления PASS. Typed textarea обрабатывает Enter без проверки `isComposing`: проверить реальный IME и, если дефект подтверждён, пометить как baseline bug. В global hotkey `App.tsx` фильтруются `INPUT`/`TEXTAREA`/`SELECT`/`BUTTON`/`A`, modifiers и `repeat`; эти границы проверить браузером.

Визуальные артефакты **NEW** `Plans/Kotlin/artifacts/stage1/`: desktop и 320 CSS px для карточки front/reveal/typed, всех четырёх разделов матрицы, контекстной справки и прогресса; дополнительно landscape, zoom/large text и reduced motion как P12 evidence. Для каждого снимка фиксировать viewport, DPR, browser/OS, locale, timezone, font readiness, storage fixture, motion preference и состояние UI. Снимки проверяются на содержимое/overflow/доступность controls, а не на попиксельное равенство будущему Compose. Бинарные артефакты включать в репозиторий только если они нужны для ревью; пути и provenance обязательны в `Evidence.md`.

Developer владеет fixtures, browser harness и документацией; Tester независимо сверяет coverage/воспроизводимость и восполняет acceptance gaps; Reviewer читает итоговый diff и evidence. Если baseline bug требует продуктового исправления, его решение согласуется как отдельное изменение контракта и не маскируется обновлением golden JSON.
