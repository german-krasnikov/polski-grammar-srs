# Module design: sixteen-exam web audio delivery

2026-11-12. Architecture handoff for the 16-paper P9 publication candidate in sibling `p9-publication`; this file changes no media, app code, release or production deployment. Preserve that worktree's source/catalog changes when integrating. The existing six public papers remain byte-for-byte stable. The ten new papers are B2 February 2022, February/June 2023, February/June 2024, and C1 March/November 2022, April/November 2023, April 2024. B2 June 2022 remains excluded because its received MP3 fails full decode. Original files and pinned source hashes remain the authority for native assets and audit.

## Scope and consumers

GitHub Pages serves the Kotlin browser compatibility distribution from `.github/workflows/deploy.yml`; `kotlin/composeApp/src/webMain/kotlin/polski/ui/ExamListeningWeb.kt` sets `HTMLAudioElement.src = exam.audioUrl` and seeks within authored millisecond windows. `dsl/exam-published/pipeline.mjs` requires each listening task URL to match its media declaration. Keep all 16 `webPath` values and task `audioUrl` values stable; this is a delivery-byte change, not an exam, answer, transcript, segmentation, playback or shared-domain change. `scripts/prepare-ios-exam-assets.ts` must continue reading each `localSourcePath` and original `sha256` for the published IDs, staging original bytes into the native app.

The [sixteen-paper local preview](P9-PUBLICATION-PREVIEW-EVIDENCE.md) reports 1,163,038,310 original MP3 bytes; the reproducible original tar is outside the repository at sibling `p9-audio-artifact/polski-exam-audio-v2.tar` (1,163,059,200 bytes, SHA-256 `e077045ec390dafae4d8672e269fe94d529713d389891c84fb488f012b54daaa`). [GitHub's current Pages limit](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) says the **published site** may be no larger than 1 GB; its custom Actions exception applies only to build frequency. The full original set cannot be the Pages payload. The existing six total 326,860,829 bytes; their current compatibility distribution has 29,218,694 other bytes. Measured with `stat` and `ffprobe` from the local preview, the ten new source files total 836,177,481 bytes over 22,675.423 seconds. Two new sources already use 192 kb/s (`B2-2022-02`, `C1-2023-04`); the other eight use 320 kb/s. These are source measurements, not encoded output evidence.

## Public contract

Extend `ExamAudioAssetRow` in `dsl/exam-assets.data-contract` (existing) with `webSha256: string OPTIONAL` and `webLocalSourcePath: string OPTIONAL`, generated by the existing `GENERATE exam-audio-assets` step in `dsl/biome.project`. Set the row cardinality to `COUNT 1..`, matching the existing variable-size `ExamRow` and `ExamPublicationRow` contracts. Enforce **exact** one-to-one equality of published exam IDs and audio manifest IDs in the publication gate and preparer; a publication addition with missing or surplus media must fail. Snapshot the intended 16 IDs in acceptance tests for this release, not in a permanent schema count. `sha256` and `localSourcePath` always mean the original. For a row with neither web field, playback bytes are exactly the original and the effective web hash is `sha256`. For a row with a derivative, **both** web fields are required, the derivative is an MP3 at a distinct ignored local path, and `webSha256` pins its exact bytes. Biome marks the fields optional individually; the cross-field pair invariant belongs in runtime/CI validation. Mixed or malformed pairs fail validation. `webPath` remains the sole browser URL and path in published listening rows. `officialDownloadUrl` identifies only the original source, never the derivative. There is no runtime media manifest or new shared Kotlin API.

Author derivative fields for only the eight 320 kb/s new rows. Keep the original six and the two 192 kb/s new rows without web fields. Suggested derivative source layout (NEW, ignored media vault): `ExamBin/web/<level>/<session>/audio.mp3`; exact paths are explicit per DSL row, not inferred from `webPath`. Author rows through Biome format/generate, never edit `dsl/exam-assets/generated/ExamAudioRows.ts` by hand. Record the encoder program/version, exact arguments, source SHA, output SHA and byte size in a new media provenance entry; do not put an estimated hash into DSL.

The eight derivatives should be encoded from verified original PCM to stereo MP3 at a target 160 kb/s CBR, preserving channel count, sample rate and entire recording timeline. Do not trim, shift, normalize, resample or alter authored cut timestamps. Pin the actual encoder build and command in provenance; if its output changes, regenerate and review the candidate rather than accepting another hash. MP3 re-encoding is **lossy**. The source originals remain available and unmodified for native delivery and later re-encoding.

At 160 kb/s, the measured duration of the eight 320 kb/s originals projects about 364.9 MB of derivative bytes. With the six original public assets, the two new 192 kb/s originals and the observed 29.2 MB non-audio distribution, the site projects about **827 MB**, leaving roughly **173 MB** below the 1 GB published-site ceiling. This is a sizing hypothesis; ID3 tags, encoder padding and final build growth make the actual assembled-site gate authoritative. If output fails the budget or audio-boundary checks, adjust the web encoding candidate and repeat the gates without touching source media or cuts.

## State and resources

The source vault owns original MP3s. The derivative vault owns reproducible web MP3s; neither is committed as a generated Kotlin file. The DSL owns the source-to-web hash chain. Browser and native staging own copies only. Preserve original sources and v1 archive; store the new web archive as a versioned release artifact with member list, deterministic tar metadata, archive SHA and per-member manifest SHA. A separate original v2 archive may serve native workflows; its prepared local bytes and hash above are **not** proof of an uploaded release. CI should verify archive SHA before extraction, reject unexpected/missing members and unsafe paths, then run web `prepare --offline`, which verifies the 16 effective playback files but does not claim to re-audit eight absent originals. The original archive's SHA and its 16 member source hashes, plus the derivative production provenance, preserve the upstream audit chain. No network fallback during deploy. The main agent coordinates actual release/archive changes and production deployment after implementation acceptance.

## Decisions and tradeoffs

Keeping full originals on Pages fails the documented published-site size ceiling. Hosting through GitHub Release redirects would add an external media origin and risks signed redirect expiry, range/seek and CORS behavior for a browser player; a separate asset site/CDN adds hosting and cache ownership. Neither is needed if the measured derivative candidate passes the byte and playback gates. Browser MP3 derivatives preserve existing URLs and native source fidelity with one DSL contract. They do introduce lossy encoding, so acoustic and timing validation is a hard publication gate, not an assumed property of bitrate.

## Verification

1. **Source and encoding:** in the maintainer-only source/derivative gate, verify all 16 original hashes, eight derivative hashes and exact source/derivative pairing; full-stream `ffmpeg -xerror` decode for each derivative. Compare decoded sample counts/duration and signal alignment against each original over the full recording, including start/end and the 48 start/end edges of the 40 task windows in the eight derivative papers. The 10 new papers have 50 task windows and 60 candidate start/end edges; all 16 papers have 80 task windows. Keep every published task window at its original time coordinates and do not change DSL cuts. Re-run independent speech/signal checks at the 48 affected candidate edges and human acoustic review where ambiguous; the existing original audit of 60 new-paper edges does not automatically certify derivatives. Record encoder/version/arguments and actual byte totals.
2. **Contract tests:** row without optional fields copies original; derivative row in web `prepare --offline` requires and verifies only derivative bytes, while `check-source` and `encode` require/verify the original independently. Wrong source fails source/encode/native gates; wrong or missing derivative, mixed fields, duplicate URL, invalid path, missing/surplus published media fail web preparation without replacing a previously valid published asset. `check-paths` finds 5 listening tasks per paper/80 total and matching URLs. Native staging/check-app still verifies original SHA even when a web derivative exists. Run `biome fmt`, `biome generate`, `biome generate --check`, affected Vitest, typecheck and shared/native checks as dictated by touched consumers.
3. **Build and deployment candidate:** JS/Wasm/compatibility dist hash checks use effective web hashes; assembled site byte count passes the 850,000,000-byte target (150 MB reserve) and absolute 1 GB limit. Check actual final artifact manifest and served `check-url` hashes under the real Pages subpath. Test HTTP `206` range requests, seeking and replay with Vite preview and after deployment. A successful archive, hash or Gradle build is not browser playback evidence.
4. **Real browser:** on a fresh compatibility artifact, Playwright opens all 16 papers, loads every audio file and plays/seeks across all 80 authored listening windows, including >40-second positions, end boundaries, replay and route disposal. Record Chromium/Firefox/WebKit results separately; use a native Safari/device check if required by the web support matrix. Do not change transcript text or cuts merely to make an automated score pass.
