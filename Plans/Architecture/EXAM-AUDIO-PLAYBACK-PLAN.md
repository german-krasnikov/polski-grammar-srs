# Аудио-воспроизведение в listening-модуле экзаменов

Дата: 2026-11-08. Дополняет `Plans/Architecture/EXAM-MODULES-PLAN.md` (раздел «Аудио» там —
одна строка-заглушка; этот план разворачивает её в конкретную архитектуру для web, с учётом
того, что уже реально лежит в репозитории).

## Проверенные факты

- `ExamBin/pl/<level>/<year>/audio.mp3` — ОДИН файл на экзамен (22–83 МБ), не в git:
  `ExamBin/.gitignore` → `*.mp3`. Подтверждает решение EXAM-MODULES-PLAN «НЕ коммитить MP3».
- Реальные данные уже существуют: `exams/pl/certyfikat-polski/B1/2019/listening-tasks.core-data`
  — 5 `LISTENING_TASK` строк, `audioUrl: "ExamBin/pl/B1/2019/audio.mp3"`,
  `segmentStartMs: 0` / `segmentEndMs: 0` у всех пяти (заглушки, не размечено).
  Контракт `dsl/exam.data-contract` (`ListeningTaskRow`) уже содержит `segmentStartMs`/
  `segmentEndMs: int` — менять контракт не нужно.
- Текущий web-код (`ExamListeningData.kt`, `ExamListeningWeb.kt`) — рукописный плейсхолдер
  с выдуманными вопросами и `audioUrl = "exam-audio/B1-2019.mp3"`, никак не связан ни с
  `.core-data`, ни с `ExamBin`. Его подключение к реальному pipeline — задача другого агента
  (data-pipeline/import); этот план фиксирует контракт плеера так, чтобы импортёру было
  достаточно просто проставить `audioUrl`/`segmentStartMs`/`segmentEndMs`.
- В `:shared` сейчас нет ни одного stateful `expect/actual` моста (только чистые функции —
  `AnswerNormalizer.kt`, `PolskiTextCodec.kt`). Rive — другой стейтфул-мост из нескольких API —
  сознательно реализован **в каждом хосте отдельно** (`webMain`/`androidMain`), без общего
  `expect class` в `:shared`, именно из-за расхождения платформенных API. Это прямой прецедент
  для `AudioPlayer`.
- `kotlin/composeApp/build.gradle.kts`: `js { browser { commonWebpackConfig {...} } }` и
  `wasmJs { browser { commonWebpackConfig {...} } }` уже существуют — туда добавляется
  `devServer.static` без новых плагинов.
- Критический баг в текущем `ExamListeningWeb.kt`: `redraw()` делает `c.innerHTML = ""` и
  пересоздаёт `<audio>` при **любом** вызове — включая клик по варианту ответа
  (`answers[q.id] = opt; redraw()`). С реальным 60+ МБ файлом и `currentTime`-сикингом это не
  просто лишний трафик — это сброс позиции/паузы воспроизведения при каждом клике. Это нужно
  исправить вместе с добавлением сегментного плеера, иначе новый плеер будет сломан тем же
  паттерном.

## Scope и границы

Web-реализация (JS/Wasm browser target), `:composeApp` `webMain`. Контракт плеера сформулирован
как обычный `interface` (не `expect/actual` — см. «Решения»), чтобы при появлении Android/iOS/
Desktop listening-UI другие хосты реализовали его в своём `platformMain` без переноса в
`:shared` заранее.

Не в scope: заполнение реальных `segmentStartMs`/`segmentEndMs` для всех 6 экзаменов (это
ручная разметка — см. ниже), подключение `ExamListeningData.kt` к `.core-data` (data-pipeline),
Android/iOS/Desktop плеер.

## Публичный контракт

```kotlin
// kotlin/composeApp/src/webMain/kotlin/polski/ui/AudioSegmentPlayer.kt — NEW
package polski.ui

import kotlinx.coroutines.flow.StateFlow

/** Один mutable экземпляр на экран прослушивания; владеет одним <audio> DOM-узлом. */
internal interface AudioSegmentPlayer {
    /** Переключает текущий сегмент. Не пересоздаёт <audio>, если url не изменился
     *  (тот же файл экзамена — 5 заданий делят один src). */
    fun loadSegment(url: String, startMs: Int, endMs: Int)
    fun play()
    fun pause()
    fun replay() // seek(startMs) + play()
    fun dispose()

    val isPlaying: StateFlow<Boolean>
    /** 0..(endMs-startMs), для прогресс-бара; не абсолютная позиция в файле. */
    val positionMs: StateFlow<Int>
    val segmentDurationMs: Int
}
```

Поведение:
- `loadSegment` ставит `currentTime = startMs/1000.0`, не трогает `src`, если файл уже тот же
  (сравнение по `url`) — иначе 60–80 МБ скачиваются повторно при каждой навигации между
  заданиями одного экзамена.
- Авто-стоп: подписка на `timeupdate`; `currentTime*1000 >= endMs` → `pause()`.
- `endMs == 0` (неразмеченный сегмент, текущее состояние данных) — не авто-стопить вообще,
  играть до конца файла; UI показывает варнинг «сегмент не размечен» вместо тихого молчания.
- Ошибка загрузки (404/отсутствует `ExamBin` локально) — `error`-событие `<audio>` переводит
  плеер в явное состояние "недоступно", не в вечный спиннер.

### `AudioPlayerBar` (NEW, тот же файл или соседний) — UI-обёртка: Play/Pause, Replay,
прогресс-бар по `positionMs/segmentDurationMs`, текст подсказки. Рисуется **один раз на вход в
задание**, не на каждый `redraw()` ответов (см. «Компоненты»).

## Компоненты и зависимости

1. **`ExamListeningWeb.kt` (существующий, править)** — структурная правка перед добавлением
   плеера: сейчас `renderTask()` вызывается из `redraw()`, которая чистит весь контейнер
   `innerHTML` при любом изменении состояния (ответ, навигация). Нужно разделить:
   - внешний контейнер задания создаётся/переиспользуется **только** при смене
     `currentTaskIdx` (здесь и только здесь создаётся/перегружается `AudioSegmentPlayer`
     через `loadSegment`);
   - блок вопросов/ответов — вложенный `<div>`, который чистится и перерисовывается на каждый
     клик, как сейчас. Audio-бар находится вне этого вложенного узла и не трогается кликами по
     ответам.
   Это минимальная хирургическая правка существующего redraw-паттерна, не переписывание
   компонента целиком — остальной код (`trueFalseOptions`, `mcOptions`, `fillGapInput`,
   `renderResult`) не меняется.

2. **`AudioSegmentPlayer` (NEW, webMain)** — класс, не `object`: один экземпляр на
   `ExamListeningController`, создаётся в его конструкторе/первом `renderTask`, `dispose()` при
   `onBack`/выходе с экрана (останавливает загрузку, снимает листенеры).

3. **`ExamListeningData.kt` / `.core-data` (не трогаем контракт)** — `audioUrl` хранит путь,
   относительный к «корню аудио экзаменов», а не абсолютный `ExamBin/...` путь и не готовый
   URL. Конкретно: `"/pl/B1/2019/audio.mp3"`. Кто разрешает этот относительный путь в
   конкретный origin — см. «Delivery» ниже. Контракт `ListeningTaskRow.audioUrl: string`
   не меняется, меняется только договорённость о *значении*.

## Delivery: dev vs production

**Главное ограничение, которое меняет формулировку исходных вариантов (a/b/c)**: эти MP3 —
официальные записи CKE (экзаменующей организации), сознательно не закоммичены
(`ExamBin/.gitignore`) именно из-за копирайта (см. EXAM-MODULES-PLAN: «только транскрипция +
sourceUrl, не файлы издателя»). Поэтому «production delivery» — это не вопрос «как ужать 60
МБ», а вопрос **имеет ли это приложение право раздавать чужую копирайтную запись кому-либо
кроме себя**. Варианты (a) bundled и (c) собственный on-demand кэш на инфраструктуре проекта
одинаково нарушают это ограничение, если у production-сборки есть другие пользователи, кроме
автора на своей машине. Это нужно явно решить, не только спроектировать механику:

- **Если целевая аудитория — сам пользователь на своих устройствах** (похоже на реальный профиль
  проекта — личный SRS с личными `ExamBin`-файлами): production = тот же `ExamBin`, разложенный
  локально на каждом устройстве/хосте, без CDN вообще. Тогда вариант (b)/(c) не нужны —
  «production» web-сборка на localhost — это то же самое, что dev, только `wasmJsBrowserProductionRun`
  вместо `Development`; devServer-static решает оба случая одинаково.
- **Если планируется раздавать сборку другим людям** (публичный деплой) — тогда раздавать файлы
  из `ExamBin` нельзя. Единственный законный путь — `audioUrl` в проде указывает на публичный
  `sourceUrl` самого CKE (поле `ExamRow.sourceUrl` в контракте уже под это зарезервировано),
  если CKE действительно публикует файл по стабильному HTTPS-адресу, а `<audio src>` стримит его
  прямо оттуда (браузер сам делает Range-запросы — не нужен собственный серверный кэш). Это
  фактическая неизвестность — надо проверить, публикует ли CKE сами записи публично, прежде чем
  проектировать (c) «on-demand download + cache» как часть этого приложения; если не публикует —
  listening-модуль в публичной сборке технически не может работать с настоящим аудио и должен
  either (i) быть выключен для гостевых/публичных деплоев, либо (ii) требовать, чтобы у
  пользователя был свой легально приобретённый файл, который он сам кладёт в локальное
  хранилище (аналог личной музыкальной библиотеки), а не приложение.

**Нерешённый вопрос, который нужно подтвердить у пользователя/в `AI/decisions.md`, а не
достраивать самому**: какой из этих двух профилей — личный или публичный. Без этого ответа
пункт «production delivery» не имеет единственно верного решения — текущий план покрывает
dev полностью и даёт оба production-пути, но выбор между ними зависит от этого факта.

### Dev (конкретный, без открытых вопросов)

`kotlin/composeApp/build.gradle.kts`, в `js { browser { commonWebpackConfig { ... } } }` и
аналогично в `wasmJs { browser { commonWebpackConfig { ... } } }`:

```kotlin
commonWebpackConfig {
    sourceMaps = false
    devServer = (devServer ?: KotlinWebpackConfig.DevServer()).apply {
        static = (static ?: mutableListOf()) + listOf(
            rootProject.file("../ExamBin").absolutePath,
        )
    }
}
```

Точное имя свойства (`static`, тип `MutableList<String>`) нужно проверить разработчику против
установленной версии Kotlin Gradle Plugin (`kotlin = "2.4.20"`, см. `kotlin/gradle/
libs.versions.toml`) — механизм (webpack-dev-server «static» directory, без копирования файлов
в `build/`, без коммита в git) гарантированно существует в этой версии KGP, точный синтаксис —
дело пяти минут проверки в IDE/доках при реализации, не архитектурное решение.

Результат: при `jsBrowserDevelopmentRun`/`wasmJsBrowserDevelopmentRun` запрос
`GET /pl/B1/2019/audio.mp3` с того же origin, что и сама SPA, обслуживается статикой из
`ExamBin/pl/B1/2019/audio.mp3` напрямую с диска — ровно тот путь, который уже лежит в
`listening-tasks.core-data`. Никакого симлинка/копирования не нужно и копирайт-файл не
покидает рабочую машину разработчика.

## Разметка сегментов (`segmentStartMs`/`segmentEndMs`)

- Источник таймингов — не `klucz.pdf` (это только ключ ответов, не транскрипт с
  таймкодами) и не `arkusz.pdf` (буклет вопросов). Официальный CKE не публикует метаданные
  таймкодов — только ручная разметка на слух, по репликам ведущего («Zadanie 2. Proszę...»).
- 6 экзаменов × 5 заданий = 30 чисел на файл — разметка вручную (любым плеером с видимым
  текущим временем, в т.ч. самим `AudioSegmentPlayer`, если включить debug-режим с видимым
  `currentTime` в мс) полностью пропорциональна объёму, отдельный инструмент размётки не
  оправдан на этом масштабе.
- Формат хранения не меняется — он уже есть в `dsl/exam.data-contract`
  (`segmentStartMs`/`segmentEndMs: int`, миллисекунды). Нужно только заполнить реальные
  значения вместо текущих `0`/`0` во всех `listening-tasks.core-data` файлах (это задача
  data-pipeline/import агента, не этого плана).

## «Nagranie zostanie odtworzone dwa razy» (двойное прослушивание II–V)

Открытый факт, который нужно установить ДО того, как писать плеер-логику повтора: в настоящей
записи CKE этот текст — это часть самой фонограммы, т.е. аудио **уже содержит** две
проигровки задания одна за другой (ведущий сам говорит фразу, затем звучит дважды). Если это
так для данных файлов (нужно прослушать 1–2 реальных задания из `ExamBin/pl/B1/2019/audio.mp3`,
чтобы подтвердить), то：
- `segmentStartMs..segmentEndMs` просто охватывает оба проигрывания целиком, как записано —
  плееру **не нужна** программная логика повтора, только обычный play/pause/replay одного
  непрерывного сегмента. Это самый простой путь и совпадает с «чем меньше кода, тем лучше».

Если на части записей (например, более старых экзаменов) повтора в фонограмме нет и там звучит
только один проход — тогда нужен optional `repeatCount: Int = 1` на `ListeningTaskRow`
(contract-правка: `OPTIONAL`, не ломает уже написанные `.core-data`), и плеер в `replay()`-пути
сам зацикливает `[startMs, endMs]` `repeatCount` раз с короткой паузой между проигрываниями.
**Не добавлять это поле заранее** — сначала прослушать реальные файлы; вводить ветвление раньше
факта — это и есть то самое "jump to conclusions", от которого явно просили удержаться.

## Проверка

- Unit (commonTest/webTest недоступен для DOM-логики `<audio>` — Kotlin/JS DOM API не мокается
  в чистом JVM-тесте) → логика сегмента (авто-стоп на `endMs`, пересчёт `positionMs` относительно
  `startMs`, решение «пересоздавать `src` или нет» по сравнению URL) выносится в чистую функцию/
  маленький класс без DOM-зависимости, тестируемую в `webTest`/`commonTest` (например
  `SegmentClock.onTimeUpdate(currentMs): PlayerAction` — pure function). Сам `<audio>`-биндинг
  остаётся тонким и непокрытым unit-тестами.
- Playwright (`tests/browser/`): новый сценарий — зайти в listening-задание, кликнуть Play,
  убедиться что аудио не сбрасывается при выборе ответа (регрессия на найденный баг),
  переключиться на следующее задание и проверить, что `<audio>`-элемент в DOM не был
  пересоздан (например, по стабильному `data-testid` без потери `currentTime`), что даёт прямое
  покрытие бага из «Проверенные факты».
- Руками: один реальный экзамен (`b1-2019`) с реально размеченными 5 сегментами — слушать
  каждый от начала до авто-стопа, нажать Replay, нажать Play/Pause во время воспроизведения.
