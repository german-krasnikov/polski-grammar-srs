# P18: проверяемое расширение курса pl-ru

2026-11-13. Design handoff по [P13–P19](EXAM-LEARNING-QUALITY-PLAN.md) и [матрице пробелов](COURSE-EXAM-GAP-LEDGER.md). Цель — доступные из тренировки правила, разнообразные полные предложения и сводки по десяти установленным семействам заданий, с честными источниками и четырьмя способами подачи. Архитектор не пишет учебные тексты, не запускает тесты и не утверждает, что 127 экзаменных групп или весь B2/C1 уже покрыты. Текущий `pl-ru`: 16 навыков A1/A2/B1, 32 лайфхака; в 16 опубликованных экзаменах 127 grammar groups/1125 grammar items. Цифры воспроизводятся соседним `recovery-logs/20261112/exam-learning-quality/course-gap-inventory.{mjs,json}`.

## Состав первой полной поставки P18

Один новый устойчивый `SkillRow.id` и минимум **шесть разных упражнений с полными предложениями** на каждое из десяти семейств. Уровень указывать педагогически, не автоматически по исходному экзамену; `dsl/course.data-contract` сейчас допускает лишь A1/A2/B1/B2, поэтому C1 строка требует явного аддитивного `C1` в enum и проверки потребителей. Первой связной поставкой можно маркировать B1/B2 вводные навыки, даже если потребность обнаружена в C1; такую строку нельзя называть полным покрытием C1.

| Новый ID (предлагается) | Доказанный источник потребности | Существующая опора/предпосылка |
| --- | --- | --- |
| `degree.comparison` | B1/2017 Grammar II; B2/2017 VIII | `agreement.my`: формы прилагательного; сравнение требует отдельной операции. |
| `verb.participles` | B2/2017 Grammar I; C1/2024-04 VI | `verb.past`, `aspect`: не смешивать страдательные/деепричастные формы с базовой формой на `-ł`. |
| `voice.impersonal` | B2/2017 Grammar III | `verb.past`, `case.inst`: деятель/объект и безличность. |
| `wordform.nouns` | B2/2017 Grammar VI; C1/2024-04 III | `verb.present`, `agreement.my`: образование существительного, не только склонение. |
| `numeral.agreement` | B2/2017 Grammar VII; C1/2024-04 I | `sentence.plural`, `case.gen.neg`: числа и управление группы. |
| `wordform.adjectives` | C1/2024-04 Grammar IV | `agreement.my`: производная основа и дальнейшее согласование — разные шаги. |

Имена ID, уровни, prerequisites и шесть проверенных примеров фиксируются автором данных до генерации; после выпуска ID не переименовываются. Несколько тем нельзя склеить в один навык ради счётчика. Для каждого навыка: 6+ различающихся ситуаций/лемм/структур, включая хотя бы один осмысленный контраст и один типичный ошибочный перенос русского; исходное предложение → одна названная операция → целое целевое предложение, объяснение изменения и независимо сверенный ожидаемый ответ. Одно и то же предложение с заменой имени или пунктуации не считается новым типом. Это проверяемый минимум разнообразия, не обещание полной подготовки к B2/C1. Существующие 16 навыков и chain остаются прежними.

**Почему pool, а не новая машина форм.** Существующие `FeatureBundle`, `TextSpec`, `ConstructionRealizer` применять там, где они уже выражают правильное правило и дают разные предложения. Для производных, причастий, условных перестроек и управления новых парадигм пока нет; выдумывать польскую морфологию из нескольких строк нельзя. Один `staticOverride` делает курс механически повторяющимся. Универсальный pool — маленькое аддитивное расширение существующего escape hatch с двумя реальными pack/host consumers; оно не содержит польских веток, не копирует правила в Kotlin и допускает будущую замену на корректный генеративный рецепт. Не вводить новый Core pattern/TEMPLATE или отдельный курсный модуль ради этих десяти тем. Сравнить фактические места правки, объём rows и проверку before/after первого vertical slice по biome BestPractice/P25; если конкретная тема уже решается `TextSpec`, для неё pool не обязателен.

## Совместимость, данные и ресурсы

- У каждого нового навыка одна стабильная карточка FSRS по skill ID, как у существующих; шесть вариантов — упражнения этого навыка, а не шесть новых skill IDs. `ProgressCodec.completeKnownSkills` дополняет старый документ новыми known skills; сохраняет reviews/due/history старых 16 и unknown/foreign IDs. Проверить export/import, cold restart, выбор `pl-ru`→`en-ru`→`pl-ru`; не менять сериализованные ключи старого прогресса и defaults предпочтений. Новые навыки появляются в picker немедленно, prerequisite служит педагогической связью и проверкой DAG; **не** вводить неописанное блокирование выбора или silent FSRS reset.
- `ExerciseGenerator` владеет только кратковременным order state пула. Закрытие TrainingStore/новый экземпляр начинает новый перемешанный цикл; прогресс сохраняет только review, не порядок вариантов. Ошибка отсутствующего copy key или неверного source form должна прерывать генерацию/тест, не показывать пустой ответ. Все старые dynamic/static recipes получают byte-identical поведение и имеют прежние fixtures.
- `reference.core-data` существует как один `REFERENCE` record; добавить `systemCards` внутрь него, не придумывать отдельный `ReferenceRow` на тему. Каждая summary card ссылается тем же ID на навык (если текущий `RefSystemCardRow.id` просто string, проверить уникальность и интеграцию) и даёт правило/пример/шаги; web `MatrixWeb.renderMap` и iOS matrix уже показывают system cards. Android reference consumer проверить отдельно: он может не показывать эту секцию, поэтому Android acceptance требует минимум card-level explanation и focused exercise, а не заявления о Matrix parity. Desktop UI не расширять: заморозка допускает только bugfix; общие строки остаются читаемы без новой desktop поверхности.

## Приёмка и порядок Developer → Tester → Reviewer

1. **Срез A: механизм pool и один навык `degree.comparison`.** Developer сначала проверяет, можно ли честно собрать шесть конструктивных вариантов из существующих feature forms. Если нет — вводит optional `staticPool`; в обоих вариантах выставляет `caseReferenceAvailable=false`, шесть source-backed предложений, `SkillRow` с двумя methods и `styleContent`, один проверенный `LifehackRow`, одна summary `systemCard`. Осмысленный RED: разные упражнения одного навыка, полный source/expected, no-repeat до исчерпания (если pool), старый `aspect` singleton и старые dynamic cases не изменились. GREEN через реальные Kotlin consumers/skill picker; independent Tester проверяет грамматический источник и Browser PlayTest.
2. **Срезы B–D: оставшиеся девять.** B: `verb.participles`, `voice.impersonal`, `verb.mood` (форма и синтаксис); C: `wordform.nouns`, `wordform.adjectives`, `numeral.agreement`; D: `sentence.connectives`, `sentence.rephrase`, `case.valency`. Для каждой: таблица `exam testId → source PDF/key page → независимый грамматический источник → rule/citation → SkillRow/recipe/example key → review case`, шесть различных полных предложений и expected answers, variant/accepted forms только при независимом источнике. Source author/Developer пишет строки, Tester проверяет факты/формы/смысл/орфографию, Reviewer смотрит diff и отсутствие незаявленного scorer/FSRS изменения. Не придумывать citation, не переписывать официальный ключ, не заявлять все задания экзамена покрытыми.
3. **Срез E: интеграция и стиль.** Проверить, что все 10 навыков достижимы из web picker, выбранная тема выдаёт 6 различных упражнений за один цикл, а card back и Matrix summary доступны; проверить все четыре `PreferredStyle` для каждого навыка, отсутствие молчаливого fallback у NativeContrast и отсутствие раскрытия ответа на front. В зависимости от изменённых consumers — Kotlin common/JS/Wasm, Android compilation/Compose scenario, iOS bridge/Simulator, web PlayTests с реальным выбором навыка, вводом, раскрытием, повтором и обратным курсом. Старые цепочки/16 навыков, JSON progress roundtrip и FSRS сохраняются. Все browser/native/device gate отчёты отдельные PASS/FAIL/NOT RUN.

Данные: `biome fmt <changed .core-data>` → `biome generate --project dsl/biome.project` → `biome generate --check --project dsl/biome.project`; `BIOME_BIN` берётся из доступного соседнего checkout, не меняет toolchain pin. Независимые ожидания в `commonTest`/PlayTest опираются на исходные предложения и источники, не на сгенерированный текст как oracle. Фиксированные исторические ожидания меняются только с реальным требованием. Документацию готовит Developer/main: состав 10 тем и границы B2/C1, цитаты, пользовательские настройки и честные host results; `AI/decisions.md` фиксирует новый продуктовый контракт/изменение уровня, если принято. Никакого deployment/production switch из одного дизайна не следует.
