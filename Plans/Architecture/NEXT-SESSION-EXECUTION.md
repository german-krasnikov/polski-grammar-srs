## P1. Четыре сдачи 2017/2020

**Первый незавершённый срез — B1/2017.** Затем тем же проверенным маршрутом B1/2020, B2/2017, B2/2020. Для каждой сдачи разработчик сверяет `grammar-tests/items`, `listening-tasks/questions`, `reading-passages/questions`, `writing`, `exam` с её `arkusz.pdf` и `klucz.pdf`, фиксирует число заданий и типы; открытые/неоднозначные ответы отмечает как требующие ручной оценки, не придумывает ключ. Значения 0/0 для сегментов означают «не размечено»: получить транскрипцию/таймкоды из соответствующего MP3 и проверить границы на слух до публикации listening. Не копировать интервалы 2019. `audioUrl` и фактическая доставка MP3 проверяются отдельно согласно аудиоплану.

Изменяемые источники: `exams/pl/certyfikat-polski/{B1,B2}/{2017,2020}/*.core-data`; `dsl/biome.project` — четыре шага по образцу строк 12–13; `kotlin/shared/src/commonMain/generated/kotlin/polski/exam/data/{b1y2017,b1y2020,b2y2017,b2y2020}/ExamRows.kt` **NEW, только biome**. После полного набора строк подключить сдачу через существующие `ExamData.kt`, `ExamReadingData.kt`, `ExamListeningData.kt`, `ExamWritingData.kt`, `ExamWeb.kt`; при росте копий `mapB1*`/`mapB2*` вынести общий shape mapper, сохранив типизированный вход, без нового публичного API shared. Не показывать сдачу в каталоге до готовности всех четырёх разделов и аудиодоставки; если доставка недоступна, явно пометить listening недоступным, а не запускать пустой плеер.

Критерии E1–E4 на каждую сдачу: (E1) контракт/ссылки и `fmt` проходят, `generate --check` чистый; (E2) количество, порядок, диакритика и ключи совпадают с PDF, расхождения записаны; (E3) каждый тип вопроса из сдачи имеет работающее представление/сохранение ответа и корректный итог, либо раздел не объявлен готовым; (E4) все пять аудиосегментов имеют проверенные start/end, файл доступен и воспроизведение доходит до конца. При сомнительном PDF-фрагменте не менять эталон догадкой.

## P2. SchedulerExpandedTest → DSL oracle

Существующий `kotlin/shared/src/commonTest/kotlin/polski/srs/SchedulerExpandedTest.kt` содержит 70 кейсов, около 1144 строк; `generate_expanded_kotlin.py` отражает старую процедуру получения oracle из `ts-fsrs 5.4.2`. Новый источник `dsl/scheduler-expanded/scheduler.core-data` **NEW** заполняется из зафиксированных входов/выходов текущего теста, с provenance версии и датой; не вызывайте `FsrsScheduler` для создания expected. `dsl/scheduler-expanded.data-contract` уже существует как untracked и сохраняется. Добавить `CONTRACT scheduler-expanded` и `GENERATE scheduler-expanded data ... --rows SchedulerExpandedCaseRow ... --target kt --kt-package polski.srs.data.oracle --out kotlin/shared/src/commonTest/generated/kotlin/polski/srs/data/oracle/SchedulerExpandedCaseRows.kt` в `dsl/biome.project`. Генерат **NEW**, только biome.

Короткий рукописный `SchedulerExpandedTest.kt` читает каждую строку, парсит ISO instants/null, создаёт `StoredCard`, вызывает `FsrsScheduler.preview` и `review`, сверяет четыре preview времени и все поля `SrsCard` с тем же допуском `1e-7` для stability/difficulty; проверяет неизменность source и равенство выбранного preview `reviewed.card.due`. `Rating`/`CardState` валидировать по допустимому диапазону перед `entries[index]`; id кейса в каждом сообщении. `generate_expanded_kotlin.py` после миграции либо удалить, либо оставить как архивный provenance без права перезаписывать oracle.

Критерии S1–S3: ровно те же 70 id и входы, 70×4 preview и все прежние review assertions; намеренная порча одного ожидаемого due/состояния вызывает RED с id; Gradle common test и `biome generate --check` GREEN. Изменение FSRS-версии — отдельное решение и независимый oracle, не часть механической миграции.

## P3. Exam web UI и аудио

`ExamGrammarWeb.kt` уже обновляет ответ на текущем вопросе через `updateInPlace()`; проверка браузером набора польского текста, caret/IME и перехода назад/вперёд обязательна до объявления focus loss закрытым. `ExamReadingWeb.kt` использует `change` для текстового ответа, а типы кроме TrueFalse/FillGap попадают в общий options-рендер; `ExamListeningWeb.kt` имеет аналогичный узкий набор. Разработчик строит матрицу фактически встречающихся `QuestionType` в подключённых строках, затем реализует конкретные input/answer semantics для `word_bank`, `matching`, `transform`, `gap_fill_fragment` там, где есть реальные данные. Не считать `options` универсальным представлением для типов без options. Scorer остаётся по P25 native, как уже решено в EXAM-DSL-FIRST; при новых вариантах ответа сначала зафиксировать независимые scoring cases в `dsl/exam-scoring/scoring.core-data`.

Аудио: `ExamListeningWeb.kt` владеет одним `HTMLAudioElement` на controller; переключение задачи меняет границы сегмента, выбор ответа не меняет `src`/позицию, уход со страницы останавливает и освобождает обработчики. Предыдущий [аудиоплан](EXAM-AUDIO-PLAYBACK-PLAN.md) требует сначала проверить на реальной фонограмме, содержит ли она два проигрывания после фразы «nagranie zostanie odtworzone dwa razy». Если да — сегмент охватывает обе записи, программного повтора нет; если нет — аддитивный `repeatCount` в `dsl/exam.data-contract` и проверяемая политика повторения, но не дублирование уже записанного звука. Это открытый факт, а не разрешение зашить два play в UI.

Критерии U1–U4: focus/caret и составной ввод не сбрасываются; каждый представленный тип допускает ввод/исправление/возврат и сохраняет ответ до Submit; score/review совпадают с DSL oracle; Play/Pause/Replay, выбор ответа, смена задания и конец сегмента не сбрасывают запись, не создают лишний listener и не проигрывают её лишний раз. Если MP3 локальный и не включён в artifact, Playwright тест использует разрешённую фиксированную аудиофикстуру на реальной media boundary, а ручной реальный MP3 остаётся отдельной проверкой.

## P4. Playwright и PlayTest

`playwright.kotlin.config.ts` запускает `tests/browser/kotlin-*.spec.ts` для переданного production distribution и ветки `wasm|js`; `playwright.config.ts` обслуживает React. Прежние «53 passed, ~9 обновить» — исторический итог из NEXT-SESSION-PLAN, не текущий статус. Сначала получить точный список/причины failures на актуальном artifact; обновлять ожидания лишь вследствие принятой model change, а не чтобы скрыть регрессию. Добавить `tests/browser/kotlin-exam.spec.ts` **NEW** в Kotlin `testMatch` для E/U, использовать реальные DOM controls, input, audio и score; фиксировать context/fixture и ожидать видимый state, без `waitForTimeout`.

Пилот DSL PlayTest: один сценарий «выбор сдачи → заполнение ответа → возврат → Submit → score» и один «play → выбор ответа → segment end» на короткой контролируемой медиафикстуре. Проверить имеющийся CLI/compiler test-dialect на `PLAN_COMMAND`/query, затем предложить `dsl/exam-web/*.playtest` и узкий Playwright host **NEW** только если этот путь компилируется/исполняется без нового DSL синтаксиса и не дублирует локаторы/expected в TS. Host владеет browser context, fixture, cleanup, timeouts, аудио-событиями; DSL задаёт действия/наблюдаемые ожидания. Измерить авторские строки, места правки и число общих сценариев против двух чистых `.spec.ts`; если адаптер больше/сложнее без второго хоста или гарантий, записать P25 S1/S4 и оставить нативные Playwright tests. Не считать PlayTest доказательством до реального браузерного исполнения.

Критерии B1–B3: девять исторически падавших сценариев идентифицированы и классифицированы по актуальному run; каждый исправленный тест снова проверяет вход, видимый результат и состояние; новая exam lane проходит на заявленной сборке/браузере, JS/Wasm и Chromium/Firefox/WebKit маркируются PASS/FAIL/NOT RUN отдельно. WebKit automation не равен Safari device.

## Команды и handoff

Сначала определить локальный `BIOME_BIN` соседнего checkout (пример: `/Users/german/Work/Python/biome-dsl/implementations/typescript/packages/biome/src/bin.mjs`) и актуальный toolchain pin из `dsl/biome.project`. Для каждого изменённого `.core-data`: `node "$BIOME_BIN" fmt <file>`, `node "$BIOME_BIN" generate --project dsl/biome.project`, затем `node "$BIOME_BIN" generate --check --project dsl/biome.project`. Использовать реальные Gradle tasks из `kotlin/README.md`/`./gradlew tasks --all`; не выдавать предполагаемую задачу за выполненную. Kotlin браузер: сборка фактической production distribution, затем `KOTLIN_SPIKE_DIST=<abs-dir> KOTLIN_SPIKE_BRANCH=wasm|js npx playwright test -c playwright.kotlin.config.ts ...`; точную команду/путь зафиксировать в evidence. `npm run typecheck` проверяет TS конфиги/тесты; React `npm test` не доказывает Kotlin web.

Developer получает P1/B1-2017 первым, затем последовательно P2–P4 с TDD RED/GREEN для новых поведенческих случаев и точным diff относительно dirty baseline. Tester независимо проверяет E/S/U/B и браузерные сценарии на реальном artifact; Reviewer читает diff и evidence. `AI/decisions.md` обновляется только при новом решении (например, подтверждённый repeat policy или результат P25 PlayTest пилота). Обновить `NEXT-SESSION-PLAN.md` по фактическим завершённым срезам; Docs owner — Developer или основной агент. Для каждой группы отдельно отметить тесты, компиляцию, сборку, браузеры и устройства как PASS/FAIL/NOT RUN.
